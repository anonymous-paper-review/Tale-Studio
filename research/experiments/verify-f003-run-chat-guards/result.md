# 존재하지 않는 인물 이름이 샷에 새로 들어갔는가

실행: 2026-08-16 밤 · 티켓 `.claude/vault/backlog/verify-f003-run-chat-guards.md` · 조회만, 지출 0원

## 한 줄 결론

**밤이 맡은 감사 부분은 통과.** 수리 배포(2026-08-13) 이후 만들어진 샷 72행 중, 인물 명단에
없는 이름을 달고 있는 행은 **0행**이다. 배포 이전 구간에는 같은 검사가 16행(이름 등장 17회)을
잡아내며, 그 이름이 사고 기록에 적힌 `girl` / `tracker` 와 정확히 일치한다 — 검사 자체는 작동한다.

다만 **가드가 실제로 발동한 적이 있는지는 확인 못 했다**(아래 "빠진 대조군" 참고).
그리고 티켓이 요구하는 오너 3단계는 아직 하나도 밟히지 않았다.

## 무엇을 물었나

글쓰기 파이프라인이 도는 도중에 채팅이 끼어들어 별개 초안을 만들었고, 그 초안이 존재하지 않는
인물 이름(`girl`, `tracker`)을 달고 저장돼 인물 그림 연결이 전부 끊긴 사고가 있었다.
막는 장치를 3겹(화면 입구 · 저장 직전 거부 · 삭제 범위 제한)으로 깔았다.
밤이 셀 수 있는 것은 하나 — 그 이후로 명단 밖 이름이 **새로** 생겼는가.

## 어떻게 쟀나 — 티켓에 적힌 자 그대로

티켓 원문: "`shots.characters` 에 `characters` 테이블 밖 id 가 **수리 배포(2026-08-13) 이후 새로**
생겼는지 조인으로 센다."

실제 질의(스크립트 `probe.mjs`, 1000행씩 나눠 전량):

```
select id, project_id, character_id, name from characters                 -- 정본 명단 112행
select id, project_id, scene_id, shot_id, characters, source, created_at
from shots order by created_at asc                                        -- 샷 1796행
```

**조인 정의**: `shots.characters` 배열의 각 값이, 같은 프로젝트의 `characters` 행의
`character_id` / `id` / `name` 셋 중 **어느 것과도** 안 맞으면 "테이블 밖"으로 센다.
셋을 다 맞춰본 이유는 오탐을 피하려는 것이다. 정본 짝은 `character_id` 이며,
근거는 제품 코드 주석 `src/lib/writer/pipeline/util/persist_manifest.ts:13`
— "shots.characters 와 characters.character_id 가 동일 id 공간(referential 정합)".

**시각 경계**: 티켓은 날짜만 준다("수리 배포(2026-08-13) 이후"). 시각이 안 적혀 있어
그 날 0시(UTC) `2026-08-13T00:00:00Z` 를 경계로 잡았다. 이 선택은 결과를 바꾸지 않는다 —
경계 이후 첫 샷은 2026-08-13 03:4x 대에 만들어졌고, 명단 밖 이름은 2026-08-12 07:14~07:15 에만
몰려 있어 어느 시각을 잡아도 같은 쪽으로 떨어진다.

## 판정선 대입

티켓 원문: "판정선: 신규 발생 0건이면 통과. 1건 이상이면 가드 구멍 — 해당 행 좌표를 아침 리포트에 올린다."

배포 이후 신규 발생 0건 → **통과**. "1건 이상" 쪽에 해당하는 행이 없어 아침 리포트에 올릴
가드 구멍 좌표는 없다.

## 빠진 대조군 — 이건 확인 못 했다

숫자가 0이라고 해서 "가드가 막았다"가 되지는 않는다. 세 가지를 같이 봐야 한다.

1. **배포 이후 샷 72행은 전부 파이프라인 산출이다** (`source` 값이 전부 `pipeline`).
   즉 배포 이후에 채팅이 샷을 만든 일 자체가 한 번도 없다. 막을 일이 없었던 것과
   막아서 안 생긴 것을 이 감사는 구분하지 못한다.
2. **`source` 칸으로는 파이프라인과 채팅을 가를 수 없다.** 데이터베이스 전체 1,796행이
   **전부** `source = 'pipeline'` 이다. 사고 당시 채팅이 만든 그 16행도 `pipeline` 으로 찍혀 있다.
   따라서 이 칸은 지금 시점에 출처 구분자로 못 쓴다.
   덤으로: 티켓의 오너 3단계 중 ③이 요구하는 `source='manual'` 값은 데이터베이스에 아직 한 번도
   등장한 적이 없다.
3. 그러므로 "가드 3겹이 실제로 발동해서 막았다"는 **확인 못 함**으로 남긴다.
   그걸 확인하려면 런 중에 채팅으로 발명 인물을 유도해봐야 하고, 그건 티켓이 오너 몫으로
   지정한 부분이다.

## 아직 안 끝난 것 (오너 몫 — 티켓 본문에 있던 그대로)

티켓은 "순서대로 세 단계 다 밟아야 닫힌다"고 적었다. 셋 다 미실시다.

1. 런 진행 중 채팅 수정 시도 → 건너뜀 안내가 나오는지 확인
   (**씬 게이트 대기 중**이 핵심 — 저장 직전 거부 장치가 화면 입구 게이트보다 넓은 유일한 지점)
2. 발명 인물 유도 → "반영하지 않았어요" 응답 + 데이터베이스에 안 남는지 확인
3. 런 완료 후 수동 씬·샷 추가(`source='manual'` 확인) → 재런 → 수동분 생존 확인 →
   충돌 유도 시 런이 죽지 않고 경고만 남는지
