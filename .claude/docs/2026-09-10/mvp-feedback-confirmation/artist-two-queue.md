# MVP-25: 두 인물의 다른 시간대 모습 생성 접수

**첫 인물의 이미지 완성을 기다리느라 두 번째 인물이 큐에 들어가지 못하던 경로를 재현하고 수정했습니다.** 이제 첫 작업의 접수 번호가 확인되면 두 번째 인물도 접수합니다. 두 이미지의 완료·실패 안내와 결과는 각 인물에 따로 연결됩니다.

이 항목의 완료 기준은 두 인물의 이미지 생성 접수입니다. 이전의 코드 문장 비교 테스트 2개는 별도의 검사 방식 문제이며, 사용자에게 그 테스트의 수정 승인을 요청한 것은 이 제보의 해결과 다른 문제였습니다. 이번 작업에서 해당 2개 테스트의 기대값·skip·문장은 바꾸지 않았습니다.

## 약속과 이유

- **두 인물의 다른 시간대 모습을 함께 요청하고 승인하면 두 인물의 새 모습 이미지가 각각 큐에 등록된다.** 왜: Artist 채팅에서 쿄타로와 코마츠의 잠옷 모습을 함께 요청했는데 한 인물만 큐에 보였다는 제보를 실제 접수까지 확인한다.
- **인물 순서를 뒤집어 요청해도 같은 모습 이름 때문에 다른 인물의 접수가 중복으로 사라지지 않는다.** 왜: 두 인물 모두 ‘잠옷’이라는 같은 모습 이름을 쓴다.
- **두 번째 인물의 이미지가 먼저 완성되어도 완료 안내와 결과는 해당 인물에 붙는다.** 왜: 각각 진행하는 이미지의 완성 순서는 접수 순서와 다를 수 있다.
- **첫 이미지 생성이 실패해도 두 번째 인물의 접수와 완성은 유지하고 실패한 인물만 남긴다.** 왜: 한 작업의 실패가 다른 인물의 작업을 없애면 안 된다.
- **첫 인물의 접수가 거절되어도 두 번째 인물을 접수하고 다시 시도할 때 새 모습 행을 중복으로 만들지 않는다.** 왜: 이미 저장한 모습의 이미지 생성만 실패할 수 있다.
- **두 작업이 접수된 동안 승인을 다시 눌러도 새 모습과 유료 요청을 중복해서 만들지 않는다.** 왜: 기다리는 동안 승인 버튼을 다시 누르는 경우를 지킨다.
- **모델이 첫 인물의 제안만 보내면 두 인물을 완료했다고 하지 않고 빠진 이름을 알려준다.** 왜: 앱이 받은 제안 자체가 하나인 경우와 두 제안을 받고도 둘째를 접수하지 않는 경우를 구별한다.
- **첫 모습 저장 중 남은 요청을 취소하면 두 번째 인물의 새 모습과 이미지 접수는 시작하지 않는다.** 왜: 이미 시작한 저장과 아직 시작하지 않은 대상을 구별해 취소한다.

## 확인한 원인

기존 실행은 승인 목록의 항목을 순서대로 기다렸습니다. `createAppearance`는 새 모습을 저장한 뒤 `generateCharacterView`를 호출했고, 이 함수는 큐 접수 번호를 받은 뒤에도 이미지가 완성되거나 실패할 때까지 확인을 계속했습니다. 따라서 첫 인물만 접수된 상태에서 두 번째 인물은 첫 이미지의 완성까지 대기했습니다.

새 검사에서 모델이 정확히 두 인물의 제안을 반환하도록 고정했습니다. 실제 채팅 파싱과 승인 목록에는 두 인물이 들어왔지만, 첫 이미지의 완료 응답을 보류하자 생성 작업 기록은 1개뿐이었습니다. 이것이 수정 전 실패의 직접 원인입니다. 이 재현은 현재 코드 경로의 고장을 증명하며, 당시 운영 사건의 모델 응답·큐 기록 전체를 확정한 것은 아닙니다.

수정은 `src/stores/global-chat-store.ts`에 한정했습니다. 접수 번호를 받으면 다음 대상을 시작하고, 각 작업의 완료 관찰과 남은 요청 보존을 해당 인물에 고정했습니다. 모습 생성·이미지 생성 서버나 기존 다른 세션의 채팅 도구 구현은 바꾸지 않았습니다.

## 검증 결과

| 검증 | 결과 |
|---|---|
| 수정 전 두 인물 접수 재현 | 실패: 요청한 2개 중 실제 작업 기록 1개 |
| 새 연결 검사 | 8개 통과 |
| 관련 회귀 검사 | 8개 파일, 66개 통과 |
| Artist·Chat 전체 | 583개 통과, 기존 코드 문장 비교 2개 실패, 기존 1개 제외 |
| TypeScript | 통과 |
| 변경 파일 ESLint | 오류·경고 없음 |

연결 검사는 실제 `Artist POST → 응답 파싱 → 승인 → createAppearance → 모습 생성 POST → generateCharacterView → generate-sheet POST → falImageSubmit 입력 조립 → createGenerationJob`을 거칩니다. 두 작업이 모두 아직 진행 중인 시점에 서로 다른 접수 번호, 두 개의 저장된 작업, 각 인물의 기준 얼굴 참조, 각 잠옷 설명, 미래 시점 저장을 확인했습니다.

DB 통신은 메모리 어댑터, 모델 응답은 고정 응답, 외부 이미지 제공자 접수는 가짜 HTTP입니다. 인증·이미지 한도·템플릿 조회 등 이 제보와 독립인 경계는 테스트용으로 고정했습니다. `createAppearance`, `generateCharacterView`, 생성 라우트, 프롬프트 조립, 중복 검사, 작업 저장 함수를 통째로 가짜 함수로 바꾸지 않았습니다. 실제 유료 모델이나 운영 DB에 새 작업을 만들지 않았습니다.

## 남은 범위

실제 유료 이미지 생성과 배포 후 사용자 프로젝트 실행은 이번 검증에 포함하지 않았습니다. 모델이 두 번째 인물의 제안 자체를 생략하는 경우는 기존 누락 안내가 동작함을 확인했으며, 임의의 생성 명령을 만들어 유료 실행하지 않습니다. 이미지 동시 작업 한도에 걸리면 접수가 거절될 수 있고, 이때 남은 인물과 이미 저장한 모습이 보존되는 것을 검사했습니다.

작업 브랜치는 `dev`이며 `main` 병합·커밋·운영 배포는 하지 않았습니다.
