# Writer 미확인 이미지 숫자 수정 보고

**Writer에서 아직 보지 않은 러프 이미지의 완료 수를 표시하는 경로를 검증하고, 숫자 갱신 누락·옛 결과 재알림·중복 샷 집계 오류를 수정했다.** Director의 실사 이미지·영상 수를 Writer에 합산하지 않는다. 생성 요청만 접수되었거나 저장이 실패한 결과는 완료 수에 넣지 않는다.

사용자 확정: “아직 안 본 완료 이미지 수로 하고 싶음.” 현재 Writer를 보고 있을 때는 숫자를 숨기고 읽음 처리한다. 다른 탭으로 옮긴 뒤 새로 완료된 결과부터 다시 쌓는다. 처음 방문하지 않은 단계에 옛 완료를 한꺼번에 쌓지 않는 기존 규칙은 유지한다.

## 원인과 수정

| 문제 | 확인된 원인 | 조치 |
| --- | --- | --- |
| 완료했는데 숫자가 갱신되지 않을 수 있음 | 수신 기록의 전체 개수와 마지막 완료 시각만 비교함. 둘이 같으면 중간 기록의 단계·완료 수 변경을 놓침. | 모든 완료 기록의 단계·종류·시각·이미지 수를 비교함. 순서만 달라진 재수신은 무시함. |
| 이미 본 결과가 다시 새 완료로 뜰 수 있음 | 완료 시각 대신 마지막 수정 시각을 사용함. 완료 후 추적 정보를 붙이는 함수도 수정 시각을 바꿈. | 실제 완료 시각 `completed_at`을 우선 사용함. 그 값이 없는 예전 기록만 기존 시각으로 호환함. |
| 같은 샷이 한 묶음 안에 중복 기재되면 숫자가 늘어남 | 샷 식별자 배열 길이를 그대로 셈. | 같은 샷은 한 번만 셈. 같은 작업 기록을 중복 수신해도 한 번만 셈. |
| 10개 이상이 정확히 보이지 않음 | 배지에 `9+`로 축약함. | 실제 숫자를 표시함. |
| 하루가 지나거나 생성 이력이 많으면 아직 보지 않은 숫자가 사라짐 | 배지가 최근 진행 배치용 24시간·500행 조회를 재사용함. | 완료용 조회를 분리하고 성공 완료 이력을 마지막 페이지까지 읽음. 중간 페이지 실패는 불완전한 숫자를 정상 응답으로 반환하지 않음. |

Director 기능을 새로 연결하거나 파이프라인을 통합한 작업이 아니다. Writer의 러프 이미지 작업은 원래 `shot_rough_storyboard`로 구분되어 Writer에만 집계된다. 이전 보고에서 프리비즈 영상과 Writer 러프 이미지를 함께 설명한 것은 잘못된 설명이었다.

## 실제 저장에서 숫자까지

1. 러프 이미지 작업이 큐에 접수되어도 숫자는 0이다.
2. 결과 그리드를 샷별 시작·진행·끝 이미지로 나누고 파일과 샷 정보를 저장한다.
3. 묶음에 속한 모든 샷 저장이 성공한 뒤 작업을 완료 처리한다.
4. 공통 큐 조회가 완료된 러프의 샷 수를 Writer 완료 기록으로 반환한다.
5. Writer를 마지막으로 확인한 뒤 완료한 샷 수만 왼쪽 Writer에 표시한다.

한 샷의 시작·진행·끝 파일 3개를 숫자 3으로 세지 않는다. Writer 카드 한 샷을 1로 세며, 4샷 묶음 저장이 끝나면 4가 더해진다. 저장 중인 묶음은 아직 완료로 세지 않는다. 진행 중에는 공통 조회 주기 약 4초에 숫자가 반영된다.

## 검증

- 수정 전: 신규 회귀 테스트 7개 중 4개 실패를 확인했다. 기존 기대값을 바꾸지 않고 구현을 수정했다.
- 수정 후: 관련 테스트 40개 통과 후 오래된 이력·실제 공통 응답 검증 5개를 추가했고, 전체 생성 작업 묶음 **209개 / 36파일 통과**.
- 타입 검사 통과, 수정 제품 파일 lint 오류·경고 0개, diff 공백 검사 통과.
- 마지막 샷 저장을 멈춘 상태에서 숫자 0 → 저장을 풀면 숫자 2가 되는 실제 완료 함수 호출을 검증했다. 외부 이미지 제공자와 저장소 응답을 대체한 결정론적 실행이며, 새 유료 이미지를 생성한 검증은 아니다.
- 저장 실패 시 완료 함수가 호출되지 않음을 확인했다.
- 기존 프로젝트 전환·늦은 응답 폐기·현재 Writer 읽음 후 이탈·다음 새 완료만 증가하는 테스트도 통과했다.
- 추가 이력 검증 3개도 먼저 실패를 확인하고 구현했다. 사흘 전 완료 1개가 남고, 1,002개가 3페이지 모두에서 빠짐없이 집계된다. 다음 페이지 실패 시 일부 숫자만 성공처럼 반환하지 않는다. 권한 확인 전에는 완료 이력을 읽지 않는다.
- 화면 캡처는 루트 에이전트 통합 검증에 포함한다.

증거: `writer-badges-red.txt`, `writer-badges-history-red.txt`, `writer-badges-green.txt`, `writer-badges-job-suite.txt`, `writer-badges-typecheck.txt`, `writer-badges-lint.txt`.

## 약속과 필요한 이유

- “러프 이미지 한 샷이 완료되면 Writer 숫자는 1부터 오르고 다음 세 샷이 완료되면 4가 된다.” — 정상 완료 수를 카드 단위로 고정한다.
- “러프 이미지의 접수와 실패 및 Director 이미지·영상 완료는 Writer 숫자를 올리지 않는다.” — 진행 중·실패·다른 단계의 결과를 완료 이미지로 오해하지 않게 한다.
- “한 러프 결과의 같은 샷이 중복 기재되거나 같은 완료를 다시 받아도 이미지 수를 중복으로 올리지 않는다.” — 재수신과 중복 타깃으로 숫자가 부풀지 않게 한다.
- “이미 확인한 러프 완료에 나중에 추적 정보가 붙어도 새 이미지 완료로 다시 알리지 않는다.” — 생성 완료 이후의 기록 정리가 완료 알림을 다시 켜지 않게 한다.
- “완료 시각이 없는 예전 러프 기록도 기존 저장 시각으로 완료 개수를 표시한다.” — 예전 생성 기록이 사라지지 않게 한다.
- “전체 완료 기록 수와 마지막 시각이 같아도 Writer 완료 이미지 수가 바뀌면 숫자를 갱신한다.” — 새 결과가 있어도 숫자가 멈추는 문제를 막는다.
- “같은 완료 기록을 순서만 바꿔 다시 받아도 숫자를 다시 올리거나 변경 알림을 보내지 않는다.” — 동일 완료의 주기적 조회는 새 완료가 아니다.
- “러프 두 샷 중 마지막 저장을 기다리는 동안에는 0이고 모두 저장되면 Writer 완료 숫자는 2가 된다.” — 아직 저장되지 않은 결과를 완료로 보고하지 않는다.
- “러프 그리드 저장이 실패하면 완료 숫자를 올리거나 완료 처리하지 않는다.” — 실패를 성공으로 표시하지 않는다.
- “사흘 전에 완료한 러프도 아직 보지 않았다면 Writer 완료 숫자에 남는다.” — 오래되었다는 이유로 미확인 결과를 버리지 않는다.
- “완료 이력이 500건을 넘으면 남은 페이지까지 읽어 완료 이미지 수를 빠짐없이 표시한다.” — 생성 작업 수가 많아도 일부만 표시하지 않는다.
- “완료 이력의 다음 페이지를 읽지 못하면 일부 개수만 정상 결과처럼 돌려주지 않는다.” — 조회 실패를 완료 수 감소로 오해하게 하지 않는다.
- “현재 큐가 비어 있어도 사흘 전 저장한 Writer 이미지 완료를 공통 응답에 포함한다.” — 진행 중 작업이 없어져도 미확인 완료를 전달한다.
- “프로젝트를 볼 권한이 없으면 진행 작업과 과거 완료를 조회하지 않는다.” — 다른 프로젝트의 생성 이력을 노출하지 않는다.

## 남아 있는 기존 경계

완료 목록의 24시간·500행 누락은 이번에 함께 수정했다. 읽음 기준은 프로젝트별 브라우저 저장소에 있으며 여러 기기 사이의 읽음 동기화 기능은 기존에도 없다. 성공 이력이 많은 프로젝트는 전체 완료 조회에 더 많은 페이지를 사용한다. 마지막 읽음 이후만 서버에서 필터하는 최적화는 추후 할 수 있지만 정확한 숫자를 위해 임의의 총량 상한을 두지는 않았다. 기존 기록 중 실제 완료 시각이 비어 있으면 예전 수정 시각으로 호환한다.

## 통합 중 추가한 최초 방문 방어

완료가 0개일 때 `useStageBadges`만 실행하면 첫 방문 기록이 남지 않는 경로를 추가 검증했다. 실제 StudioLayout은 별도로 진입 시각을 기록하고 있으므로 이 현상을 원래 운영 화면 사건의 원인으로 단정하지 않는다. 훅도 스스로 미방문과 완료 0개를 본 방문을 구분하도록 최초 기준 0을 기록하게 했다. 이미 Layout이 기록한 최신 확인 시각은 덮어쓰지 않는다.

추가 4개 테스트 중 2개 실패를 먼저 확인하고 수정했으며, 최종 전체 생성 작업 묶음은 **213개 / 37파일 통과**다. 추가 파일과 변경 훅의 lint·diff 검사도 통과했다. 증거는 `writer-badges-first-visit-red.txt`, `writer-badges-first-visit-lint.txt`, 최종 `writer-badges-job-suite.txt`다. 실제 컴포넌트·브라우저 검증은 루트가 강제 읽음 주입을 제거한 뒤 최초 Writer 방문 → Artist 이동 → 첫 완료 1 경로로 수행한다.

- “완료가 없는 Writer를 처음 방문하고 다른 탭으로 떠난 뒤 첫 이미지가 완료되면 숫자는 1이 된다.” — 완료가 없는 첫 방문도 방문으로 남긴다.
- “한 번도 방문하지 않은 Writer의 옛 완료는 다른 탭을 처음 보는 동안 새 알림으로 쌓지 않는다.” — 기존의 미방문 단계 처리를 유지한다.
- “화면 진입에서 이미 기록한 확인 시각은 완료가 없어도 과거로 되돌리지 않는다.” — Layout이 남긴 최신 읽음 기록을 보존한다.
- “완료가 없는 같은 Writer 화면을 다시 그려도 최초 방문 기록은 한 번만 저장한다.” — 반복 렌더링으로 읽음 저장을 반복하지 않는다.

추가 변경: `src/lib/stage-seen.ts`, `tests/job/completion-first-visit.test.ts`.
