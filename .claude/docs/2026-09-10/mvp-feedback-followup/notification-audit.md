# MVP 19·20 알림 재점검 및 기존 실패 2건

2026-09-10 KST · notification_audit · `dev` 공유 작업 폴더 기준

**완료 알림을 전부 끈 것이 아니다. 왼쪽 숫자는 저장까지 성공한 새 결과 수를 표시한다. 다만 재점검에서 읽음 처리와 프로젝트 전환의 실제 결함 두 가지를 발견하여 수정했다. 채팅의 완료 문장은 별도 경로이므로 “러프·프리비즈가 끝나면 어디에서나 반드시 채팅 알림도 나온다”는 상태는 아니다.**

## 사용자가 보는 동작

| 상황 | 현재 동작 |
|---|---|
| Writer 러프 이미지 저장 완료 | 다른 단계를 보고 있으면 Writer에 미확인 완료 샷 수를 표시한다. 그리드 한 장이 4샷이면 4로 센다. |
| 프리비즈 영상 저장 완료 | 현재 종류 분류상 Director 완료 수로 센다. Writer에도 생성 버튼이 있으나 배지는 Director로 간다. 이 분류는 이번 수정에서 바꾸지 않았다. |
| 생성 중 / 실패 | 성공 완료 숫자에 더하지 않는다. 진행 표시·실패 표시는 별도다. |
| 같은 작업 완료를 다시 수신 | 같은 작업 ID를 중복 집계하지 않는다. 별도 작업 ID로 실제 재생성한 결과는 각각의 완료다. |
| 지금 해당 단계를 보고 있음 | 해당 단계 숫자는 숨긴다. 이번에는 보는 동안 수신한 완료까지 읽음으로 남겨, 떠난 직후 다시 숫자가 나타나는 결함도 고쳤다. |
| 다른 단계로 떠난 뒤 새로 완료 | 새 완료만 미확인으로 표시한다. |
| 프로젝트 전환 중 이전 응답 도착 | 이번 수정으로 폐기한다. 새 프로젝트에 이전 완료·진행·사용량 사본을 보여주지 않는다. |
| 브라우저 재접속 | 프로젝트별 마지막 확인 시각과 서버 최근 완료를 다시 대조한다. 단, 최근 24시간에 접수한 최대 500개 작업 범위다. 무제한 알림함은 아니다. |

서버 상태 확인 간격은 진행 중 4초, 쉬는 동안 15초다. 네트워크 및 서버 처리 시간이 추가되므로 즉시 전송되는 알림은 아니다. 처음 한 번도 방문하지 않은 단계는 과거 완료를 쌓아 보이지 않도록 숫자가 0이다. 읽음 기록은 같은 브라우저의 프로젝트별 저장소에 남으며, 계정의 여러 기기·브라우저 간 읽음 동기화는 구현되어 있지 않다.

실제 완료 판정 순서는 결과 파일 보관 → 샷의 러프/영상 저장 → 생성 작업 성공 완료다. 이미지·영상이 접수되었다는 이유만으로 성공 완료 숫자를 올리지는 않는다. 화면이 파일을 실제로 재생·표시했는지까지 검사한 숫자는 아니다.

## 이번에 재현하고 고친 결함

1. Writer 진입을 1초 시점에 기록한 뒤 2초 시점에 러프 4샷이 끝나면, Writer에서는 숫자를 숨겼지만 Artist로 옮기는 순간 `4`가 다시 나타났다. 실제로 받은 마지막 완료 시각까지 읽음으로 저장하여 고쳤다. 그 뒤 3초 시점에 새로 끝난 1샷은 계속 `1`로 표시한다.
2. A 프로젝트의 요청을 기다리는 중 B 프로젝트로 바꾸면, A의 늦은 완료 응답이 B의 공유 알림 사본을 덮어썼다. 새 프로젝트의 첫 요청도 이전 요청의 진행 표시 때문에 막힐 수 있었다. 프로젝트를 바꾸면 이전 요청을 취소하고, 취소가 늦게 적용돼도 이전 응답과 후속 예약을 버리도록 고쳤다. 첫 화면부터 프로젝트가 맞는 사본만 읽는다.

보는 동안 완료를 읽음으로 남기는 처리는 같은 완료를 반복 저장하지 않는다. 새 알림이 없는 재렌더에서 읽음 기록 변경과 재렌더가 계속 도는 상황도 회귀로 확인했다.

## 채팅 문장과 숫자는 구분해야 한다

- 왼쪽 숫자는 서버의 성공 완료 기록을 공통으로 읽는다.
- 일반 채팅 완료줄은 Artist와 Director의 개별 생성 실행이 완료를 관찰했을 때 호출한다. 이미 그 단계를 보고 있으면 일반 완료줄은 생략한다. 사용자가 시작한 일괄 생성의 결과 요약은 별도다.
- Writer 러프가 전부 준비됐다는 제안은 러프 화면이 열려 있고 모든 샷의 러프가 완료되었을 때 생긴다. 해당 화면이 닫혀 있는 동안 완료된 사건을 채팅으로 통지하는 공통 경로는 없다.
- Writer 프리비즈 생성 경로는 저장된 영상 상태를 다시 읽지만 일반 채팅 완료 통지를 호출하지 않는다.
- 브라우저를 닫은 동안의 완료 기록을 돌아와서 채팅 문장으로 빠짐없이 다시 만드는 기능은 없다. 이번 수정 범위는 두 숫자 싱크 결함이며 이 기능을 완료했다고 보고해서는 안 된다.

## “기존 실패 2개”의 정확한 뜻

**원래부터 실패하던 테스트 두 개라는 뜻은 아니다. 기존에 있던 테스트가 이번 MVP 수정으로 함수에 진행 추적용 정보를 더하면서 실패한 것이다. 사용자 약속이 바뀌었다는 증거도 아니다.**

| 기존 테스트의 한국어 약속 | 실제 실패 이유 |
|---|---|
| “채팅에서 새 모습을 만들어 달라고 하면 승인 뒤 그 캐릭터에 그 모습이 추가된다” | 옛 호출 문장이 정확히 한 줄로 남아 있어야 한다는 검사. 새 모습 생성에 추적 정보, 작업 상태 통지, 모습 생성 직후 저장 콜백을 추가해 문장이 달라졌다. |
| “채팅에서 배경의 새 모습을 만들어 달라고 하면 승인 뒤 추가되고, 특정 모습만 다시 그릴 수 있다” | 배경 새 모습 생성에도 같은 정보와 콜백을 추가하여 옛 호출 문장 검사와 달라졌다. |

추가 정보는 생성 진행·실패를 실제 결과로 알려주고, 새 모습 행은 이미 만들어졌는데 이미지 접수가 불분명할 때 같은 모습을 또 만들지 않기 위한 것이다. 인물·배경 요청을 승인 전에는 실행하지 않고 승인 뒤 해당 대상에 실행하는 실제 행동 회귀는 통과했다. 두 기존 테스트의 약속 문장·기대식·실행 여부는 변경하지 않았다.

## 검증

- 신규 읽음·프로젝트 전환 회귀: 수정 전 **5개 실패**, 수정 후 **5개 통과**.

- 숫자·승인 실제 행동 관련 묶음: **41개 통과, 0개 실패**.
- 타입 검사 통과. 이번 소유 코드와 신규 테스트의 ESLint 오류·경고 0.
- 회귀는 실제 읽음·공유 구독 모듈을 실행한다. React의 구독 등록과 화면 반영 시점, 서버 응답은 제어했다. 실제 브라우저 라우팅·다중 브라우저·유료 생성 검증으로 간주하지 않는다.
- 외부 프로젝트 데이터, 실제 생성 작업, 운영 환경은 수정하지 않았다. `main` 반영도 이 조사·수정에서 수행하지 않았다.

## 한국어 약속과 필요한 이유

- “보고 있는 단계에서 완료된 결과는 다른 단계로 떠난 뒤에도 미확인으로 다시 표시하지 않는다.” — 왜: 방금 본 결과가 다시 새 알림인 것처럼 나타나는 상황을 막는다.
- “다른 단계로 떠난 뒤 새로 완료된 결과는 미확인으로 표시한다.” — 왜: 기존 알림을 정리하면서 실제 새 결과까지 지우지 않는다.
- “같은 완료를 다시 받아도 확인 시각을 반복 저장하거나 다른 단계의 알림을 지우지 않는다.” — 왜: 반복 확인으로 알림이 흔들리거나 화면 갱신이 반복되지 않는다.
- “프로젝트를 바꾼 뒤 이전 프로젝트의 늦은 응답은 현재 알림에 섞이지 않는다.” — 왜: 이전 작품의 생성 수가 새 작품에 나타나는 것을 막는다.
- “화면 구독이 잠시 겹쳐도 새 프로젝트 완료 확인을 즉시 시작한다.” — 왜: 화면 전환 순서 때문에 새 작품의 상태 확인이 멈추지 않는다.
