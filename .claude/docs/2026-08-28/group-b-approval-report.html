그룹 B · 채팅 → 실행 연결 · 2026-08-27 ~ 08-28

채팅으로 시킨 생성이 이제 승인 카드를 거쳐 끝까지 갑니다 — 실제 화면에서 한 번 완주했습니다

"알겠다"고 답하고 아무것도 안 하던 채팅을 고치는 작업입니다. 사라졌던 완성본을 빌드 캐시에서 복구했고, 실제 화면에서 재생성 요청 → 승인 카드 → 승인 → 진짜 이미지 생성 → 완료를 한 번 완주했으며, 당신이 정한 규칙 세 개를 코드에 박았습니다. 전부 원격 main에 올라가 있습니다.

결론 먼저 — Artist 화면은 실측까지 끝났고, Director 이미지·Writer 첫 실행은 코드는 막았으나 화면 실측이 남았습니다. 이미지 생성 실비는 1건 썼습니다.

1

무엇이 고장나 있었나

화개장터 프로젝트의 실제 채팅 기록이 증거입니다. 사용자가 같은 요청을 여섯 번 반복하는 동안 채팅은 매번 "할게요"라고만 답했습니다.

적용하라고 → "vertical 무빙만 적용하고 넘길게요" → dd → "적용할게요" → ㅇㅇ → "적용할게요" → 제발 적용해줘 → "알겠어요! 적용할게요" — 그리고 실행 없음.

원인은 세 갈래였습니다. 채팅이 실제 생성 도구를 못 부르거나, 부를 수 있는데 안 부르거나, 불렀는데 그 결과가 화면과 연결되지 않는 것. 이 연결을 만들되, 돈이 나가는 생성은 반드시 당신 승인을 거치게 하는 것이 이번 작업의 전부입니다.

2

사라졌던 완성본부터 되찾았다

작업을 시작하려고 보니, 전날 다른 세션이 만들어둔 완성본이 폴더에서 사라져 있었습니다.

사고 경위

작업 유실

여러 세션이 같은 폴더를 공유하는 상태에서, 한 세션이 git reset --hard로 폴더를 원격 기준으로 되돌렸습니다. 커밋하지 않고 파일로만 있던 완성본 수십 개가 그 순간 지워졌습니다.

복구 방법

복구 성공

지워진 파일들의 원문이 빌드 캐시 안에 통째로 남아 있었습니다. 개발 서버가 화면을 만들 때 쓰는 중간 산출물(소스맵)에 원본 코드가 들어 있어서, 거기서 17개 파일을 꺼냈습니다.

덮어쓰지 않고 3-way merge(공통 조상·현재 파일·복구본 세 버전을 대조해 합치는 git 표준 방식)로 합쳤습니다. 그 사이 다른 개발 세션이 같은 파일에 넣어둔 수정 — 대사 언어 처리, 첫 진입 노드 처리 — 이 지워지면 안 되기 때문입니다. 합친 뒤 두 세션의 변경이 나란히 살아 있는 것을 파일마다 확인했고, 충돌은 0건이었습니다.

검증: 타입 검사 통과, 자동 시험 1,537건 통과. 복구본을 커밋해 원격에 올렸으므로 같은 사고로 다시 사라질 수 없습니다.

커밋 27ebaf3 · 재발 방지: 세션마다 폴더 분리(git worktree) + 자주 커밋 + reset --hard 금지

3

배선이 진짜 데이터베이스에서 작동하는지 먼저 확인했다

화면을 열기 전에, 상태가 규칙대로 넘어가는지를 운영 데이터베이스에서 직접 확인했습니다. 이미지 생성 없이 기록만 넣었다 지우는 방식이라 비용은 0입니다.

구조는 이렇습니다. 채팅 한 턴마다 영수증(기록 한 줄)이 남고, 승인 후 생성 작업이 그 영수증에 연결되며, 작업 결과에 따라 영수증 상태가 바뀝니다.

시나리오기대한 상태 흐름실측
정상 경로승인 대기 → (승인) → 생성 대기 → 완료그대로 나옴
일부만 성공 (완료 1 + 실패 1)"일부 성공"으로 집계그대로 나옴
전부 실패"실패"로 집계그대로 나옴

확인용으로 넣은 기록은 확인 즉시 지워 운영 데이터에 잔여물 0건입니다. 이 확인에 필요한 테이블 추가(스키마 변경)도 운영 데이터베이스에 이때 적용했습니다 — 미적용 변경 11개를 한꺼번에 밀지 않고 이번 것 하나만 골라서.

테이블: chat_traces, generation_jobs.chat_trace_id · 적용: supabase migration 20260827120000

4

실제 화면에서 완주 — 요청부터 완료까지

고장 사례가 실제로 났던 화개장터 프로젝트, 실제로 무반응이었던 그 요청으로 시험했습니다. 유일하게 실비가 나간 단계입니다(이미지 생성 1건).

Artist 채팅에 "체장수 캐릭터 이미지를 다시 생성해줘"를 입력했습니다. 예전엔 여기서 "그러겠다"고 답하고 끝이었습니다. 이번엔 승인 카드가 떴습니다:

Artist: 체장수 4뷰 전체 재생성할게요.

[제안] 캐릭터 뷰 재생성: main, back, sideLeft, sideRight
· 이미지 생성 비용이 발생합니다.
· 기존 선택 이미지는 새 생성이 끝날 때까지 유지됩니다.
· 승인 전에는 재생성이 시작되지 않습니다.
[승인] [나중에]

승인을 누르자 캐릭터 카드가 "생성 중"으로 바뀌고 진행 표시줄이 떴습니다. 그리고 데이터베이스에 이렇게 찍혔습니다:

시점영수증 상태생성 작업
승인 직후생성 대기(queued) · 승인 대기 해제작업 생성됨 · 영수증에 연결됨
약 2분 뒤조회 시 "완료"로 집계완료 · 결과 이미지 주소 있음

이 문서에서 가장 중요한 한 줄

채팅 요청 → 승인 카드 → 승인 → 실제 이미지 생성 서비스(fal)가 돌아 결과물이 나옴 → 영수증이 "완료"로 집계 — 이 사슬 전체가 운영 환경에서 한 번에 이어졌습니다. "알겠다"고만 하던 무반응이 이 화면에서는 끝났습니다.

실측 원본 기록 (코드값 그대로)
chat_traces:      70ab8a3d | artist | queued | pending=false
generation_jobs:  71238ba5 | character_view | completed | chat_trace_id=70ab8a3d | result_url 있음
getChatTrace(70ab8a3d) → generationStatus: 'completed', resultReady: true

영수증 테이블의 상태 칸은 queued로 남지만, 조회 함수가 연결된 작업들을 보고 최종 상태를 계산합니다(설계 의도대로 동작).

5

당신이 정한 규칙 세 개, 그리고 그 규칙으로 찾아낸 구멍 두 개

실측 후 남은 설계 논의를 물었고, 당신이 답을 정했습니다. 그 규칙을 잣대로 코드 전체를 감사하니 규칙 위반 경로가 두 개 나왔습니다.

확정된 규칙

  • "수정 얘기냐 생성 요청이냐"는 채팅이 추정하되 — 데이터만 고치는 수정(무료)은 즉시 적용하고, 이미지·영상을 만드는 생성(유료)은 반드시 확인 카드를 거친다. 추정이 틀려도 돈 나가기 전에 카드에서 멈춘다.
  • 생성은 무조건 물어본다. 화면 구분 없이 전부.
  • 예상 비용 수치는 카드에 표시하지 않는다.

감사 결과 — 승인 없이 돈이 나가던 경로 두 개

Director 채팅의 이미지 생성

승인 없이 즉시 실행되던 것막음

채팅이 이미지 생성 지시를 내리면 카드 없이 곧바로 생성이 시작됐습니다. Artist 화면은 카드를 거치는데 Director 화면만 예외였던 겁니다. 이제 같은 응답 안의 무료 수정은 즉시 반영하고, 이미지 생성(한 샷이든 일괄이든)만 카드 한 장으로 묶어 승인 뒤에 기존 생성 경로를 태웁니다.

채팅 모델의 지시문에도 규칙을 박았습니다: 수정 요청에 생성을 멋대로 덧붙이지 말 것, 사용자가 명시적으로 생성을 요청했을 때만 생성 지시를 낼 것. "수정 얘기했는데 영상부터 만들려 든다"던 그 증상의 재발 방지입니다.

Producer→Writer 첫 넘김

승인 없이 즉시 실행되던 것막음

"Writer로 넘겨줘"라고 하면 씬·샷 생성(유료, 오래 걸림)이 곧바로 시작됐습니다. 재실행은 동의를 받으면서 정작 첫 실행은 안 받고 있었습니다. 이제 첫 실행도 카드를 거칩니다. 비용 없는 화면 이동(Artist→Director 등)은 예전처럼 바로 넘어갑니다.

일부러 그대로 둔 것

의도된 예외

대사 삭제, 캐릭터 기본 외형 덮어쓰기는 무료지만 되돌리기 어려운 변경이라 확인 절차를 유지했습니다. "무료 수정은 즉시"의 예외이며, 비용 방어가 아니라 실수 방어입니다.

검증: 타입 검사 통과, 승인 경계 시험 18건 통과, 제품 전체 자동 시험 1,539건 통과. 이 과정에서 시험 코드 자체의 결함 두 개(검사 범위가 과했던 것, 연타 방어 장치가 시험 간에 남던 것)도 고쳤습니다.

확실한 것과 아직 모르는 것

이건 확실합니다

  • Artist 화면에서 요청→카드→승인→실제 생성→완료가 운영 환경에서 한 번 완주했다
  • 상태 흐름 세 갈래(완료·일부 성공·실패)가 운영 데이터베이스에서 규칙대로 돈다
  • 승인 없이 돈 나가던 두 경로가 코드에서 막혔고, 그 경계가 자동 시험으로 잠겼다
  • 사라졌던 완성본이 복구·커밋됐고 다른 세션 작업은 하나도 안 지워졌다

이건 아직 모릅니다

  • Director 이미지·Writer 첫 실행의 카드가 실제 화면에서 뜨고 완주하는지 — 코드와 시험으로만 확인했고 화면 실측은 한 번도 안 했다
  • 수정/생성 의도 추정이 실사용 문장에서 얼마나 자주 빗나가는지 — 빗나가도 카드에서 멈추는 구조지만, 빈도는 측정한 적 없다
  • 영상 생성은 채팅에서 여전히 "지원 안 함"으로 정직하게 거절만 한다 — 승인 카드로 실행까지 이어주는 건 만들지 않았다

결론

1. "알겠다"만 하던 무반응은 Artist 화면에서 끝났고, 실측으로 확인됐다.

고장 사례가 났던 바로 그 프로젝트에서 완주했습니다.

2. 채팅에서 돈 쓰는 일은 이제 전부 당신 승인 버튼 뒤에 있다.

Artist 재생성, Director 이미지, Writer 첫 씬·샷 생성 — 코드가 강제하고 시험이 잠급니다.

3. 다음에 확인할 것은 하나다.

화개장터를 열고 Director 채팅에 "이 샷 이미지 생성해줘"를 한 번 던져보면, 새로 막은 두 경로 중 하나가 화면에서 검증됩니다. Writer 첫 실행은 새 프로젝트를 하나 만들어야 시험할 수 있습니다.

4. 폴더 공유 사고의 재발 방지는 습관 문제로 남는다.

세션마다 폴더 분리, 자주 커밋, reset --hard 금지. 이번 복구는 빌드 캐시가 우연히 남아 있어 가능했던 것이고, 다음에도 남아 있으리란 보장은 없습니다.

이 문서가 근거로 쓴 것 — 화개장터 프로젝트의 실제 채팅 기록과 승인 카드 화면(2026-08-27 실측), 운영 데이터베이스의 영수증·생성 작업 기록 원문, 자동 시험 결과(1,537건/1,539건 통과), 원격 main 커밋 27ebaf3 · 0c45689 · 2142d47. 인용한 채팅과 데이터 행은 기록에 있는 그대로입니다.

이 문서가 하지 않는 것 — Director 이미지와 Writer 첫 실행의 화면 실측 결과는 여기 없습니다(아직 안 했습니다). 생성된 체장수 이미지가 좋은지는 판정하지 않습니다 — 그건 화면에서 당신이 봅니다. 의도 추정의 정확도 측정도 하지 않았습니다.
