P12 일일 대사 — 놓친 결제를 다음 날 아침에 안다

유저는 돈을 냈는데 우리 장부에 아무 기록이 없는 경우. 지금은 아무도 모른다.

먼저 알아둘 것

대사(對査) = 두 장부를 나란히 놓고 어긋난 줄을 찾는 것. 여기서는 Paddle 이 가진 결제 목록과 우리 장부(billing_events)를 맞춰 본다. 회계에서 은행 거래내역과 회사 장부를 맞추는 그 작업과 같은 말이다.

장면

유저가 $29 를 결제한다. Paddle 이 우리 서버에 알림을 건다. 그런데 그 순간 우리가 배포 중이라 서버가 안 뜬다. Paddle 이 재시도한다 — 샌드박스 3회/15분, 라이브 60회/3일. 그 안에 우리가 못 살아나면 Paddle 은 포기한다.

유저 화면: 결제 성공. 카드에서 $29 빠짐. Take 0 개. 우리 화면: 아무 일도 없었다. 유저가 문의를 넣기 전까지 우리는 모른다.

지금

웹훅은 받은 알림을 전부 저장한다. 안 온 알림은 저장할 것이 없다 — 그래서 "안 온 것"은 장부 어디에도 흔적이 없다.

src/lib/billing/paddle-webhook.ts:169const recorded = await deps.recordEvent({ id: event.event_id, type: event.event_type, payload: event })
← 이 줄은 알림이 도착했을 때만 실행된다. 안 온 알림은 이 코드를 지나가지 않는다.

고치는 법

하루 한 번 Paddle 에 "어제 완료된 결제 목록"을 물어보고 우리 장부와 대조한다. Paddle API 가 날짜로 거르는 걸 지원한다(billed_at[GTE], status=completed).

어긋난 모양뜻우리가 하는 것
Paddle 에 있는데 우리 장부에 없다알림 유실. 이 잡의 존재 이유디스코드로 결제 번호. 관리자가 Paddle 대시보드에서 재전송하거나 손으로 적립
우리 장부에 있는데 Paddle 에 없다있을 수 없는 일 — 위조나 버그 신호디스코드 경보
전부 맞다정상아무것도 안 한다. 매일 "OK" 가 오면 진짜 경보를 안 읽게 된다

어제 하루치만 본다. 매일 전체를 훑으면 Paddle 호출이 늘고 같은 경보가 매일 반복된다. 자동으로 다시 처리하는 것(빠진 알림을 우리가 직접 만들어 넣기)은 첫 버전에 안 넣는다 — 잘못 만들면 없는 결제로 Take 를 주게 된다. 경보까지만.

재사용Cron 자리는 오늘 만든 만료 잡과 같다(vercel.json + CRON_SECRET). 새 부품 없음.

P10 스모크 자동화 — 어제 내가 손으로 한 것을 기계가 한다

부품은 다 맞는데 이음새에서 깨지는 것을 잡는다.

먼저 알아둘 것

스모크 = 켜자마자 연기가 나는지 보는 검사. 이 저장소에는 이미 있다(pnpm smoke) — 브라우저를 열어 화면이 뜨는지, 콘솔 에러가 있는지, 스크린샷을 남긴다. 판정은 하지 않는다(오너 몫). 여기에 결제 한 바퀴를 추가하는 일이다.

단위 테스트(2,112개)와 다른 점: 단위 테스트는 부품 하나를 흉내 DB 로 본다. 스모크는 진짜 브라우저 · 진짜 Paddle · 진짜 DB 를 관통한다. 어제 이 관통을 사람 손으로 한 번 했고(결제창 → 카드 4242 → 웹훅 → 적립 50 → 토스트), 그게 P7 을 끝냈다.

장면

라이브 키로 바꾼 직후. 상품 ID 가 라이브 것으로 갈렸고 웹훅 주소도 바뀌었다. 하나라도 어긋나면 첫 유저 결제가 그대로 사고다. 사람이 그때 한 번 더 카드를 꺼내 눌러야 하나? 그걸 기계가 하게 만든다.

지금

있는 것없는 것
pnpm smoke — 로그인·화면 열기·클릭·스크린샷·콘솔 에러 수집Paddle 결제창(iframe) 안에 카드번호를 넣는 부분
어제 실물 1회 통과 기록(수동)적립·차감을 확인하고 흔적을 지우는 부분

결제창은 iframe(우리 페이지 위에 뜨는 Paddle 의 별도 화면)이라 바깥에서 요소를 못 잡는다. 어제는 브라우저 도구로 iframe 안 요소를 직접 짚어 넣었다 — 그 방법이 되는 것은 실측으로 확인했다.

고치는 법

스모크 계정으로 dev 에서 한 바퀴를 돌린다. Mini 팩 결제 → 웹훅 → 적립 50 → 영상 생성 1회 → 차감 확인 → 흔적 정리. 어느 단계에서 멈추면 그 화면 스크린샷과 그때의 장부 상태를 남긴다.

스모크 계정은 구독 상태로 둔다. 무료 플랜이면 "무료는 팩 1회" 규칙에 두 번째 실행이 막혀 반복이 안 된다(그 규칙 자체는 정상 동작이다).

이 검사가 잡는 것

깨지는 자리단위 테스트가 잡나스모크가 잡나
상품 ID 가 env 에 안 들어감✗○
웹훅 주소·시크릿이 어긋남✗○
결제창이 안 열림(도메인 승인 등)✗○
적립은 됐는데 생성이 그 잔액을 못 봄✗○

P15 플랜 변경 — 유저가 스스로 올리고 내린다

정책은 09-07 에 확정됐다. 남은 것은 화면과 Paddle 호출.

지금

구독 중인 유저가 /pricing 에서 다른 플랜을 누르면 "이미 구독 중이에요. 플랜 변경은 곧 열려요" 토스트가 뜨고 끝난다(P7 에서 그렇게 막아 뒀다 — 안 막으면 구독이 두 개가 된다). 플랜을 바꾸려면 지금은 관리자가 Paddle 대시보드에서 손으로 해야 한다.

확정된 정책 (09-07)

돈갱신일Take
상위로그날 새 플랜 한 달치 전액. 옛 플랜 안 쓴 날짜는 안 깎는다오늘로 리셋남은 것 그대로 + 새 플랜 전액. 얹은 것도 새 갱신일에 같이 사라진다
하위로지금 결제 없음그대로다음 갱신일부터 새 플랜 기준

예: S-5(잔여 40) → S-10 을 9월 15일에. 오늘 $110, 갱신일 10월 15일, 잔액 40 + 100 = 140.

열려 있던 질문 — 문서에는 답이 있다

"Paddle 에 전액 즉시 청구와 갱신일 리셋을 한 요청으로 보낼 수 있나" 가 P15 의 유일한 미지였다. API 문서를 확인했다.

Paddle API 문서 — 구독 수정(PATCH /subscriptions/{id}), 2026-09-08 확인next_billed_at            : "Include to change the next billing date."
proration_billing_mode    : "Required when making changes to items or the next billing date."
  full_immediately        : "Paddle does not calculate proration, creating a transaction
                             to collect for the full amount immediately."

문서상 된다같은 요청에 items(새 플랜) + next_billed_at(오늘+1개월) + proration_billing_mode: full_immediately 를 함께 보낸다. 실측은 아직이다 — 샌드박스에서 한 번 돌려 봐야 확정이다.

안 되면 대안은 "옛 구독 즉시 취소 + 새 구독 시작"인데, 결제창이 한 번 더 뜨는 흐름이라 오너가 09-07 에 피하자고 한 "새로 결제하는 것처럼"이 된다. 그래서 위 방법을 먼저 실측한다.

화면

결제창은 안 뜬다. 저장된 카드로 서버가 바로 청구한다. 대신 확인창 하나가 뜬다 — 오늘 낼 금액 · 새 갱신일 · 바뀔 Take. 하위 플랜이면 "N월 N일부터 S-5 로 바뀝니다".

결정이 필요한 것

질문안 정하면선택지추천
대사 결과를 매주 요약해서 보낼까 디스코드에 아무것도 안 오는 날, 그게 "정상"인지 "잡이 죽었는지" 구분이 안 된다 안 보낸다 / 주 1회 "이번 주 결제 N건, 불일치 0" 안 보낸다. 잡이 죽는 것은 잡 자체의 실패 경보가 잡는다. 조용함 = 정상을 지킨다
스모크가 영상까지 만들까 "결제 → 적립" 까지만 보고 "적립 → 생성 → 차감" 이음새는 안 본다 결제까지만(fal 비용 $0) / 영상 1개까지(1회당 원가 $0.31) 영상까지. 그 이음새가 깨지면 "결제했는데 못 만든다" 가 되고, 그건 환불 문의다. 하루 1회면 월 $9.3
스모크를 얼마나 자주 언제 도는지 안 정해지면 안 돌게 된다 배포마다(하루 5회면 월 $46) / 하루 1회(월 $9.3) / 손으로만($0) 하루 1회 + 라이브 키 전환 직후 손으로 1회. 결제 코드는 매일 안 바뀌니 배포마다는 과하다

P15 의 확인창에 무엇을 보일지는 화면이 나온 뒤 스크린샷으로 판정한다 — 지금 문장으로 물으면 답하기 어렵다.

알고만 있으면 되는 것

사실뜻
P12 는 빠진 알림을 자동으로 처리하지 않는다첫 버전은 경보까지. 잘못 만들면 없는 결제로 Take 를 준다. 재처리는 Paddle 대시보드에서 재전송을 누르거나 관리자 적립
P10 은 샌드박스 카드만 쓴다실 카드 자동화는 스모크 헌법상 금지. 라이브 전환 뒤의 확인은 사람이 한 번
P15 의 Paddle 호출은 문서 기준이다한 요청에 되는 것은 문서로 확인했고 실측은 안 했다. 안 되면 "옛 구독 취소 + 새 구독" 으로 바뀌고 크기가 늘어난다
스모크 계정이 구독 상태여야 한다P10 을 만들기 전에 스모크 계정으로 dev 에서 구독을 하나 걸어 둔다(어제 오너가 S-1 을 이미 걸었다 — 그대로 쓰면 된다)
