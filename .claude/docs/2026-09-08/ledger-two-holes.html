구멍 1 — 같은 결제로 Take 가 두 번 들어간다

언제 일어나는가, 왜 지금 코드로는 못 막는가.

먼저 알아둘 것 하나

Paddle 이 알림을 보낸다 = Paddle 이 우리 서버에 요청을 건다. 우리는 5초 안에 "받았다" 고 답해야 한다. 답이 없으면 Paddle 은 실패로 보고 같은 알림을 다시 보낸다. 이 문장을 빼먹으면 아래 장면이 안 읽힌다.

장면

유저가 Mini 팩 $29 를 산다. Paddle 이 "결제됐다" 요청을 우리 서버에 건다(요청 A). 우리 서버가 일을 시작하는데 배포 직후라 5초가 넘게 걸린다. 우리는 죽은 게 아니라 계속 일하고 있다. Paddle 은 답이 없으니 같은 알림을 다시 건다(요청 B). 이제 A 와 B 가 같이 돈다. Vercel 은 요청마다 다른 서버 인스턴스에 태우니 A 와 B 는 서로를 모른다.

둘 다 "이 결제로 이미 Take 넣었나?" 를 장부에 물어본다. 둘 다 아직 안 넣었으니 둘 다 "없다" 를 받는다. 둘 다 넣는다. $29 를 받고 100 개를 준다.

가장 헷갈리는 것 — 재전송은 같은 결제다

요청이 둘이라고 해서 결제가 둘인 게 아니다. Paddle 이 답을 못 받아 같은 알림을 다시 보낸 것이라 내용이 전부 같다.

요청 A요청 B
알림 번호evt_01abc…evt_01abc… 같음
결제 번호txn_01xyz…txn_01xyz… 같음
금액$29$29
유저가 낸 돈$29 한 번뿐. 결제는 한 번이다

결제 번호가 서로 다르면 그건 다른 결제이고 각각 50 개씩 주는 게 맞다. 막아야 하는 건 "같은 번호로 두 줄" 뿐이다.

"조회와 삽입 사이가 원자적이지 않다"

원자적이 아니다 = 두 동작 사이에 다른 요청이 끼어들 수 있다. 시각 순으로 늘어놓으면 이렇다.

시각요청 A요청 B장부
0ms묻는다 → "없다"0
5ms묻는다 → "없다"0
20ms넣는다50
25ms넣는다100

B 가 5ms 에 물었을 때 A 는 아직 안 넣었다. 그래서 B 도 "없다" 를 받는다. 멱등성 문제가 맞다 — 우리는 멱등성(같은 알림을 몇 번 처리해도 결과가 한 번과 같음)을 원하고 있고, 지금 방법이 순차로 오면 지키고 동시에 오면 못 지킨다. "멱등성이 없다" 가 아니라 "멱등성을 보장하는 수단이 약하다".

왜 DB 로 고치나 — Paddle 이 해주지 않나

책임이 3층으로 나뉜다.

층하는 일누구 몫
Paddle알림마다 고유 번호를 붙인다(재전송이면 같은 번호). 5초 안에 답이 없으면 다시 보낸다Paddle
우리 서버번호를 보고 "이미 했나" 판단한다. 서버가 여러 대고 서로를 모른다우리 (지금 여기만 쓴다)
DB하나뿐이라 "이건 한 줄만" 을 강제할 수 있다우리 (안 쓰고 있다)

Paddle 은 우리가 그 알림으로 무엇을 하는지 모른다. 우리 장부는 우리 DB 에 있다. Paddle 문서도 "이미 처리한 웹훅인지 event id 로 확인하는 것이 best practice" 라고 적어 뒀다 — 우리 몫이다. DB 로 고치는 건 관행이 아니라 구조다. 서버는 여러 대라 서로 모르고 DB 는 하나다. "동시에 온 둘 중 하나만" 을 판정할 수 있는 자리가 DB 뿐이다.

그렇다고 서버 조회가 의미 없는 건 아니다. 두 가지를 갈라야 한다 — 중복이 오는 원인은 Paddle 재전송이고, 중복을 못 거르는 원인이 서버가 여럿이라는 것이다. 재전송의 대부분은 5초 뒤에 와서 그때 첫 처리가 이미 끝나 있다. 그러면 조회가 잡고 정상 경로로 끝난다(어제 실물 테스트가 그랬다). 조회 = 흔한 경우를 빠르게 거르는 1차 필터, DB 제약 = 드문 경우의 최후 방어. 둘 다 두는 게 표준이다.

멱등성을 보장하는 방법들 — 무엇이 "안전하다" 인가

방법판정자강도우리
조회 후 삽입각 서버 (여럿)약함 — 동시에 오면 깨진다지금 이것만
DB 유일 제약DB (하나)강함 — DB 가 두 번째를 거부가려는 곳

큐로 한 줄 세우기큐 (하나)강함. 부품 추가 + 지연안 씀

"안전하다" 의 기준 셋. ① 판정자가 하나인가 ② 그 판정자가 이미 쓰는 부품인가(새 실패 지점을 안 늘림) ③ 실패해도 안전한 쪽으로 실패하는가(제약 위반 = 삽입 안 됨 = 이중 적립 없음). DB 유일 제약이 셋 다 만족한다. Redis 잠금은 ②에서 걸린다.

고치는 법

장부 테이블에 "(결제 번호, 적립 종류) 조합은 한 줄만" 이라는 제약을 건다. 두 번째 삽입은 DB 가 거부하고, 웹훅은 그 거부를 "이미 적립됨" 으로 읽고 성공으로 답한다.

  • 요청을 안 받는 게 아니다. A 도 B 도 받는다. 받아서 결과가 하나가 되게 한다 — 첫 번째는 넣고 두 번째는 "이미 있네" 하고 답만 한다.
  • 결제 번호만으로 걸지 않는 이유: 나중에 환불이 오면 같은 결제 번호에 회수 행(refund_revoke)이 하나 더 붙어야 한다. 번호만으로 걸면 그게 막힌다. 그래서 종류까지 묶는다.
  • 조회는 그대로 둔다. 위에서 말한 1차 필터다. 조회가 놓친 것만 DB 가 잡는다.

왜 아직 안 터졌나

재전송은 보통 5초 뒤에 오고 우리 처리는 0.5초에 끝난다(실측 499ms). 겹칠 창이 좁다. 어제 실물 테스트에서도 재전송이 duplicate 로 정상 처리됐다. 이 구멍은 느려질 때만 열린다 — 배포 순간, 콜드 스타트, DB 지연.

구멍 2 — 만료일이 지난 Take 가 사라지지 않는다

화면에는 "10월 7일 만료" 라고 쓰여 있는데, 10월 8일에도 그대로 있다.

장면

어제 오너가 dev 에서 S-1 을 구독했다. 장부에 이렇게 들어갔다.

dev 장부 실측 2026-09-08 09:00 KSTgrant_purchase   50 | 만료 2027-09-07 | txn_01m1xpbffccf03   ← Mini 팩
grant_plan       16 | 만료 2026-10-07 | txn_01m1xqgnmk2swk   ← S-1 한 달치
grant_purchase  200 | 만료 2027-09-07 | txn_01m1xqqrvb7h98   ← Standard 팩

가운데 줄이 문제다. 10월 7일이 지나면 저 16 개는 사라져야 한다(v4 "구독 포함분은 매월 말 소멸 — 원가 방어"). 그런데 사라지게 하는 코드가 없다. 10월 8일에도 잔액은 266 이고, 유저는 안 쓴 9월분으로 10월에 영상을 만든다. 우리는 9월치 원가를 10월에 한 번 더 낸다.

지금 코드

잔액은 장부 행의 단순 합이다. 만료일은 행에 적혀만 있고 합산에서 빠지지 않는다. 주석이 이미 "다음 슬라이스" 라고 적어 뒀다 — 그 다음 슬라이스가 이것이다.

src/lib/billing/take-ledger.ts:16-24/**
 * 워크스페이스의 현재 Take 잔액 — sum(delta).
 * 만기(expires_at < now)인 grant 의 잔여분을 제외하지 않는다 — 만기 정산은 expire 행이 처리하며
 * (다음 슬라이스), 이번 슬라이스는 원장 전체의 단순 합만 계산한다.
 */
export async function takeBalance(workspaceId: string): Promise<number> {
  const { data, error } = await supabaseAdmin
    .from('take_ledger').select('delta').eq('workspace_id', workspaceId)
  if (error) throw error
  return (data ?? []).reduce((sum, row) => sum + (row.delta as number), 0)
}

구멍합산을 바꿔 만료를 빼는 방법도 있지만 안 쓴다. 잔액이 "장부 행의 합" 이라는 규칙이 깨지고, 내역 화면에 "왜 줄었는지" 가 안 남는다. 대신 만료 행을 실제로 넣는 잡을 만든다.

고치는 법 — 어려운 건 "넣기" 가 아니라 "얼마를 넣을지"

먼저 용어 하나. lot = 한 번에 들어온 Take 묶음. 적립 행 하나가 lot 하나다. "9월 7일에 들어온 플랜 16 개" 가 lot 하나, "9월 3일에 산 팩 50 개" 가 또 하나. 유통기한이 다른 우유팩이라 묶음마다 만료일이 다르다. 잡(job) 은 시간마다 도는 프로그램이고 완전히 다른 것이다.

lot 마다 남은 양이 다르다. 장부는 이렇게 생겼다.

lot 하나가 살아온 이력 (예시)grant_plan     +16    9/7 적립, 10/7 만료      ← lot A
hold            -3    lot A 에서 잡아둠(영상 생성 시작)
hold_release    +3    생성 실패로 돌려줌
hold            -5    lot A 에서 잡아둠
lot A 의 남은 양 = 16 - 3 + 3 - 5 = 11

만료 행은 −11 이지 −16 이 아니다. 그래서 "만료일 지난 lot 을 찾아 → 그 lot 의 남은 양을 세어 → 그만큼 음수 행을 넣기" 3단계가 된다. 세는 동안 다른 요청이 그 lot 에서 또 빼가면 숫자가 틀어지니 DB 안에서 한 덩어리로 한다(구멍 1 과 같은 종류의 문제).

"소진됨" 표시를 두면 안 되나 — 그러려면 lot 마다 남은 양 컬럼을 두고 잡아둘 때마다 UPDATE 해야 한다. 그게 2026-09-01 실측에서 깨진 방식이다(동시 차감 오버슛 11). 그래서 장부를 더하기만 하는 구조로 만들었고, 대가로 "셀 수밖에 없다" 가 따라온다.

잡이 돌기 전까지는? — 읽을 때 빼면 새는 창이 0 이 된다

초판에서 "합산을 바꿔 만료를 빼는 방법도 있지만 안 쓴다" 고 적었다. 그게 틀렸다(2026-09-08 오너 지적). 둘 중 하나를 고르는 문제가 아니라 둘 다 하는 것이고, 그게 표준이다.

어디서무엇을왜
읽을 때잔액 표시 · 생성 게이트만료일 지난 lot 은 남은 양을 0 으로 친다잡이 아직 안 돌았어도 유저가 그 Take 를 못 쓴다. 새는 창 0 분
잡Cron만료 행을 실제로 넣는다내역에 "만료 −16" 이 남고, 죽은 lot 을 계속 세지 않게 정리된다. 새는 창을 막는 역할이 아니라 주기가 느슨해도 된다

코드 변경은 두 군데다. 잔액 계산 함수와, 잡아두기 RPC 의 lot 순회에 "만료 안 된 것만" 조건 한 줄(and (tl.expires_at is null or tl.expires_at > now())).

까다롭다고 적었던 것 셋 — 다시 보니 둘은 저절로 풀린다

걱정실제로는

둘을 묶는 이유

  • 둘 다 DB 를 고친다. 하나는 유일 제약, 하나는 만료 계산 함수. 마이그레이션을 한 번에 dev DB → live 로 옮긴다. 따로 하면 두 번 옮긴다.
  • 둘 다 첫 라이브 결제 전에 끝나야 한다. 결제가 시작된 뒤에 만료 규칙을 켜면 "어제까진 있었는데" 가 되고, 이중 적립은 터진 뒤에 고치면 이미 나간 Take 를 회수해야 한다.
  • 둘 다 화면이 없다. 검수 표면이 약속 문장뿐이라 한 번에 삼진하는 게 낫다.
  • 합쳐서 1.5일 예상. 마이그레이션 2개(제약 1 + 함수 1), Cron 1개, 약속 12문장.
