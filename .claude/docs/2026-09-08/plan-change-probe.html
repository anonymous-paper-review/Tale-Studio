샌드박스 실측 · 2026-09-08 · 결제 P15

플랜 변경 실측

"전액 즉시 청구 + 갱신일 오늘로" 를 한 요청으로는 못 한다. Paddle 이 명시적으로 거부한다. 두 요청으로 나누면 된다 — 둘 다 미리보기로 확인했다.

막힌 것 하나: API 키에 구독 쓰기 권한이 없다. 읽기·미리보기는 되는데 실제 변경이 403 이다. 오너가 Paddle 대시보드에서 열어줘야 P15 를 만들 수 있다.

Paddle 샌드박스 실측 2026-09-08 13:05 KST · 구독 sub_01m1xqhw…(스모크 계정 S-1) · 미리보기라 실제 청구는 없었다

1

문서로는 된다고 봤는데 실제로는 거부한다

09-08 오전 "남은 세 조각" 문서에서 문서를 근거로 "한 요청에 된다" 고 적었다. 틀렸다.

PATCH /subscriptions/{id}/preview — items + next_billed_at + full_immediately 를 함께{
  "error": {
    "type": "request_error",
    "code": "bad_request",
    "detail": "not possible to change items and billing date in the same request"
  }
}

정정문서에는 두 필드가 각각 설명돼 있고 "같이 못 쓴다" 는 말이 없었다. 실물만 안다. 이래서 실측이 필요했다.

2

나눠서 재보니 둘 다 된다

보낸 것결과주기 끝
S-1 → S-2, full_immediately즉시 청구 $30.00 · 크레딧 $010/07 그대로
S-1 → S-10, full_immediately즉시 청구 $110.00 · 크레딧 $010/07 그대로
S-1 → S-2, prorated_immediately(비교용)즉시 청구 $14.6410/07 그대로
갱신일만 30일 뒤로, do_not_bill청구 없음10/08 로 바뀜

우리 정책과 정확히 맞는 것은 full_immediately 다. 09-07 에 정한 "그날 새 플랜 한 달치 전액, 옛 플랜 안 쓴 날짜는 안 깎는다" 가 크레딧 $0 · 전액 청구로 그대로 나온다. prorated_immediately 는 남은 날짜를 깎아 $14.64 만 받는데, 그러면 Take 이월과 날짜 크레딧을 둘 다 주는 이중 보상이 된다(09-07 에 피하기로 한 그것).

3

그래서 P15 는 이렇게 만든다

순서요청일어나는 일
1PATCH /subscriptions/{id} — items + full_immediately새 플랜 한 달치 전액이 저장된 카드로 즉시 청구된다. 결제창 안 뜬다
2PATCH /subscriptions/{id} — next_billed_at + do_not_bill갱신일이 오늘+1개월로 리셋된다. 추가 청구 없음
3(웹훅이 알아서)1번 청구가 transaction.completed 로 돌아와 새 플랜 Take 가 적립된다 — 이미 있는 코드다

주의1번이 성공하고 2번이 실패하면 돈은 받았는데 갱신일이 안 밀린 상태가 된다. 유저는 한 달 뒤가 아니라 옛 갱신일에 또 청구된다. 2번 실패 시 디스코드 경보 + 관리자가 손으로 맞추는 자리가 필요하다. 약속 문장에 넣는다.

하위 플랜은 do_not_bill 로 다음 갱신일부터 적용한다(미리보기에서 청구 없음 확인). 이건 한 요청이면 된다.

4

막힌 것 — API 키 권한

PATCH /subscriptions/{id} — 실제 변경 시도{"error":{"type":"request_error","code":"forbidden",
  "detail":"not authorized to read|update subscription"}}
동작결과
구독 조회 GET200
미리보기 PATCH …/preview200
실제 변경 PATCH403

지금 키(pdl_sdbx_api…)는 읽기만 있다. 오너가 Paddle 대시보드 → Developer tools → Authentication 에서 그 키에 subscription write 권한을 켜주면 그 뒤는 자동이다. 켜지면 이 실측을 실제 변경으로 한 번 돌려 확인한 뒤 P15 구현에 들어간다.

덤같은 키로 취소 예약 철회도 막혔다. 어제 오너 스모크에서 이 구독에 취소가 예약된 채로 남아 있다(10/07 발효). 권한이 열리면 같이 지운다 — 안 지우면 10월 7일에 스모크 계정 구독이 사라진다.

5

덤으로 잡은 사고

이 실측을 하려고 구독 상태를 보다가 스모크 계정 구독 행이 우리 DB 에서 사라진 것을 발견했다. Paddle 에는 살아 있는데 우리 쪽만 없는 상태였다.

범인은 오늘 만든 돈 드는 검사다. 구독 행은 워크스페이스당 하나라(onConflict: workspace_id) 스모크의 가짜 구독이 진짜 행을 덮어쓰고, 정리 단계에서 가짜 ID 로 지우니 덮어쓰인 진짜 행이 함께 사라졌다.

고침시작 전에 구독 행을 통째로 떠 두고 끝나면 그대로 되돌린다. 마지막 검사 문장도 "원래 구독이 그대로 돌아온다" 로 고쳤다. 커밋 7c6ba1f. DB 행은 Paddle 실제 값으로 복구했다.

근거로 쓴 것 — Paddle 샌드박스 API 실측 2026-09-08 12:55~13:10 KST. 전부 /preview 라 실제 청구·변경은 일어나지 않았다. 구독 sub_01m1xqhwxsvx5gtvwxqmnnstvd(스모크 계정, S-1, 주기 09/07~10/07). 가격 ID 는 .env.local 의 샌드박스 값. 정책은 paddle-scenarios.md 장면 6(09-07 오너 확정).

이 문서가 하지 않는 것 — 실제 플랜 변경을 한 번도 실행하지 않았다(키 권한 없음). 그래서 "두 요청으로 나누면 된다" 는 미리보기 기준이고, 실제로 돌렸을 때 웹훅이 어떤 순서로 오는지·Take 이월이 정확히 맞는지는 아직 모른다. P15 화면과 확인창도 만들지 않았다.
