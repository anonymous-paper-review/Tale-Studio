# 글로벌 채팅·요청 보존 작업 보고

**여러 대상을 요청해도 첫 대상만 남던 결함을 고쳤습니다. 승인 전에는 실행하지 않고, 각 대상의 실제 생성 결과를 기록합니다. ‘나중에’는 프로젝트별 보류 목록으로 남기며, 다른 단계에서도 승인 카드를 볼 수 있습니다. 안내 본문은 대화에 한 번만 기록됩니다.**

실제 채팅 요청부터 승인 소비까지 실행하는 신규 회귀 21개와 기존 핵심 회귀를 합쳐 **45개 통과**했습니다. 관련 전체 609개에서는 **606개 통과·2개 실패·1개 기존 제외**입니다. 남은 2개는 아래에 명시한 기존 소스 문자열 검사입니다. 화면 증거는 리더가 같은 변경으로 수집합니다. 유료 생성·운영 배포·외부 메시지 발송은 수행하지 않았습니다.

## 지킨 약속과 이유

- “여러 인물의 새 모습을 요청하면 승인 목록에 요청한 모든 인물과 모습이 표시된다” — 왜: 두 번째 인물이 앱의 첫 항목 선택 때문에 사라지는 고장을 재현한다.
- “일부 작업이 끝나고 일부가 남으면 완료한 작업을 유지하면서 남은 대상만 이어서 처리한다” — 왜: 부분 성공 뒤 재승인에서 완료한 인물을 중복 생성하지 않아야 한다.
- “다른 유료 제안이 떠 있어도 새 요청의 모든 대상을 보류 목록에 남긴다” — 왜: 이미 떠 있는 카드 때문에 새 요청이 소실되는 고장을 막는다.
- “요청한 항목은 완료·진행 중·시작 실패·미처리 중 어느 상태인지 이름과 함께 알려준다” — 왜: 둘째 제출 실패를 사용자가 결과 수를 세기 전에 확인해야 한다.
- “나중에를 누른 작업은 접어둔 목록에 남고, 다시 펼치면 이어서 처리할 수 있다” — 왜: 새로고침 후에도 승인할 대상을 잃지 않아야 한다.
- “Writer와 Artist 사이를 이동해도 이미 나온 대화와 안내는 같은 기록에서 확인할 수 있다” — 왜: 탭 이동으로 안내가 사라지는 고장을 막는다.
- “러프 스토리보드 완료 안내는 트리트먼트 탭에 들어가도 이전 대화 기록에 남는다” — 왜: 화면 도움말이 완료 사실을 덮어쓰면 안 된다.
- “다른 탭에서 승인해도 요청한 작업은 원래 담당 단계에서 실행된다” — 왜: 승인 카드가 글로벌로 보여도 실행 대상을 현재 탭으로 바꾸면 안 된다.
- “접수된 작업의 응답을 잃어도 다시 승인하면 기존 작업만 확인한다” — 왜: 작업 ID가 있는 요청을 중복 발주하지 않아야 한다.
- “생성 요청이 진행 중일 때 보류 목록을 다시 눌러도 같은 요청을 중복 실행하지 않는다” — 왜: 승인 실행 중 복원 버튼을 중복 입력할 수 있다.
- “요청 뒤 다른 탭으로 이동해도 돌아온 승인 목록에는 원래 요청 대상이 모두 남는다” — 왜: 응답이 늦게 도착하는 실제 경로를 재현한다.
- “다른 프로젝트로 이동하면 이전 프로젝트의 보류 작업을 승인할 수 없다” — 왜: 프로젝트 전환으로 비용과 대상이 섞이면 안 된다.
- “보류한 단계 안내는 새로고침 뒤 자동으로 뜨지 않고 수동으로 다시 열 수 있다” — 왜: 기존 ‘나중에 자동 재등장 금지’와 재개 경로를 함께 지킨다.
- “취소한 요청은 보류 목록에 남지 않고 실행하지 않는다” — 왜: 취소와 보류의 결과가 달라야 한다.
- “접수 결과를 받기 전에 새로고침하면 확인되지 않은 요청을 바로 재발주하지 않는다” — 왜: 접수 여부를 모르는 상태에서 같은 요청을 다시 과금하면 안 된다.
- “인물 요청의 순서를 바꾸어도 모든 인물을 각각 한 번 처리한다” — 왜: 첫 항목에만 의존한 구현의 역순 재현이다.
- “여러 배경의 새 모습을 요청하면 승인 전에는 실행하지 않고 승인 뒤 모든 배경을 처리한다” — 왜: 인물과 같은 첫 항목 누락 경로가 배경에도 있었다.
- “여러 배경을 다시 만들라고 하면 승인 뒤 각 배경의 재생성을 한 번씩 요청한다” — 왜: 재생성 명령에서도 첫 작업만 찾는 고장을 재현한다.
- “일부 작업을 시작한 뒤 남은 요청을 취소하면 이미 시작한 작업을 중복 실행하지 않고 나머지는 시작하지 않는다” — 왜: 복구·생성 진행 중 취소 경계를 지킨다.

- “인물의 원래 설명을 저장했으면 생성 진행 중이 아니라 완료로 알린다” — 왜: 저장이 끝난 원천 설명 변경을 이미지 생성과 같은 진행 상태로 오인하면 안 된다.
- “다른 화면이 이미 확인 중인 작업이 끝나면 재조회도 완료로 알린다” — 왜: 기존 조회를 공유할 때 완료를 진행 중으로 잘못 보고하는 경계를 확인한다.

- 공유 계약: B가 소유한 Artist store의 `traceId/onJob/onCreated`를 사용한다. 새 행의 키를 승인 요청에 보존하며 생성 영수증으로 실제 상태를 읽는다.

- 넓은 검사: `agent-a-related.log` — chat/producer/artist 77파일, 606 통과·2 실패·1 기존 제외.
- 타입 검사: A 변경과 신규 19개 시점 `node node_modules/typescript/bin/tsc --noEmit --pretty false` 통과. 신규 21개 시점 최신 출력(`agent-a-typecheck.log`)은 리더 임시 화면 fixture 두 곳의 ArtistState에 없는 projectId 속성으로 실패하며 A 경로 오류는 없다. 리더에 전달했다.

## 남은 빨간불 판정 카드

1. 약속: “채팅에서 새 모습을 만들어 달라고 하면 승인 뒤 그 캐릭터에 그 모습이 추가된다”. 실제: 새 모습 호출에 영수증·생성 행 키를 전달하는 옵션을 추가하면서 기존 `tests/artist/appearances.test.ts:107`의 **정확한 호출 문자열** 정규식이 불일치한다. 같은 약속을 실제 채팅→승인→생성으로 실행한 신규 검증은 통과한다.
2. 약속: “채팅에서 배경의 새 모습을 만들어 달라고 하면 승인 뒤 추가되고, 특정 모습만 다시 그릴 수 있다”. 실제: 동일한 추가 옵션으로 `tests/artist/location-appearances.test.ts:149`의 호출 문자열 정규식이 불일치한다. 여러 배경 승인 소비와 모습 키 유지 검증은 통과한다.

기대값을 완화하거나 테스트를 지우지 않았다. 테스트를 맞추려고 실행되지 않는 코드/주석을 추가하지도 않았다. **제안: 한국어 약속은 그대로 유지하면서 이 두 소스 문자열 검사를 실제 실행 경로 검증으로 바꾸는 판단이 필요하다.** 현재 결과를 전체 통과로 보고하면 안 된다.

## 혼자 정한 것

요청 수·모델·가격·자동 재시도 상한 정책을 새로 정하지 않았다. 구현 선택은 기존 카드 한 장 안에 대상 전체를 묶고, 보류를 같은 브라우저에서 프로젝트별로 복원하며, 실패 뒤에는 명시적인 다시 열기/승인으로 남은 대상만 확인하는 것이다. 기존에 접수된 작업은 식별자로 조회하고 접수가 불명확하면 재발주하지 않는다.
