# 러프 중복 접수 수정 보고 — MVP-18

**같은 5개 샷이 세 번씩 생성된 운영 사건을 확인했고, 외부 이미지 접수 전에 샷을 원자적으로 예약하는 수정안을 완성했다. 접수 응답 유실·SDK 내부 재시도·큐 정리 버튼을 통한 재발주 경로도 막았다. 관련 경로 34개와 기존 모델·키 회귀 43개가 통과했다. 실제 개발 DB의 격리 검증은 A 담당이 수행하며, 운영 적용 및 유료 생성 검증은 이 보고의 완료 범위에 포함하지 않는다.**

## 사건과 원인

운영 조회 근거는 [C 사건 보고](agent-c-history.md)와 [허용된 시각·식별자 자료](agent-c-history-data.json)다. 동일 프로젝트의 `sh_01_09`는 서로 다른 작업 3개, `sh_02_10`~`sh_02_13` 묶음도 작업 3개로 접수되어 모두 완료됐다. 서로 다른 5샷에 총 15샷분이 생성되었으며, 중복분은 10샷분이다. 청구 금액은 확인하지 않았다.

자동 요청은 22:14:59.776·22:15:04.100·22:15:09.558 KST에 각각 미완료 39·큐 8을 읽었다. 이어진 서버 분류는 모두 39개 중 5개 제출 계획을 만들었다. 첫 단일샷 작업의 DB 생성은 22:15:14.300545였다. 외부 접수가 끝난 뒤에야 작업 행을 만들던 순서 때문에, 앞선 요청이 처리 중인 샷을 다음 요청이 다시 고를 수 있었다.

수정 전 실제 POST 경로 회귀에서도 동시 두 요청이 같은 5샷을 서비스에 총 4번 접수했다. 수정 후에는 서로 다른 두 묶음만 총 2번 접수하고 두 요청이 같은 작업 번호를 공유한다. 다중 탭·화면 재마운트·폴링 중 어느 것이 당시 첫 중첩을 일으켰는지는 호출 식별자가 없어 미확정이다.

## 실행한 한국어 약속

- 같은 러프 샷을 동시에 요청해도 서비스에는 한 번만 접수한다.
- 러프 접수 응답을 잃으면 같은 샷을 다시 보내지 않고 접수 확인 대기로 남긴다.
- 서비스가 러프 접수를 거절했다고 확인되면 예약을 해제하고 실패를 알린다.
- 접수된 러프의 기록 저장이 실패해도 작업 번호를 바꾸어 다시 접수하지 않는다.
- 러프 진행 작업 조회가 실패하면 빈 목록으로 간주해 새로 접수하지 않는다.
- 서비스가 503을 반환해도 러프 HTTP 접수는 한 번만 보내고 불확실한 오류를 보존한다.
- 접수 중인 러프는 정리 버튼으로 예약을 풀어 중복 주문하지 않는다.
- 화면과 상태를 다시 조회해도 러프 접수 확인 대기 안내가 사라지지 않는다.

이 약속은 이미 접수됐을 수 있는 유료 작업을 새 번호로 다시 주문하지 않기 위한 경계다. 고정 동시성·재시도 횟수·복구 시간 상한을 새로 정하지 않았다.

## 수정 결과

| 경계 | 결과 |
| --- | --- |
| DB 예약 | 프로젝트 단위 트랜잭션 잠금 안에서 소유자·워크스페이스·샷 소속·내용을 검사하고 기존 queued 작업과의 부분 겹침까지 확인한다. 겹치면 기존 작업을 반환한다. |
| 외부 호출 | 예약한 작업 행을 먼저 저장한 뒤 서비스에 한 번 접수하고, 받은 요청 번호를 같은 행에 연결한다. |
| 완료와 경합 | 후보를 읽은 뒤 다른 요청이 이미 완성했으면 자동 생성에서 제외한다. 명시적 재생성은 기존 force 의도를 유지한다. |
| 명확한 접수 거절 | HTTP 4xx 중 응답 불확실성에 해당하는 408·425·429를 제외한 거절은 예약을 실패로 전환하고 오류를 돌려준다. |
| 응답 유실·5xx·연결 저장 실패 | 예약을 queued로 보존한다. 시간이 지났다는 이유로 실패 처리하거나 다른 요청으로 재발주하지 않는다. |
| SDK 재시도 | 설치된 SDK 1.9.5의 queue.submit은 내부적으로 최대 3회 재시도한다. 러프에서만 키 레지스트리 내부의 HTTP 1회 제출을 사용한다. 다른 이미지·영상의 기존 호출 동작은 유지한다. |
| 작업 정리 | 아직 queued인 러프 작업 삭제는 409로 막는다. 외부 작업이 종료되지 않은 상태에서 선점을 지워 재발주할 수 없게 한다. 완료 이력·다른 종류 작업 정리 동작은 기존 계약을 유지한다. |
| 화면 재진입 | 기존 예약의 접수 확인 대기 상태를 RPC·POST·GET에서 보존하고 화면에 안내한다. |

공식 HTTP 계약은 [fal 호출 문서](https://fal.ai/docs/documentation/development/calling-your-endpoints)의 queue POST, `Authorization: Key`, `fal_webhook` 규칙과 설치된 SDK의 `queue.js`·`request.js`를 대조했다. 테스트에는 가짜 자격값과 가짜 fetch만 사용했다. 키 원문·운영 프롬프트를 증거에 남기지 않았다.

## DB 검증과 남은 범위

로컬 libpq에는 initdb·psql은 있으나 postgres 실행 파일이 없어 격리 로컬 DB 시작이 실패했다. 설치나 의존성 추가는 하지 않았다. 이후 사용자의 Supabase 접근 권한 확인에 따라 A 담당이 기존 개발 DB 연결로 **격리 스키마의 실제 SQL 동시성·권한 검증**을 맡았다. A의 최종 증거가 별도 첨부되어야 실제 SQL 검증 통과로 판단할 수 있다.

새 예약 RPC는 배포 전 해당 환경 DB에 적용되어야 한다. RPC가 없는 환경에서는 접수가 실패로 닫히므로 코드만 단독 배포하면 러프 신규 접수가 동작하지 않는다. 운영 DB 적용과 DB 타입 재생성은 이 B 작업에서 수행하지 않았다.

불확실한 외부 접수는 자동으로 새 발주하지 않도록 남긴다. 서비스 요청 번호 자체를 잃은 작업의 결과 연결·안전한 수동 해제 자동화까지 새로 구현한 것은 아니다. 실제 서비스 생성·청구·이미지 품질 검증은 하지 않았다. 기존 운영 중복 결과를 삭제하거나 환급하지 않았다. 화면에 보였던 8→5→4→14 전체 연쇄 중 ‘14’의 원래 의미는 C 보고의 제한대로 조사 대기다.
