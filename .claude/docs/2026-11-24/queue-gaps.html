C05 · 접수 번호를 잃은 예약이 영구 좀비가 된다

닫힘

막는 길 3개를 넣었다. 순서대로 작동한다.

확인한 것 / 안 한 것

확인한 것

  • 새 테스트 7파일 · 문장 18개. 접수 기록 재시도(DB 오류만 · 0행은 즉시 실패) · 웹훅 잡 id 되찾기 · 워치독 예약 건너뛰기 · 제출 경로 5곳이 잡 id 를 심는 것 · 종류별 시계 · 예외표 10분 기억.
  • 기존 테스트 976 파일 8,244건 통과(흉내 DB 기준). pnpm typecheck · pnpm lint:design 통과.
  • DB 트리거가 fal_key_id 가 비어 있을 때 키를 고르는 것(마이그레이션 20261027100000 본문 확인).
  • projects.workspace_id 외래키가 있어 한 질문 소유 확인이 가능한 것(마이그레이션 20260305082450).

안 한 것

  • 실제 DB 트리거와 함께 돌려 보지 않았다. 테스트는 DB 를 흉내 낸다.
  • 실제 fal 웹훅이 ?jobId= 가 붙은 주소로 그대로 오는지 확인하지 않았다. fal 문서는 웹훅 URL 을 그대로 호출한다고 적지만 실측은 없다.
  • 접수 기록이 실제로 실패하는 상황을 만들어 보지 않았다. 11/23 장애 때 추정으로 남은 원인이다.
  • 예약 왕복 수 변화를 시간으로 측정하지 않았다. 폴링 보고서의 측정 스크립트는 상태 조회만 잰다.
  • 안 심은 4곳의 제출 경로는 손대지 않았다.
