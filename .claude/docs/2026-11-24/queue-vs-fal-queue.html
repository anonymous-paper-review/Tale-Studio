1

큐라는 낱말의 두 뜻

먼저 알아둘 것: 이 문서에서 큐(queue, 요청을 줄 세워 두는 구조)는 두 가지 다른 물건을 가리킨다.

뜻하는 일누구의 것
(a) 대기줄요청을 받아 두고 자리가 나면 차례로 처리한다fal 큐
(b) 장부와 입장 통제요청을 기록하고 정원을 넘으면 거절한다우리 generation_jobs

fal 큐의 동작

  • 우리가 https://queue.fal.run/<model> 로 요청을 보내면 request_id 를 즉시 돌려준다.
  • fal 이 GPU 가 빌 때 처리한다. 초과 제출도 거부하지 않고 자기 큐에 태운다.
  • 끝나면 우리가 적어 준 fal_webhook 주소로 HTTP 요청을 1회 보낸다(웹훅, 서버가 일이 끝난 뒤 상대 주소로 보내는 알림 요청). 우리가 status 를 직접 물어도 된다.
  • 결과 파일은 fal CDN(파일을 내려받게 해 주는 서버)에 잠시 있다 사라진다. 보존 시간은 미확인이다.

질문은 이렇다. fal 에 큐가 있는데 내부 큐를 만든 이유가 "우리가 관리할 수 있다"였고, 그래도 유저가 결과를 언제 받을지 모르는 문제는 못 푸는 것 아닌가.

"관리 가능"에 해당하는 장부·과금·안전망·분류는 이뤘다. "기다리는 경험"에 해당하는 대기줄·예상 시각은 애초에 만들지 않았고, 그 자리에 폴링 비용이 들어왔다. 오너 판단 "결과적으로 같은 문제를 못 푼다"는 결과 도착 시각에 한해 맞다.

  • 로컬 개발은 fal 이 보낼 공개 주소가 없고(be2be659 본문 "웹훅 없는 로컬은 폴링이 유일한 완결 경로"), 운영에서도 웹훅이 가끔 유실돼 폴링 틱이 fal 에 직접 묻는 안전망이 주 경로로 자랐다. 유실이 얼마나 자주 일어나는지 측정한 기록은 이번 조사에 없다.
