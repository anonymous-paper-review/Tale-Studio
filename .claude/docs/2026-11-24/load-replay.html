열쇠 포기가 생기는 길(코드로 확인)

  1. 열쇠 자리는 legacy-1000 34 + prod-2000 1(운영 FAL_KEYS). 화면 요청(pickFalKey)과 DB 트리거 모두 "남은 자리가 가장 많은 열쇠"를 고른다.
  2. legacy-1000 에 34장이 그려지는 중이면 다음 그림은 prod-2000 으로 간다. 잔액이 0 이라 fal 이 즉시 거절한다.
  3. 거절된 그림은 실패로 기록된다(종류 billing). 즉시 실패해서 prod-2000 의 자리는 항상 비어 보인다. 그래서 넘치는 그림은 전부 이 죽은 열쇠로 빨려 들어간다.
  4. 화면이 10초 뒤 같은 칸을 다시 보낸다. 아직 34장이 차 있으면 또 죽은 열쇠, 두 번째 실패.
  5. 자동 그리기는 같은 칸 실패 2번이면 포기한다(billing 은 면제 종류가 아니다). 서버는 "건너뜀"이라고 200 으로 답하고 그림 번호를 주지 않는다. 학생 화면엔 실패 표시, 사람이 직접 "다시 그리기"를 눌러야 산다.

20명 × 3장 = 60장 동시 → 34장을 넘는 26장이 이 길로 간다. 20명 × 2장 = 40장이면 6장이다. 열쇠를 빼면 넘치는 그림은 죽은 열쇠 대신 "정원 찼음"(429)을 받고, 화면이 10초 뒤 다시 보낸다. 기다리는 것이고 실패가 아니다.

"1개만 받은 인스턴스도 5~11초"가 뜻하는 것. 그 서버가 일을 느리게 한 것이 아니다. 요청이 서버 안에 들어가기 전에 밖에서 기다린 시간이 응답 시간에 들어간 것이다. 카나리(검열 · fal 을 거치지 않는 요청)도 같은 순간 8~12초였으니 기다린 자리는 라우트 안이 아니라 공통 입구다.

왜 기다렸나, 후보 둘. (가) 새 인스턴스를 켜는 시간: 제출 30개가 인스턴스 16개로 갈렸다는 것은 그 순간 새 서버가 많이 켜졌다는 뜻이고, 하나 켜는 데 1~3초가 든다. (나) 한 인스턴스 안에서 CPU 를 나눠 쓰는 경합: Fluid Compute 가 켜져 있으면(오너 확인) 한 서버가 여러 요청을 같이 받는다. 바깥 서비스를 기다리는 것은 CPU 를 안 먹지만, 제출 요청이 그림 입력을 꾸미고 로그인 서명을 확인하는 동안은 CPU 를 쓴다. 그 서버에 함께 올라탄 카나리 · 폴링이 그만큼 늦어진다. 1판의 "한 번에 1요청만 받아 자리가 모자란다"는 Fluid 가 꺼져 있을 때의 설명이라 접는다. 둘 중 어느 쪽인지는 Vercel 함수 로그(콜드 스타트 표시 · 함수별 소요 시간)에서 1분 안에 갈린다.

오너 질문 "Vercel 문제는 아닌 것 맞지?"에 대한 답. 반은 맞다. 그림을 실패시킨 것은 Vercel 이 아니다(열쇠다). 그러나 느려진 곳은 Vercel 서버 함수가 맞다: 같은 순간 DB 직접 질문 0.11초 vs Vercel 경유 8~12초. 실제 브라우저에서 이 느림은 잡 상태 폴링(한도 10초)이 끊겨 3→6→12초로 물러나는 모양으로 나타난다. 그림은 결국 뜨지만 "완료" 표시가 늦게 온다. 제출 요청에는 한도가 없어 20초를 그냥 기다린다.

알고만 있을 것

시험 도구 로그인 실패가 무엇인가

부하 스크립트는 시험 계정 20개로 들어가기 위해 이메일 없이 서버에서 로그인 링크(마법 링크)를 직접 만들어 바로 쓴다. 같은 계정에 이 링크를 연달아 2번 만들면 먼저 것이 무효가 되고(otp_expired), 짧은 시간에 많이 만들면 Supabase 로그인 서버가 429 로 막는다. 실행 B 에서 1명이 이 때문에 못 들어갔고 실행 C 전에 스크립트를 고쳤다(계정당 1번 발급). 실제 학생은 이 길을 쓰지 않는다(이메일 · 비밀번호 로그인). 앱 문제가 아니다.

"제출 라우트를 DB 자리 예약만 하고 바로 답한다"가 무슨 뜻인가

지금 학생이 "그려줘"를 누르면 서버는 차례로 ① 글 검열 회사(Creem)에 묻고 답을 기다린다(1~3초) ② DB 에 그림 자리를 예약한다(0.3초) ③ fal 에 그림을 주문하고 접수증을 기다린다(1~2초) ④ 그 다음에야 학생에게 "접수됐어요"라고 답한다. 학생은 4~5초 동안 단추가 돌아가는 것을 본다. 바꾸면 ② 자리 예약만 하고 0.5초 안에 "접수됐어요"라고 답하고, 서버는 답을 보낸 뒤에도 그 요청의 나머지(① 검열 → ③ fal 주문)를 이어서 한다(Vercel 의 "응답 뒤 작업"). 검열에 걸리거나 fal 이 거절하면 그 자리를 실패로 바꾸고, 화면은 지금처럼 폴링으로 실패를 본다. 좋은 점: 학생 체감이 빠르고, 서버 연결이 짧게 끝난다. 주의할 점: 지금은 검열 거절을 즉시 안내문으로 보여주는데, 바꾸면 몇 초 뒤 폴링으로 알게 되어 안내 길을 다시 짜야 한다. Fluid 가 켜져 있으면 서버가 하는 일의 양은 같다. 그래서 지금은 하지 않는다.

동시 장수 3 → 2 가 바꾸는 것

  • 그림만이다. Artist 화면이 빈칸을 스스로 채울 때 한 사람이 한 번에 보내는 장수. 영상은 다른 상수(사용자당 영상 자리 3)이고 건드리지 않았다.
  • 학생 1명이 6장을 받는 시간: 3장씩 2번 ≈ 2.5분 → 2장씩 3번 ≈ 3.7분(장당 68초 기준).
  • 20명이 동시에 들어올 때 fal 자리(34)를 넘는 장수: 26장 → 6장. 서버 함수에 동시에 걸리는 제출: 60 → 40.
  • 러프 스토리보드가 도는 동안의 1장 규칙은 그대로다.
  • 되돌리기: 상수 1개(ARTIST_SLOTS_IDLE)와 같은 이름의 테스트 기대값.

화면 그리기 · 그림 내려받기가 없어도 병목 측정이 맞는 까닭

화면 그리기는 학생 컴퓨터에서 일어난다. 그림 내려받기는 Supabase 파일 저장소(DB 도 Vercel 서버 함수도 아닌 별도 서버)에서 온다. 병목 후보 둘을 하나도 거치지 않는다. 그림이 뜨기까지 1~2초가 더 걸릴 뿐이다. 오히려 실제 브라우저는 탭이 뒤에 있으면 폴링을 느리게 하므로, 스크립트가 실제보다 조금 더 가혹하다.

DB 메모리 "약속 2.6 GB" 가 무엇인가

대시보드의 Memory commitment 는 "기계 안 모든 프로그램이 쓰겠다고 예약한 양의 합"이다. 실제로 쓴 양(Used)이 아니다. Postgres 는 연결 1개마다 작업 메모리를 예약하고(최대 60연결), 공유 버퍼를 예약한다. 같은 기계에 로그인 서버 · 조회 서버(PostgREST) · 연결 풀러 · 저장소 서버도 산다. 예약 합이 기계 메모리를 넘으면 배지가 WARNING, 메모리 + Swap 까지 넘으면 SEVERE 다. 11/23 은 0.38 GB 기계에 2.62 GB 를 약속해 둔 상태에서 20명이 실제로 쓰기 시작하자 Swap(디스크)으로 넘쳤고, Swap 이 디스크 예산을 태웠다. 오늘 Micro 는 1.06 GB 기계에 1.63 GB 약속 · Swap 0.15 GB 로 끝났다. 수업 뒤 같은 화면에서 Swap 이 0.3 GB 를 넘으면 Small(2 GB · 월 $5 추가)로 간다.

DB 를 둘로 나누는가(무료 티어 하나 더 등)

나누지 않는다. 까닭 4개

  • 로그인은 프로젝트에 묶여 있다. 두 번째 DB 는 같은 사용자를 모른다. 소유 확인(RLS · workspaces)을 다시 만들어야 한다.
  • 11/23 의 부하는 "사용자별 폴링"이었다. 데이터를 어디로 옮기든 폴링은 그 데이터를 따라간다. 요청 수는 안 줄고 자리만 바뀐다.
  • 무료 티어는 Nano(0.5 GB)이고 1주일 안 쓰면 멈춘다. 지금 Micro 보다 약하다.
  • Supabase 문서(Read Replicas): 읽기가 많아도 "가장 큰 컴퓨트(16XL)에 닿은 뒤" 복제본을 권한다. 그 전에는 컴퓨트 크기를 올리라는 뜻이다. 그리고 오늘 실측에서 DB 는 이미 병목이 아니다.

대신 하는 것. 순서대로

  • 이번에 한 것: Nano → Micro(비용 0). 다음은 Small(월 $5 추가). 돈으로 사는 것이 코드보다 싸다.
  • 열쇠 빼기 · 동시 장수 2(결정됨). 그 다음 Vercel 로그로 느림의 원인을 가른다.
  • 폴링을 밀어주기(Realtime 2층)로 바꾸면 DB 질문 자체가 준다. 1층 보고서 6절에 적었다.
  • 자주 읽는 작은 상태(작업 상태)만 캐시(Vercel KV 등)에 두는 방법도 있다. 두 번째 DB 가 아니라 두 번째 "서랍"이다. 지금은 필요 없다.
