알고만 있을 것

DB 메모리 "약속 2.6 GB" 가 무엇인가

대시보드의 Memory commitment 는 "기계 안 모든 프로그램이 쓰겠다고 예약한 양의 합"이다. 실제로 쓴 양(Used)이 아니다. Postgres 는 연결 1개마다 작업 메모리를 예약하고(최대 60연결), 공유 버퍼를 예약한다. 같은 기계에 로그인 서버 · 조회 서버(PostgREST) · 연결 풀러 · 저장소 서버도 산다. 예약 합이 기계 메모리를 넘으면 배지가 WARNING, 메모리 + Swap 까지 넘으면 SEVERE 다. 11/23 은 0.38 GB 기계에 2.62 GB 를 약속해 둔 상태에서 20명이 실제로 쓰기 시작하자 Swap(디스크)으로 넘쳤고, Swap 이 디스크 예산을 태웠다. 오늘 Micro 는 1.06 GB 기계에 1.63 GB 약속 · Swap 0.15 GB 로 끝났다. 수업 뒤 같은 화면에서 Swap 이 0.3 GB 를 넘으면 Small(2 GB · 월 $5 추가)로 간다.

DB 를 둘로 나누는가(무료 티어 하나 더 등)

나누지 않는다. 까닭 4개

  • 로그인은 프로젝트에 묶여 있다. 두 번째 DB 는 같은 사용자를 모른다. 소유 확인(RLS · workspaces)을 다시 만들어야 한다.
  • 11/23 의 부하는 "사용자별 폴링"이었다. 데이터를 어디로 옮기든 폴링은 그 데이터를 따라간다. 요청 수는 안 줄고 자리만 바뀐다.
  • 무료 티어는 Nano(0.5 GB)이고 1주일 안 쓰면 멈춘다. 지금 Micro 보다 약하다.
  • Supabase 문서(Read Replicas): 읽기가 많아도 "가장 큰 컴퓨트(16XL)에 닿은 뒤" 복제본을 권한다. 그 전에는 컴퓨트 크기를 올리라는 뜻이다.

대신 하는 것. 순서대로

  • 이번에 한 것: Nano → Micro(비용 0). 다음은 Small(월 $5 추가). 돈으로 사는 것이 코드보다 싸다.
  • 서버 함수 쪽: Fluid Compute(4절 2번). 지금 병목은 DB 가 아니라 여기다.
  • 폴링을 밀어주기(Realtime 2층)로 바꾸면 DB 질문 자체가 준다. 1층 보고서 6절에 적었다.
  • 자주 읽는 작은 상태(작업 상태)만 캐시(Vercel KV 등)에 두는 방법도 있다. 두 번째 DB 가 아니라 두 번째 "서랍"이다. 지금은 필요 없다.
