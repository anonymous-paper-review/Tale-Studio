function dedupeLoadData(projectId: string | null, run: () => Promise<void>): Promise<void> {
  if (!projectId) return run()
  const running = loadDataInFlight.get(projectId)
  if (running) return running
  const started = run().finally(() => {
    if (loadDataInFlight.get(projectId) === started) loadDataInFlight.delete(projectId)
  })
  loadDataInFlight.set(projectId, started)
  return started
}

Supabase Realtime 조사

오너 질문 3개에 답한다. 실제로 쓰는가, 공학적으로 이득인가, 유료만 되는가. 근거는 Supabase 공식 문서(2026-11-24 열람).

먼저 알아둘 것

Realtime 은 브라우저와 Supabase 사이에 열어 두는 연결(WebSocket)이다. DB 행이 바뀌면 Supabase 가 그 연결로 알림을 밀어 준다. 화면이 3초마다 묻는 대신 바뀔 때 한 번 받는다.

질문답근거
실제로 쓰는 기능인가그렇다. 두 방식이 있다. Postgres Changes(표의 변경을 그대로 구독)와 Broadcast(DB 트리거가 채널로 메시지를 보냄). 문서는 구독자가 많으면 Broadcast 를 권한다.docs/guides/realtime/postgres-changes · subscribing-to-database-changes
유료만 되는가아니다. Free: 동시 연결 200 · 초당 메시지 100. Pro: 500 · 500. 수업 20명은 Free 범위 안이다.docs/guides/realtime/limits 표
공학적 이득이 있는가있다. 잡 상태 폴링(3초마다 요청)과 진행 목록 폴링(4초마다 요청)이 0 이 된다. 남는 것은 30초 안전망 폴링 1개다. 단, 1층 경량화는 그 안전망과 다른 라우트에 그대로 필요하다.이 문서 3절 측정 · 원장 1절

주의

Postgres Changes 는 변경 1건마다 구독자 수만큼 권한 검사를 한다. 구독자 500 · RLS 켬 기준 초당 변경 30건이 상한이다(문서 표, Micro). 우리 쓰기 빈도(초당 1건 미만)에서는 문제가 없다. 그래도 표를 열지 않는 Broadcast 방식이 우리 구조에 맞다.
