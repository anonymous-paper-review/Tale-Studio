요청의 생애

화면은 서버가 먼저 말을 걸 수 없어서 3초마다 "다 됐나" 하고 묻는다(폴링). 이 물음 하나하나가 Vercel 서버 함수를 새로 켜고, 함수마다 DB 왕복을 3~4번 치른다.

서버 함수는 라우트마다 적힌 maxDuration(30~300초)까지만 산다. "한 요청에 5분, 10분 기다려 준다"는 기억은 이 저장소에서는 맞지 않는다.

결정할 것 0개, 알아둘 것 3개.

근거 커밋 34d853d4 · 176c7885 · be2be659 · 2026-11-23 장애 조사

1

먼저 알아둘 것

이 문서의 결론 세 개가 기대는 메커니즘 네 줄.

  • 브라우저는 서버가 먼저 말을 걸 수 없다. 서버가 브라우저에 소식을 전하는 방법은 브라우저가 주기적으로 묻는 것(폴링) 아니면 브라우저가 열어둔 연결 둘뿐이다.
  • 웹훅은 fal 이 우리 서버로 보내는 HTTP 요청이다. 공개 주소가 있는 서버만 받을 수 있고 브라우저와 localhost 는 받지 못한다.
  • Vercel 서버 함수는 요청 1건마다 켜지는 일회용 실행이다. 응답을 보내거나 maxDuration(라우트가 적은 최대 실행 초)이 지나면 꺼지고, 요청 사이에 항상 떠 있는 서버는 없다.
  • 서버와 DB 사이 왕복은 1.2~2.4초가 걸린다(11/23 실측, DB 는 싱가포르 Supabase, 함수는 미국 동부).

화면이 폴링하는 이유

fal 에 그림을 맡기면 결과는 웹훅으로 우리 서버에 온다. 서버는 그 결과를 저장할 수 있지만 브라우저에 직접 알릴 수 없다. 화면이 결과를 보려면 브라우저가 서버에 물어야 하고, 그 물음이 pollGenerationJob 이다. 2026-06-05 첫 커밋(34d853d4)의 본문은 "탭을 닫아도 서버가 결과를 영속화"한다고 적고, 같은 커밋에 "브라우저 polling 헬퍼"를 넣었다. 같은 날 커밋 176c7885 는 폴링 창구에 "웹훅 미수신 시 안전망"을 겸하게 했다. 웹훅을 받을 수 없는 로컬 개발에서는 폴링이 결과를 완결하는 유일한 경로다(be2be659 본문).

폴링의 생애주기

여러 사용자가 여러 요청을 동시에 쏠 때 폴링이 어떻게 시작해서 끝나야 하는지와 우리 코드의 차이.

먼저 알아둘 것. 폴링 한 번은 서버 함수를 새로 켜는 요청 한 건이고, 앞 요청이 끝나기를 기다리는 일은 폴링하는 쪽 코드가 하지 않으면 아무도 하지 않는다.

왜 이렇게 됐나

설계 결정의 결과로 보기 어렵다. 기본 도구가 그렇게 동작한다. setInterval 은 앞 요청이 끝났는지 알지 못하고, fetch 는 시간 한도를 걸지 않으면 영원히 기다린다.

!res.ok 면 throw 하는 방식은 추정이지만 이렇게 읽힌다. 2026-06-05 첫 판에서 이 라우트가 실패하는 경우는 권한(401)과 없는 잡(404)뿐이어서 "HTTP 오류는 작업 실패"가 맞았다. 그 뒤 DB 지연으로 500과 504 가 나오기 시작하자 같은 줄이 일시 오류까지 실패로 분류하게 됐다. 이 설명은 코드 주석과 커밋 메시지에서 추정했고, 당시 구현자에게 확인하지 않았다.

같은 DB 지연이 11/23 에는 generation-status 에서 실패 181회(그중 148회는 5분 대기 뒤 끊김)로 나타났다. generation-jobs/[id] 의 오류 횟수는 이 문서에서 확인하지 않았다.

after() 와 코드 두 곳

after() 는 응답을 보낸 뒤 같은 요청 컨텍스트에서 계속 실행한다. Next.js 16 기능이고, 같은 maxDuration 예산 안에서 돈다.

웹훅은 finalize 를 after() 에 넘기고, 컨텍스트 밖(테스트)이면 그 자리에서 실행한다.

src/app/api/fal/webhook/route.ts:67-72async function runAfterResponse(work: () => Promise<void>): Promise<void> {
  try {
    after(work)
  } catch {
    await work()
  }

"5분, 10분" 기억의 교정

플랫폼이 한 요청을 5~10분 기다려 주는 일은 없다. 라우트마다 적은 maxDuration 까지만 기다리고, 이 저장소의 값은 30초에서 300초다. 10분은 STALE_QUEUED_MS(generation-job-timing.ts:9)로 화면이 폴링을 포기하고 서버가 잡을 유령으로 보는 시각이지 함수 수명이 아니다. 300초(5분)는 코드 주석에 "Hobby 한도"로 적힌 값이다. 11/23 에 generation-status 148회가 5분을 기다린 뒤 끊겼는데, 그 5분의 출처는 확인하지 않았다.
