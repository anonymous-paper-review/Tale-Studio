# 3단계 — MoR 체크아웃 + 웹훅

상태: **열림 (2단계 뒤)** · 기획 의존: 통로 이원화 결정 + 게시 문서 4종

핵심 명제: **"결제 성공"의 진실원은 브라우저가 아니라 웹훅이다.** 성공 리다이렉트 페이지를 믿고
권한을 주면 위조당한다. 2단계가 끝나 있으므로 웹훅 핸들러가 할 일은 "플랜 세팅 + Take 적립"으로 좁다.

## 작업 목록

| # | 항목 | 내용 |
|---|---|---|
| 3-1 | 벤더 선정 | ✅ **Paddle 확정** (2026-09-01 오너). 남음(오너): paddle.com 계정 + 샌드박스(sandbox-vendors.paddle.com) 개설 — 사업자 정보 필요. 그 뒤 체크아웃·웹훅은 에이전트 몸. 웹훅 서명은 Paddle-Signature(HMAC) 검증 |
| 3-2 | 체크아웃 연동 | 팩 4종(Mini/Standard/Pro/Studio) + 구독 사다리. 결제 주체는 workspace |
| 3-3 | 웹훅 핸들러 | 4원칙: ①서명 검증 ②멱등성(`billing_events.mor_event_id` UNIQUE, 중복 무시) ③순서 뒤집힘 허용(이벤트 타임스탬프 판단) ④원본 페이로드 저장. 실패 시 5xx로 응답해야 MoR이 재시도함 |
| 3-4 | 결제 직후 UX | 웹훅은 수 초~수 분 늦다. 성공 페이지에서 짧은 폴링("결제 확인 중") — 안 하면 "결제했는데 크레딧 0" 문의가 1순위가 된다 |
| 3-5 | 환불·차지백 | `refunded`/`disputed` 이벤트 → 잔여 Take 회수, 이미 썼으면 음수 잔액 + 신규 생성 차단. 환불 정책 문서와 규칙 일치 확인 |
| 3-6 | 자동 충전 | 기본 OFF · 월 상한(기획 숫자) · 실패 시 재시도 정책 |
| 3-7 | 일일 대사 | MoR 거래 목록 vs `billing_events` 비교 스크립트 — 웹훅 유실은 반드시 일어난다. Vercel Cron으로(기존 `CRON_SECRET` 인프라 재사용 — 밤 루프는 2026-09-01부로 폐지) |
| 3-8 | 웹훅 실패 알림 | 핸들러 에러는 조용히 죽으면 안 됨. 이메일/텔레그램 아무거나 즉시 알림 |
| 3-9 | 심사·라이브 전환 | 문서 4종+실가격 페이지 게시 → MoR 입점 심사 → dev 전 구간 스모크 → 라이브 키 전환 |

## 기획 의존 — `specs/payments-planner-agenda.html`

- **안건 ① 통로 이원화**: S·P=MoR / 국내 법인=수동 계약 여부. 3-2의 상품 구성과 2-7 수동 경로의 최종 모양이 이 결정에 달림.
- **안건 ④ 문서 4종**: 약관(생성물 권리·학습 사용)·환불정책·개인정보처리방침·실가격 페이지. 심사 제출물이라 3-9의 전제.
- **안건 ② 법률**: 선불전자지급수단 확인 결과에 따라 충전분 소멸(2-6) 정책이 바뀔 수 있음 — 코드가 아니라 정책 파라미터로 흡수.

## 완료 증거

- dev에서 샌드박스 카드로 전 구간 스모크: 체크아웃 → 웹훅 → Take 적립 → 생성 1회 → 차감 확인
  (실 카드 결제는 자동화 금지 — 스모크 헌법과 동일)
- 같은 웹훅을 2회 재전송해도 적립은 1회 (멱등성 테스트)
- 환불 이벤트로 잔여 Take 회수 + 생성 차단 확인
- 웹훅 핸들러 강제 에러 시 알림 도착 확인
- 심사 통과, 라이브 키는 Production 스코프에만 존재
- 라이브 첫 결제 1건을 일일 대사 스크립트가 정상 대조
