# fal 다중 키 풀 — 동시성·할당 정책

상태: **✅ 단계 0+1 구현·배포 완료 (2026-09-01, main `86ceadb`)** — production은 FAL_KEYS 2키(prod-2000: 34 + legacy-1000: 34 = **합산 상한 68**), preview/dev·local은 legacy 10. 잡별 제출 키 기록(`generation_jobs.fal_key_id`)·least-loaded 디스패치·키별 합산 세마포어 가동 중. 마이그레이션은 dev→live 순으로 적용됨(이력 `20260901150000`). 한도 조정은 코드 배포 없이 FAL_KEYS의 maxInflight 숫자만 바꾸면 다음 배포부터 반영.

## 동시성 실측 (2026-09-01 밤, tale-dev DB · 가짜 키 · 과금 0)

가짜 키 2개(각 maxInflight 6, 합산 12)로 코드 경로 전체를 실제 DB 경쟁으로 검증:

| 항목 | 결과 |
|---|---|
| 레지스트리 파싱·합산 상한 | PASS |
| 병렬 pick 30회 예외 0 · 동률이면 첫 키 | PASS |
| least-loaded (한 키 적재 후 다른 키로 배분) | PASS (10/10) |
| 유저 영상 3개 → video 차단, image는 분리 풀로 통과 | PASS |
| 전역 포화 → 새 유저도 scope=global 차단 | PASS |
| **count-then-submit 경쟁** | ⚠ 발견 — 남은 슬롯 1에 동시 12명 진입 시 **12명 전원 통과(오버슗 11)** |

발견의 의미: 오버슗은 마진으로 봇밖하는 값이 아니라 "같은 순간에 도착한 요청 수"만큼 열린다.
단, 초과의 결과는 에러가 아니라 fal 큐 대기이고, 현 트래픽(시간당 ~17잡)에서 동시 도착은 극소하다.
근본 수리는 티켓 `gen-quota-atomic-gate`(아래) — phase-2 Take hold가 자연스럽게 원자 관문이 되므로 그때 함께 닫는다.

### 마진 결정 (2026-09-01 밤 · 실측 반영)

- **키당 마진 6은 유지** (40→4개 키당 34): 목적은 경쟁 봇밖이 아니라(실측상 불가능) ① 적당한 오버슗 흡수로 fal 큐 대기 0 유지 ② webhook 지연으로 끕늘 카운트 왜곡 ③ 충전액 연동 티어 하락 대비. 상한을 우리 쪽 429로 끓으면 안내 가능한 거절, fal로 넘기면 침묵 대기 — 전자가 UX 통제권을 갖는다.
- **개발 여유 6은 폐지** (legacy 28→34): 상시 유저 슬롯 6개를 놀리는 확정 손실 vs dev 제출이 가끔 fal 큐에 잠깐 걸리는 드문 불편. 밤 루프 폐지로 dev 트래픽이 거의 0이라 후자가 압도적으로 싸다. 유저가 기다리는 것보다 개발이 기다리는 게 맞다.
- 이론상 legacy 계정 총 소비(production 34 + preview 10 + local 10)가 40을 넘을 수 있지만, 세 경로가 동시 포화하는 확률은 현 규모에서 무시 가능 — 초과 시 legacy 쪽만 잠시 큐 대기.

## 현재 구조 (코드 실측)

- 키는 단 하나: `FAL_KEY`. `src/lib/writer/llm/fal.ts`가 모듈 스코프에서 `fal.config()` — **전역 싱글턴**이라 지금 구조로는 키를 못 늘린다.
- 동시성: `src/lib/generation-quota.ts` — 유저당 영상 3·이미지 6(분리 풀), 전역 세마포어 34.
  34의 근거는 계정 동시 한도 실측 40 − 마진 6 (`scripts/fal-slot-probe.mjs`, 2026-08-26).
- ⚠ fal 동시 한도는 **충전액 연동 티어**다 ($1000 충전 = 40 동시). 키마다 충전액이 다르면 한도도 다르다 — 이 문서가 필요한 이유.
- fal은 초과분을 거부하지 않고 큐에 태운다 — 증상은 에러가 아니라 뒤에 온 유저의 대기(head-of-line blocking).
- **제약(설계를 결정짓는 사실)**: fal 잡 status는 제출한 키로만 조회 가능. 다른 키로 조회하면 404.
  → 잡마다 "어느 키로 나갔나"를 기록하지 않으면 폴링·`reconcile.ts`(고스트 잡 정리)·finalize가 전부 깨진다.

## 정책

### 1. 키 레지스트리

env `FAL_KEYS` JSON 배열로 전환. 단일 `FAL_KEY`는 제거한다(호환 레이어 금지 — 콜사이트 한 번에 이행).

```
FAL_KEYS=[{"id":"paid-1","key":"...","pool":"paid","maxInflight":34},
          {"id":"free-1","key":"...","pool":"free","maxInflight":10},
          {"id":"ops-1","key":"...","pool":"ops","maxInflight":8}]
```

`fal.config` 싱글턴 → 키별 `createFalClient` 인스턴스 맵. `maxInflight`는 키별 실측 − 마진.

### 2. 풀 분리 — 유저를 키에 어떻게 태우나

**워크스페이스 고정(sticky) 할당은 하지 않는다.** 고정은 핫 키 쏠림 + 노는 키 낭비를 만들고,
유저별 원가 추적은 fal 대시보드가 아니라 우리 `generation_jobs`로 하면 되기 때문이다.

대신 **풀 = 유저 등급 격리**가 1순위 목적:

오너 결정(2026-09-01)으로 단순화: **풀은 당분간 `production` 하나다** (40+40). free는 v4 정책상 영상 생성이 없어 풀 배정 문제가 소멸했고,
밤 루프는 폐지돼 ops 풀도 불필요. 풀 구조 자체는 레지스트리에 남겨둔다 — 나중에 격리가 필요해지면 env 설정만으로 분리 가능.

풀 안에서는 잡 단위 **least-loaded** (in-flight가 가장 적은 키로 제출). 풀에 키가 1개면 그냥 그 키.

### 3. 세마포어 재구성

- 전역 상한 34 → **키별 상한의 합**. `countQueuedJobsGlobal` → `fal_key_id`별 카운트로 교체.
- 유저당 상한(영상 3·이미지 6)은 풀과 직교하므로 그대로 유지.
- 풀 포화 시 동작은 현행 유지(429 + 안내) — fair-queue 대기열은 기존 백로그(group-a 논의 3)와 합류.

### 4. 잡 기록 — 단계 0의 핵심

`generation_jobs.fal_key_id` 컬럼 추가, 제출 시 기록. status 폴링·reconcile·finalize 전부 이 키의 클라이언트로.
**키가 1개인 지금 미리 넣으면 나중 마이그레이션이 공짜다** — 백필도 상수 한 줄.

### 5. 키별 한도 실측

`fal-slot-probe.mjs`를 키 인자를 받게 확장. 키 추가·충전액 변경 때마다 1회 실측(⚠ 과금 발생) →
`maxInflight` = 실측 − 마진. 마진 근거는 generation-quota.ts 주석의 3가지(오버슛·webhook 지연·티어 하락) 유지.

### 6. 장애 처리

- 제출 실패(네트워크·4xx)는 같은 풀의 다른 키로 **1회만** 재시도 — 제출이 성공했는지 불명확한 실패는 재시도 금지(중복 생성 방지).
- 한 키가 연속 N회 제출 실패하면 쿨다운(레지스트리에서 일시 제외) + 알림. N·쿨다운 시간은 단계 2에서.

### 7. 관측

- 키별 in-flight·일일 생성 수를 `fal_key_id` 집계로. 원가 대시보드(readiness 6장)의 집계 축.
- fal 계정마다 지출 알림(billing alert) 설정 — phase-1 1-7의 완료 증거에 포함.

## 할당 확정 (2026-09-01 · 오너 결정: Production 40+40)

두 계정 모두 동시 40($2000 충전도 40 = 티어 상한). **둘 다 Production 풀에 합산한다 — 목표 80 슬롯.**
별도 개발 전용 계정은 두지 않는다(밤 루프 폐지로 개발 부하 미미 — dev·local은 기존 키를 그대로 쓰면서 계정 40을 공유).

| 키 | 역할 | 상태 |
|---|---|---|
| 새 키 ($2000) | Production 주력 | ✅ Vercel Production `FAL_KEY` 교체 완료(2026-09-01, 다음 배포부터 적용) |
| 기존 키 | Production 보조(단계 1에서 합류) + local·dev Preview | ✅ local `.env.local` + Vercel Preview/Development 배선됨 |

- 단계 1 전(현재 코드 = 단일 키): Production은 새 키 40만 사용, `MAX_GLOBAL_INFLIGHT_JOBS = 34` 그대로(계정당 40 − 마진 6 — 코드 무변경 전환).
- 단계 1 후: `FAL_KEYS=[새키40, 기존키40]` 단일 production 풀 least-loaded, 합산 상한 ≈ 68~74(키별 마진 적용 — 기존 키는 dev 사용분 공제).
- ⚠ 기존 계정 잔액이 $1000 밑으로 떨어지면 한도 하락 가능 — 프로브 재측정 전 인지.

### free 유저 풀 문제는 소멸됨

v4 확정 정책상 free = 프로듀서→라이터 트리트먼트까지(영상 생성 0)이므로 free는 fal 슬롯을 쓰지 않는다 — 풀 배정 문제 없음.
단, 현재 베타 코드는 free도 생성 가능(실제 게이트는 슬롯 1개뿐) — v4 경계로 좁히는 건 phase-2 몸이다.
⚠ 교체 타이밍: fal 잡 status는 제출 키로만 조회되므로, Production 키 교체는 진행 중(queued) 잡이 없는 시점에 한다.
⚠ 한도 재산정: `MAX_GLOBAL_INFLIGHT_JOBS = 34`는 옛 계정 실측 40 기준. 새 계정($2000)은 대시보드 표기 확인 → 필요 시 probe 실측(과금) → 상수 재산정.

## 논의 필요 (오너)

1. **동일 사업자 다계정이 fal 약관상 허용인지** — 정책상 volume 협상(v4 로드맵 분기점 A)과도 얽힘. 계정 쪼개기 대신 한 계정 충전액을 올려 한도를 키우는 게 정답일 수도 있다 — fal에 직접 확인이 가장 싸다.
2. 계정별 충전 정책 — 한도가 충전액 연동이라, 풀별 목표 동시 슬롯을 먼저 정하고 거기서 충전액을 역산.
3. ops 풀 월 예산.

- 단계 1: free 키를 일부러 포화시켜도 paid 워크스페이스 제출이 즉시 실행되는 테스트.
