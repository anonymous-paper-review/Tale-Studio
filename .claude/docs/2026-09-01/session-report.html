결제 시스템 준비 · 하루 작업 보고 · 2026-09-01

토이프로젝트가 돈 받을 준비를 시작한 첫날 — 무엇이 바뀌었고 무엇을 확인했나

아침까지 이 서비스는 코드를 고치면 곧바로 실서비스에 반영되고, 데이터베이스도 하나뿐이었습니다. 결제를 붙이려면 이 방식으론 안 됩니다. 오늘 하루 동안 바꾼 것과, 바꾼 게 실제로 작동하는지 잰 결과를 정리합니다. 개발 용어는 처음 나올 때마다 풀어 씁니다.

결론 먼저 — 실험실과 매장이 분리됐고, 영상 생성 엔진은 열쇠 2개 체제(동시 처리량 약 2배)가 됐으며, 돈의 장부(스키마)가 실서비스에 깔렸습니다. 단, 아직 결제 버튼은 없습니다 — 장부와 스위치까지가 오늘입니다.

2

실험실과 매장을 분리했다

결제가 붙으면 배포 실수가 곧 남의 돈 문제가 됩니다. 실험은 실험실에서, 손님은 매장에서.

용어부터

  • 브랜치(branch) — 코드의 작업 통로. main 통로에 올리면 실서비스로 배포되고, 오늘 만든 dev 통로에 올리면 연습용 화면으로만 배포됩니다.
  • CI(Continuous Integration) — 코드를 올릴 때마다 기계가 자동으로 돌리는 검사원. 우리는 타입 검사와 자동 테스트 1,700여 개를 돌립니다. 빨간불이면 뭔가 깨진 것.
  • 환경변수 스코프 — 비밀 열쇠(DB 접속 정보, 결제 키 등)를 배포 환경별로 나눠 담는 금고. 실서비스 금고와 연습용 금고가 섞이면 "테스트한다고 눌렀는데 실결제" 같은 사고가 납니다.
  • 마이그레이션(migration) — DB 구조 변경을 파일로 남겨 순서대로 적용하는 방식. "누가 언제 어떤 구조를 바꿨나"의 이력이 됩니다.

3

영상 생성 엔진 — 열쇠 1개에서 2개로

영상은 외부 생성 서비스(fal.ai)가 만듭니다. 계정마다 "동시에 몇 개까지"라는 한도가 있고, 오늘 $2,000을 충전한 새 계정이 생겨 두 계정을 합쳐 쓰기로 했습니다.

왜 그냥 열쇠만 바꿔 끼우면 안 되나

결정적인 제약이 하나 있습니다: fal에 맡긴 작업은 맡길 때 쓴 열쇠로만 결과를 조회할 수 있습니다. 다른 열쇠로 물어보면 "그런 작업 없음"이 돌아옵니다. 그래서 열쇠를 여러 개 쓰려면 작업 하나하나에 "어느 열쇠로 보냈나"를 기록해야 하고, 진행 확인·복구 코드 전부가 그 기록을 따라가야 합니다. 오늘 그 배선을 전부 깔았습니다.

  • 동시 상한(세마포어) — 동시에 굴러가는 작업 수의 뚜껑. fal은 한도를 넘겨도 거절하지 않고 말없이 줄을 세우기 때문에, 뚜껑은 우리 쪽에서 덮어야 "왜 안 나오지?"라는 침묵 대기를 막을 수 있습니다.
  • least-loaded 배분 — 새 작업을 두 열쇠 중 여유가 더 많은 쪽으로 보내는 방식.
  • 마진 — 계정 한도 40에서 6을 뺀 34까지만 쓰는 안전 여유. 아래 4절의 실측이 이 숫자의 역할을 정확히 밝혀줬습니다.

확정한 열쇠 배치

오너 결정 반영
열쇠쓰는 곳동시 상한

"개발 몫으로 6을 항상 비워둘까"도 검토했는데 폐지했습니다 — 손님 자리 6개를 상시 비워두는 확정 손실이고, 개발 작업이 그 자리가 필요할 확률은 밤 자동화 폐지 후 거의 0이기 때문입니다. 겹치면 개발 쪽이 잠깐 줄을 서면 됩니다. 손님보다 개발이 기다리는 게 맞습니다.

연습용 DB에 가짜 열쇠 2개를 물리고, 실제 DB 경쟁 상황을 만들어 쟀습니다. 생성 요금은 0원 — fal을 실제로 부르지는 않는 시험 설계입니다.

발견 — 초과 진입은 마진으로 못 막는다

마지막 줄이 이 시험의 진짜 수확입니다. 자리를 세어보고 넣는 두 동작 사이가 원자적이지 않아서(한 덩어리로 묶여 있지 않아서), 같은 순간에 도착한 요청 수만큼 상한이 뚫립니다. 마진 6은 이걸 막는 장치가 아니었습니다 — 실측으로 확인됐습니다.

그런데 지금 당장은 사고가 아닙니다. 초과의 결과는 오류가 아니라 fal 쪽 대기이고, 현재 트래픽(시간당 17개 안팎)에서 같은 순간 도착은 드뭅니다. 위험해지는 건 결제 이후입니다 — 크레딧 차감이 걸리면 이 구멍은 "대기"가 아니라 "과금 경쟁"이 됩니다.

그래서 고치는 시점을 크레딧 차감 기능(다음 단계)과 묶었습니다. 차감 자체를 DB가 한 덩어리로 처리하게 만들면(이 저장소에 이미 같은 패턴의 선례가 있습니다) 두 문제가 한 번에 닫힙니다. 추적 티켓: gen-quota-atomic-gate.

5

돈의 장부를 깔았다 — 은행 통장 방식

가격 정책(v4)의 크레딧 규칙을 DB 구조로 번역했습니다. 결제 버튼은 아직 없지만, 장부와 관리자 스위치는 오늘 실서비스에 들어갔습니다.

핵심 설계 — 왜 "잔액 칸"이 아니라 "장부"인가

원장(ledger)은 은행 통장과 같은 방식입니다. 잔액 숫자 하나를 고쳐 쓰는 게 아니라, 입금·출금을 한 줄씩 쌓고 잔액은 전부 더해서 구합니다. 이유는 4절의 실측과 직결됩니다 — 숫자 하나를 여럿이 동시에 고치면 반드시 깨지지만, 줄을 쌓는 방식은 동시에 써도 안전합니다. 환불로 잔액이 마이너스가 되는 경우도 줄 하나로 자연스럽게 표현됩니다.

  • lot 추적 — 출금 줄마다 "어느 입금분에서 깎였나" 꼬리표를 답니다. 가격 정책의 "구독분은 월말 소멸, 충전분은 12개월 유효, 무료분부터 먼저 소진" 규칙은 이 꼬리표 없이는 정확히 계산할 수 없습니다.
  • RLS(Row Level Security) — DB가 행 단위로 "누가 이 줄을 볼 수 있나"를 강제하는 자물쇠. 오늘 만든 장부 4개 테이블은 전부 자물쇠를 채우고 브라우저 쪽 열람 규칙을 하나도 안 만들었습니다 — 즉 사용자 브라우저에서는 원천적으로 접근 불가, 서버만 만질 수 있습니다.
  • 멱등성(같은 요청이 두 번 와도 결과는 한 번) — 결제 알림(웹훅)이 재전송돼도 크레딧이 두 번 적립되지 않도록, 알림 고유번호를 유일키로 잡는 자리를 미리 파뒀습니다.

검증 — 가짜가 아니라 진짜 DB로

7종 전부 통과

자동 테스트 32개(통과)와 별개로, 연습용 DB에 실제로 줄을 쌓아봤습니다: 50 적립 → 잔액 50, 관리자 회수 −20 → 잔액 30, 잘못된 부호의 줄은 DB가 스스로 거부(제약 규칙 작동 실측), 예약(hold)과 반환의 왕복 후 잔액 보존, 요금제 10단 사다리 수치 일치. 자동 테스트는 DB를 흉내로 대체하기 때문에, 이 실물 확인이 없으면 "코드와 실제 구조가 어긋나는" 사고를 못 잡습니다.

덧붙여 검수에서 설계 결함 하나를 배포 전에 잡았습니다 — 예약 반환(hold_release)의 부호가 차감으로 잘못 지정돼 있었고, 그대로 갔으면 다음 단계에서 예약 왕복이 DB 규칙에 막혔을 것입니다.

관리자 스위치(/api/admin/billing)로 이제 결제 없이도 특정 워크스페이스에 요금제를 부여하고 크레딧을 적립·회수할 수 있습니다. 모든 수동 조정은 사유(reason) 없이는 거부됩니다 — 돈을 만지는 권한에는 감사 기록이 따라붙어야 하기 때문입니다. 이 수동 경로는 나중에 국내 법인 계약(세금계산서 + 계좌이체) 경로로 재사용됩니다.

결정한 것, 미룬 것

확실한 것과 모르는 것

확실하다 — 재봤거나 배포돼 돌고 있다

  • 자동 테스트 1,749개 통과 · CI 초록 (dev·main 양쪽)
  • 연습용 DB는 실서비스와 수치 대조로 동일
  • 다중 열쇠 배선이 실서비스에 배포됨 (합산 상한 68)
  • 동시성 게이트 5종 정상 작동 (연습 DB 실측)
  • 장부의 제약 규칙이 실제 DB에서 작동 (7종 실측)
  • 세어보고-넣기 구멍의 크기: 동시 12명이면 12명 통과

모른다 — 이 보고서에 답이 없다

  • 새 fal 계정의 동시 한도가 정말 40인지 — 대시보드 표기 미확인
  • 실서비스 부하에서 두 열쇠 배분이 어떻게 굴러갈지 — 아직 트래픽이 작아 실전 검증 전
  • 결제 대행(MoR) 벤더 — 미선정, 수수료·한국 카드 승인률 비교 전
  • 베타 무료 사용자 이행 방침 — 오너 결정 대기
  • 가격 미결 숫자 3개 (계정 초과 단가 · 자동충전 상한 · 무료 크레딧 유효기간)
8

결론

  • 1. 실험실(dev 통로 + 연습용 DB)과 매장(실서비스)이 분리됐고, 검사원(CI)이 두 통로 모두를 지킨다.
  • 2. 영상 생성은 열쇠 2계정 합산 체제(동시 68)로 배포됐고, 작업마다 제출 열쇠가 기록되므로 조회·복구가 열쇠를 잃지 않는다.
