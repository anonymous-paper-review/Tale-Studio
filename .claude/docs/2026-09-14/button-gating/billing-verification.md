# Director 중복 차감 실제 DB 검증

2026-09-14, 개발 PostgreSQL의 임시 공간에서 검증했다. **같은 요청의 재전송을 막는 장치는 동작하지만, 원장 자체의 중복 차감 방어는 없다.** 같은 작업 번호로 5 Takes 차감을 두 번 요청하면 순차 요청과 동시 요청 모두 총 10 Takes가 빠졌다.

| 확인한 상황 | 실제 결과 | 판단 |
|---|---|---|
| 같은 작업 번호로 5 Takes 차감을 두 번 요청 | 총 10 차감, 잔액 100 → 90 | 원장 차감 함수 자체는 반복 요청을 막지 않는다 |
| 같은 작업 번호로 5 Takes 차감을 동시에 두 번 요청 | 총 10 차감, 잔액 100 → 90 | 잠금은 요청을 차례로 처리하지만 같은 작업인지는 확인하지 않는다 |
| 같은 요청키로 새 영상 생성을 동시에 두 번 예약 | 영상 1개·작업 1개, 한 요청은 기존 작업 재사용 | 동일 요청의 중복 예약 방어 확인 |
| 다른 요청키로 같은 샷의 새 테이크를 동시에 예약 | 영상 2개·작업 2개 | 서로 다른 새 테이크로 허용한다 |
| 위 두 작업에 각각 5 Takes 차감을 요청 | 총 10 차감 | 다른 키의 새 테이크를 같은 사용자 의도로 묶는 방어는 없다 |
| 같은 기존 영상의 재생성을 다른 키로 동시에 예약 | 1개 허용·1개 거절 | 같은 기존 영상의 겹치는 재생성은 DB가 막는다 |
| 같은 일괄 및 같은 항목을 다시 예약 | 같은 일괄·같은 작업 1개 재사용 | 동일 일괄 항목의 중복 예약 방어 확인 |
| 잔액 5에서 서로 다른 두 작업이 각각 5를 동시에 요청 | 한 작업만 5 차감, 다른 작업은 부족으로 거절 | 잔액 초과 방어 확인 |
| 지급분 2와 98에서 한 작업이 5를 요청 | 차감 행은 2개지만 합계는 5 | 정상 분할 차감을 중복으로 오판하지 않음 |

일반 Director 영상 제출 코드는 기존 예약을 재사용한 요청에 차감을 다시 호출하지 않는다(`src/lib/director/video-submit.ts`의 `!reservation.replayed` 조건). 따라서 **원장 함수의 취약점이 곧 일반 버튼 한 번의 이중 차감 사고라는 뜻은 아니다.** 같은 작업을 다시 차감하지 않도록 상위 호출 코드가 지켜 주는 구조라는 뜻이다.

다른 탭에서 진행 상태가 전달되기 전에 같은 샷의 **새 테이크**를 각각 요청하면 요청키가 달라질 수 있다. 이번 DB 실험에서 그 조건의 두 예약이 허용됨을 확인했다. 기존 영상의 재생성과 새 테이크 생성을 구분해야 한다.

## 검증한 범위

- 원본 SQL 함수 8개를 읽어 실행했다. 함수 본문은 가짜 구현으로 바꾸지 않았다. 스키마 이름과 공용 용량 잠금 이름만 임시 공간으로 한정했다.
- 실행한 8개 함수 본문은 실제 개발 DB의 함수 본문과 모두 일치했다.
- 동시 요청 실험은 서로 다른 PostgreSQL 접속·트랜잭션 두 개를 사용했다. 둘 다 같은 잠금 앞에서 기다리는 것을 확인한 뒤 동시에 진행시켰다. 접속 번호·트랜잭션 번호·관측 결과를 JSON에 남겼다.
- 차감 호출은 잔액 부족을 차단하는 `enforce=true`로 실행했다. 관리자 면제 경로를 사용하지 않았다.
- 기존 개발 테이블의 정의·인덱스·검사 제약을 복제했다. 고객 행, 외부 테이블을 참조하는 외래키, 무관한 트리거와 인증 정책은 복제하지 않았다. 검증 대상의 원본 용량 트리거는 임시 공간에 적용했다.
- **API 전체·브라우저 두 탭·외부 유료 생성은 실행하지 않았다.** 예약 재사용 실험의 0 차감은 예약 함수 자체에 차감이 없기 때문이다. 이를 실제 영상 생성이 무료라는 의미로 읽으면 안 된다. 다른 키 실험의 총 10 차감은 반환된 두 작업에 실제 차감 함수를 명시적으로 호출해 확인한 결과다.
- 운영 환경의 활성 과금 모드와 고객의 실제 중복 차감 이력은 조회하지 않았다.

## 검증 결과와 정리

8개 검증이 실행 완료됐다. 여기서 통과는 관측 절차와 보호되는 동작이 맞았다는 뜻이며, 위 두 중복 차감 관측이 안전하다는 뜻이 아니다. 결과 JSON에는 이 두 경우를 `safe: false`로 남겼다.

임시 스키마와 시험 데이터를 전부 제거했다. 개발 DB 공용 함수 28개의 실행 전후 지문이 같았다. 고객 데이터 쓰기 0건, 운영 쓰기 0건, 유료 생성 요청 0건이다.

- 재실행: `node tests/manual/director-double-charge.verify.mjs`
- 상세 원본 관측: `billing-verification.json`
- 첫 실행기의 메타데이터 쿼리 오류와 정상 정리 증거: `billing-verification.attempt-1.json`
- 실행 전 한국어 동작 목록: `billing-verification-plan.md`

제품 코드와 과금 정책은 변경하지 않았다. 확인된 취약점을 고치려면 별도 변경과 회귀 검증이 필요하다.
