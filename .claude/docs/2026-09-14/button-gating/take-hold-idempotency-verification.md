# Director Take 차감·반환 보완 결과

동일 작업의 차감을 다시 요청해도 한 번만 차감하도록 보완했다. 개발 DB의 임시 공간에서 실제 SQL을 실행한 20개 테스트가 모두 통과했다. 같은 테스트를 기존 함수에 실행했을 때에는 17개가 실패했고 3개가 통과했다. 실패한 테스트의 기대를 바꾸지 않았다.

| 확인한 동작 | 기존 함수 | 보완 후 |
| --- | --- | --- |
| 같은 작업의 5 Take 차감을 동시에 두 번 요청 | 총 10 차감 | 총 5 차감, 한 요청은 기존 처리 반환 |
| 첫 차감으로 잔액이 0이 된 뒤 같은 요청 재전송 | 잔액 부족으로 거절 | 추가 차감 없이 기존 성공 반환 |
| 같은 작업에 다른 금액·다른 작업공간 요청 | 추가 차감 | 예외로 거절, 추가 차감 0 |
| 차감 재전송과 반환이 경쟁 | 5 Take가 다시 차감된 채 남음 | 차감 5·반환 5, 잔여 차감 0 |
| 과거 중복 차감 20 중 6이 반환된 작업 반환 | 추가 반환 4에 그침 | 미반환 14를 모두 반환 |
| 차감 확정 전에 실패·반환이 먼저 도착 | 반환 0 뒤 차감 5가 남음 | 확정된 5를 전액 반환 |
| 실패 처리 중 늦게 도착한 최초 차감 | 차감 허용 | 실패 확정 후 거절 |

분할 지급분의 여러 원장 행은 정상적인 한 번의 차감으로 계산했다. 반환의 동시 재호출, 완료 작업의 기존 차감 재전송, 없는 작업·종료된 작업의 신규 차감 거절, 실패 후 새 작업의 정상 차감, 잔액 한도 경쟁, 환불·만료한 지급분 제외, 지급분 없는 한도 미적용 차감도 함께 통과했다.

반환 기록이 있는 작업은 다시 차감할 수 없다. 완료된 작업에 기존 차감이 있으면 같은 금액 재전송은 성공으로 돌려준다. 최초 차감은 대기 중인 실제 작업에만 허용한다. 작업별 잠금과 작업 행 잠금을 차감·반환 양쪽에 적용했고, 작업공간 잠금 이후 기존 환불·만료 잔액 계산과 지급분 배분을 유지했다.

기존 고객 원장은 자동 보정하지 않는다. 과거 중복 차감 작업에 반환 함수가 호출되면 그때 해당 작업의 미반환 총액을 반환한다. 새 요청키로 별도 생성 작업 두 개를 만드는 문제는 이 SQL의 범위 밖이며, 같은 작업에 대한 반복 차감과 반환만 보호한다.

검증 환경은 개발 프로젝트의 임의 이름 스키마이며, 고객 행을 읽거나 복사하지 않고 합성 작업·지급분만 넣었다. 테스트 전후 public 함수 28개의 지문이 같고, 두 실행 모두 임시 스키마 삭제를 확인했다. 유료 생성 요청·운영 DB 쓰기·public 데이터 쓰기는 0이다. 기존 함수 3개가 개발 DB 본문과 일치함도 확인했다. 이 검증에서 개발·운영의 실제 함수를 교체하지 않았다.

근거: `take-hold-idempotency.before.json`은 기존 함수 관측과 실패 종료를, `take-hold-idempotency.after.json`은 보완 함수의 동일 테스트 통과를 보존한다. 기존 `billing-verification.json` 감사 결과는 그대로 두었다. 새 테스트 파일의 ESLint와 전체 TypeScript 검사도 통과했다.

재현:

```sh
node tests/manual/take-hold-idempotency.verify.mjs --baseline
node tests/manual/take-hold-idempotency.verify.mjs
```

첫 명령은 보완이 필요한 동작을 증명하므로 실패 종료가 정상이다. 두 명령 모두 검증 결과 JSON을 갱신하고 임시 공간을 제거한다.
