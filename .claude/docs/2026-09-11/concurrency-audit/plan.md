- 기준 커밋: `867cda835195315e6a73cb4f8d262ef736302ff9`.
- 비교 설정: 가짜 fal 연결 두 개에 각각 34 또는 40, 합계 68 또는 80.

## 시나리오와 판정

1. 사용자마다 1·2·3·4·6·9개를 순차 접수한다. 전체 한도까지 통과하고 이후에는 거절하는지, 완전 수용 인원과 일부 수용 인원을 측정한다.
2. 영상 3개와 이미지 6개가 개인별로 구분되며, 전체 한도는 합산하는지 검증한다.
3. 마지막 한 칸을 여러 사용자가 같은 시점에 확인하고 12개를 제출한다. 전체 한도를 넘으면 현재 전역 상한 약속의 실패로 기록한다.
4. 빈 두 계정의 작업 수를 50개 요청이 동시에 확인한다. 한 계정으로 몰리는지와 계정당 설정·물리 40칸 기준 초과량을 기록한다. 외부 실행 결과는 추정이며 실제 fal 실행으로 표시하지 않는다.
5. 기존 사용자가 완료 직후 재신청하고 새 사용자가 그다음 신청하는 순서를 12회 반복한다. 새 사용자가 계속 거절되는지 관측한다. 공평한 순서는 현재 구현된 약속이 아니므로 신규 정책을 임의로 확정하지 않는다.
6. 집계 오류, 30분이 지난 미완료 작업, 관리자 예외에서 실제 집계·접수 결과를 관측한다.
7. 기존 영상 일괄·러프·Artist 관련 회귀 검사를 메인에서 실행하고, 포화 시 사용자에게 보이는 재시도·중단·대기 상태를 코드와 대조한다.
8. 개발 DB의 고유 임시 스키마에서 실제 PostgreSQL 영상 한도 트리거를 실행한다. 사용자 영상 2개 + 동시 12개 요청은 1개만 추가되어야 한다. 이미지와 전역 한도는 같은 경쟁에서 보호되는지 별도로 판정한다.

## 증거 수준

- 제품 함수 검사: 실제 메인의 집계·쿼터·키 선택 함수를 실행한다. DB 저장 경계와 인증·외부 생성 클라이언트만 가짜 값으로 대체한다. 장벽으로 같은 읽기 결과를 보는 요청 간 순서를 재현한다.
- 실제 SQL 검사: 개발 DB의 별도 스키마에서 실제 마이그레이션의 이름 공간만 변경해 독립 세션 경쟁을 실행한다. 운영 전체 스키마와 네트워크·생성 속도 검증은 아니다.
- 코드 추적: 자동 재개 및 화면 안내 경로의 존재를 확인한다. 실제 브라우저 클릭 검증과 구분한다.
- 실패한 약속의 기대값은 결과에 맞춰 바꾸지 않는다. 코드 수정 없이 실패와 영향을 보고한다.
- 결과물: 실행 가능한 테스트·실행기, 원시 JSON/로그, 한국어 결과 보고서.

## 이번 검사로 확정하지 않는 것

fal의 실제 처리 시간·현재 계정 티어·특정 모델의 추가 한도·웹 서버와 DB의 최대 처리량·실제 사용자의 대기 시간 분포·화면 품질은 측정하지 않는다. 68/80칸 계산은 운영 전체의 동시접속 보장 인원이 아니다.
