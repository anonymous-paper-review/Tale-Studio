# 68칸·80칸 동시성 검증 결과

2026-09-11 · 메인 `867cda83` · 실제 생성 요청 0건 · 운영 설정 변경 0건

**68칸을 80칸으로 늘리면 계산상 용량은 17.6% 늘지만, 접수 초과·계정 쏠림·사용자별 대기 편차는 해결되지 않습니다.** 순차 접수에서는 설정을 지켰지만, 동시에 요청하거나 초안을 묶음으로 생성할 때 엄격한 상한을 보장하지 못하는 경로를 재현했습니다.

앞서 대화에서 말한 “7명에게 9개씩”은 계산상 수용량입니다. 개인 한도와 전체 한도가 지켜지고 용량이 골고루 배분된다는 가정이며, 현재 제품에서 7명의 생성 속도·대기 시간을 보장한다는 뜻은 아닙니다.

## 1. 계산과 순차 접수 검증

두 계정에 각각 34 또는 40칸을 설정한 메인 함수를 실행했습니다. 아래 인원은 각자의 요청을 모두 동시에 접수할 수 있는 인원이며, 남은 칸으로 다음 사람의 일부 작업을 받을 수 있습니다.

| 한 사람의 동시 작업 | 68칸 | 80칸 | 증가 |
|---|---:|---:|---:|
| 9개: 영상 3 + 이미지 작업 6 | 7명, 5칸 남음 | 8명, 8칸 남음 | 1명 |
| 6개 | 11명, 2칸 남음 | 13명, 2칸 남음 | 2명 |
| 4개 | 17명 | 20명 | 3명 |
| 3개 | 22명, 2칸 남음 | 26명, 2칸 남음 | 4명 |
| 2개 | 34명 | 40명 | 6명 |
| 1개 | 68명 | 80명 | 12명 |

12개 비교 모두 순차 접수 결과가 계산과 일치했습니다. 두 계정의 최종 배분도 34/34 또는 40/40이었습니다. 이 검사는 작업 수를 확인하며, 영상과 이미지의 처리 시간 차이는 측정하지 않았습니다.

## 2. 요청이 몰렸을 때

| 시나리오 | 68칸 설정 | 80칸 설정 | 제품에서 중요한 점 |
|---|---|---|---|
| 마지막 한 칸에 서로 다른 12명 요청 | 67 → **79개 접수**, 11개 초과 | 79 → **91개 접수**, 11개 초과 | 남은 수를 확인하는 순간과 접수하는 순간 사이에서 경쟁 발생 |
| 빈 두 계정에 50명이 함께 요청 | **50개 / 0개** 배분 | **50개 / 0개** 배분 | 합계 용량이 남아도 한 계정으로 몰릴 수 있음 |
| 한 사용자의 이미지 5개 진행 중, 12개 동시 요청 | **17개 접수** | **17개 접수** | 이미지 개인 상한도 동시 진입에서 엄격하게 지켜지지 않음 |
| 한 칸 남았을 때 Artist 인물 2 + 배경 2 초안 | 67 → **71개 접수**, 3개 초과 | 79 → **83개 접수**, 3개 초과 | 실제 초안 함수가 용량을 한 번 검사한 뒤 4개를 제출 |
| 기존 사용자들이 자리가 날 때마다 먼저 재신청, 12회 반복 | 기존 12개 / 신규 **0개** | 기존 12개 / 신규 **0개** | 공통 사용자 대기순서가 없어 재신청 시점이 결과를 좌우 |

동시 요청 검사는 모든 요청이 작업 수를 읽은 뒤 새 작업을 기록하도록 실행 순서를 고정했습니다. **발생 가능한 경쟁을 재현한 것이며, 실제 트래픽에서 그 경쟁이 발생하는 빈도를 측정한 것은 아닙니다.** 순서를 반대로 한 대조군에서는 신규 사용자가 접수되고 기존 사용자가 거절됐습니다. 기존 사용자라는 신분을 우대하는 규칙이 있는 것이 아니라, 먼저 재요청한 쪽이 칸을 차지합니다.

“50개 / 0개”는 앱의 계정 선택 결과입니다. fal에서 두 계정이 각각 40개를 실행할 수 있다고 가정하면 첫 계정의 10개는 외부 대기를 겪을 수 있다는 계산이 나오지만, 실제 fal에 보내서 측정한 대기 수는 아닙니다.

**초안의 중간 초과 수용과 키 선택 함수의 비예약 방식은 메인에 이미 명시된 동작입니다.** 이 결과들은 엄격한 상한이라는 진단 기준을 충족하지 못함을 보여줍니다. 모두 새 회귀 버그이거나 이미 합의한 제품 약속 위반이라고 단정하지 않습니다.

## 3. 실제 DB에서 확인한 방어선

개발 DB에 별도 임시 공간을 만들고, 메인의 영상 한도 SQL을 이름 공간만 바꾸어 실행했습니다. 실제 사용자 데이터는 복사하지 않았습니다. 독립 DB 세션 12개가 같은 수를 읽은 뒤 동시에 저장하도록 했습니다.

| 시나리오 | 저장 / 거절 | 최종 진행 작업 |
|---|---:|---:|
| 한 사용자의 영상 2개 + 영상·미리보기 혼합 12개 | **1 / 11** | **3개** |
| 한 사용자의 이미지 5개 + 이미지 12개 | 12 / 0 | **17개** |
| 전체 67개 + 서로 다른 사용자 12명 | 12 / 0 | **79개** |
| 전체 79개 + 서로 다른 사용자 12명 | 12 / 0 | **91개** |
| 진행 영상 3개 중 하나 완료 후 다음 영상 | **1 / 0** | **3개** |

영상은 실제로 12개 요청이 같은 잠금을 기다리는 것을 관측했고, 최종 3개를 지켰습니다. 이미지·전체 한도는 이 영상 트리거에서 최종 방어하지 않았습니다. 실제 제품 쿼터 함수에서도 이미지·전역의 같은 읽기 경쟁이 통과한 결과와 연결됩니다.

이는 **최소 가짜 테이블 + 해당 메인 트리거**의 실제 SQL 검사입니다. 운영 전체 스키마나 인증부터 생성 완료까지의 전체 HTTP 경로를 실행한 검사는 아닙니다. 임시 공간 삭제 및 공용 함수 28개의 지문 불변을 확인했습니다.

## 4. 고객이 겪는 대기는 화면마다 다르다

| 고객 행동 | 혼잡할 때 | 자동 재개 |
|---|---|---|
| Writer 러프 전체 생성 | 대기하고 다시 확인 | 화면이 열려 있을 때 약 8초 간격, 최대 40라운드 |
| Writer 러프 개별 버튼 | 이번 요청 종료 가능 | 개별 요청 자체의 재시도 루프 없음 |
| Artist 인물·배경 개별 생성 | 안내 후 이번 요청 종료 | 다시 시도해야 함 |
| Artist 자동 채움 | 해당 항목 종료 후 다음 항목 처리 | 같은 항목을 자리가 날 때 자동 재접수하는 공통 대기열 없음 |
| Director 실사보드 일괄 | 일괄 루프 중단 | 용량 초과용 자동 재시도 없음 |
| Director 영상 개별 생성 | 대기 표시로 되돌리고 이번 요청 종료 | 용량 초과용 자동 재시도 없음 |
| Director 영상 일괄 생성 | 서버에 남은 작업을 대기로 보관 | 완료 알림 또는 2분 주기 복구에서 재개 |

따라서 영상 일괄 사용자는 완료 직후 다음 작업을 자동으로 요청할 기회가 있지만, Artist나 개별 영상 사용자는 다시 눌러야 합니다. 러프 사용자는 화면을 닫으면 브라우저의 대기 루프도 끝납니다. 이런 차이가 별도 우선순위 설정 없이도 체감 우선순위로 나타날 수 있습니다.

서버 초안이 처음부터 혼잡으로 건너뛰어지면 인물·배경 이미지가 비고, 이후 영상 제작에 필요한 선행 이미지 준비도 늦어질 수 있습니다. 위 화면 경로는 코드 추적과 관련 회귀 검사로 확인했으며, 이번에 브라우저에서 직접 재현한 것은 아닙니다. 상세 근거: [제품 경로별 확인](product-paths.md).

## 5. 80칸을 전부 쓰기 전에 판단할 것

이번 결과상 우선순위는 다음과 같습니다. 이는 정책 제안이며 제품에는 적용하지 않았습니다.

1. **접수할 작업 수만큼 칸을 먼저 확보한다.** 한 칸을 여러 요청이 함께 통과하거나, 한 칸 확인 후 네 개를 접수하는 경로를 함께 다뤄야 합니다. 전체 용량뿐 아니라 계정별 배분에도 같은 문제가 있습니다.
2. **혼잡할 때 접수된 대기인지, 다시 눌러야 하는지 경험을 일관되게 정한다.** 화면 안내와 실제 재개 방식이 맞아야 합니다.
3. **기다리는 사용자별로 다음 작업을 어떤 순서로 시작할지 정한다.** 영상 일괄의 자동 재신청과 신규 사용자의 첫 작업이 경쟁하는 기준이 필요합니다.
4. **그다음 68·80에서 실제 생성 시간과 대기 시간을 비교한다.** 현재 결과는 빈자리 확보와 접수 순서를 검증한 것이며, fal 처리 속도나 웹 서버 처리량 검증은 아닙니다.

현재처럼 계정당 40칸을 전제하면 68 설정은 합계 12칸의 여유를 둡니다. 80 설정은 이 여유를 없애지만 초과 접수와 계정 쏠림은 그대로입니다. 따라서 **숫자를 80으로 바꾸는 것만으로 더 많은 사람에게 안정적인 생성 경험을 보장할 근거는 얻지 못했습니다.**

개발 환경이 운영과 같은 fal 계정을 계속 공유한다면 개발 작업은 운영 DB의 작업 수에 잡히지 않는다는 추가 변수가 있습니다. 계정 공유는 이전 운영 문서에 기록돼 있으며 이번 실험에서는 현재 개발 키 설정을 재조회하지 않았습니다.
