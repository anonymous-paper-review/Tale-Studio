# 측정 시나리오 — Director · Writer

2026-08-26 기준. "완료됐는데 화면에 안 뜬다"가 실재하는지, 실재하면 어느 단계에서 끊기는지를
장부 데이터로 가리기 위한 절차다. 오너가 평소처럼 쓰면서 밟으면 된다.

부검 명령은 하나다:

```
node scripts/generation-autopsy.mjs <projectId>
```

projectId 는 스튜디오 주소창의 `?projectId=` 뒤 문자열. 읽기 전용이라 아무것도 바꾸지 않는다.

## 무엇이 기록되는가 (좌표 4개)

| 좌표 | 언제 남나 | 없으면 무슨 뜻인가 |
|---|---|---|
| 제출 거부 | 동시 생성 한도에 걸려 시작조차 못 함 | — (있으면 한도 문제) |
| 잡 생성 | 요청이 fal 에 접수됨 | 요청이 나가지 못함 |
| 잡 완료·실패 | fal 이 끝냄 | 결과가 안 돌아옴 |
| 화면 반영 | 결과가 화면 상태에 실제로 들어감 | **완료됐는데 화면에 안 뜬 것** |

배선 위치: Director 캔버스(스토리보드·노드 뷰), Writer 러프 스토리보드. 두 곳 모두 2026-08-26에 깔았다.

## Director 측정

### D-A. 화면을 띄운 채 기다린다 (가장 값진 데이터)

1. Director 탭 진입, 스토리보드 뷰
2. 샷 2~3개 이미지 생성 (또는 영상 1개)
3. **화면을 그대로 두고** 완료될 때까지 기다린다. 브라우저를 최소화하거나 다른 앱을 봐도 된다 — 그건 "화면 밖"이 아니다
4. 이미지가 카드에 뜨는지 눈으로 확인. 안 떴으면 **시각과 샷 번호를 메모**

판정: 여기서 부검에 `완료·미반영`이 나오면 **진짜 반영 버그로 확정**. 볼 사람이 있었는데 안 떴다는 뜻이므로 다른 해석의 여지가 없다.

### D-B. 탭을 다녀온다 (네가 겪던 그 패턴)

1. Director에서 생성 시작
2. 생성 중에 Writer 또는 Artist 탭으로 이동
3. 30초~1분 뒤 Director로 복귀
4. 스피너가 계속 도는지 / 결과가 떴는지 확인

판정: 여기서 나온 `완료·미반영`은 (a) 진짜 버그일 수도, (b) 완료 순간 Director 화면이 없어 보고할 주체가 없었을 수도 있다. **이동한 시각을 메모**해야 구분된다.

### D-C. 새로고침 중간에 끼워넣기

1. Director에서 여러 샷 생성 시작
2. 생성 중에 F5로 새로고침
3. 복귀 후 스피너가 되살아나는지 확인

판정: 스피너가 안 살아나면 진행 표시 복원(queue-restore) 문제. 결과는 나중에 뜨는데 스피너만 없다면 표시 계층만의 문제로 좁혀진다.

### D-D. 한도 안내 확인 (과금 최소)

1. 이미지를 7개 이상 한꺼번에 생성 시도 (유저당 이미지 동시 한도 6)
2. 7번째에서 **"이미지는 동시에 6개까지"** 토스트가 뜨는지 확인
3. 영상 생성을 곧바로 시도 → 이미지 한도와 무관하게 **영상은 별도 3개**까지 되는지 확인

판정: 토스트가 안 뜨면 무음 삼킴이 남아 있는 것. 부검의 `거부` 항목에 건수가 잡히는지도 대조한다.

## Writer 측정

Writer는 러프 스토리보드가 대상이다. 2026-08-26에 화면 반영 배선을 넣어 Director와 같은 기준으로 잴 수 있게 됐다.

### W-A. 러프 보드 생성 후 화면 유지

1. Writer 탭 → 러프 스토리보드
2. 빈 패널이 있는 샷 3개 정도 생성
3. 화면을 그대로 두고 패널이 채워지는지 확인

판정: D-A와 동일. 미반영이면 진짜 버그.

### W-B. 탭 왕복

1. 러프 생성 시작 → Artist 또는 Director로 이동 → 복귀
2. 스피너 유지 / 결과 반영 확인

### W-C. "재생성 불가" 재현 (A1 미해결 건)

네 리포트의 재현 조건을 그대로 밟는다:

1. 러프 보드에서 축소 버튼(-)을 눌러 패널을 가장 작게 만든다
2. 그 상태로 생성 시작
3. **썸네일을 클릭하지 않은 채** 다른 탭에 다녀온다
4. 복귀 후 그 샷을 재생성해본다 — 버튼이 안 먹는지 확인

판정: 재현되면 그 순간의 시각·샷 번호를 메모. 이게 A1의 남은 절반이고, 재현 절차만 확보되면 바로 고칠 수 있다.

## 결과 읽는 법

부검 출력에서 볼 것:

- `[거부] N건` — 한도에 걸려 시작 못 한 생성. 많으면 한도 상향 또는 대기열 전환 필요
- `[완료] N건 — 반영 있음 X / 없음 Y` — Y가 0이 아니면 반영 문제 실재
- `완료→화면반영 지연` 중간값 — 수 초면 정상. 수십 초면 폴링 주기(4초) 밖의 지연이라 재수화 경로를 봐야 한다
- `[실패] N건` — 사유가 `[finalize]`로 시작하면 fal 은 성공했는데 우리 저장 단계에서 죽은 것

## 알려진 한계

- 화면 반영 보고는 **해당 화면이 떠 있는 동안 완료된 잡**만 남는다. Director를 떠나 있는 사이 완료된 잡은 보고 주체가 없다 — D-B에서 시각 메모가 필요한 이유다.
- 보고 시점은 "스토어 반영 완료"까지다. 데이터가 반영됐다는데 눈에는 안 보이는 경우(리액트 렌더 문제)는 이 배선으로 구분되지 않는다. 그런 사례가 나오면 이미지 로드 시점 보고를 한 겹 더 얹는다.
- 2026-08-26 저녁 배선 설치 **이전** 데이터는 전부 `미반영`으로 나온다. 그 이전 기록은 무시할 것.

# A2 통제 실측 — 93% 완료 전환 (2026-08-26 23:45~23:52 KST)

## 조건 정정

앞선 기록의 "Writer 탭 왕복" 표현은 틀렸다. Writer 파이프라인 생성 화면은 탭 뷰를 전면
대체하므로 그 상태에서 러프·트리트먼트·대사 탭 전환이 불가능하다. 오너의 실제 행동은
**브라우저를 최소화하거나 뒤 탭으로 보낸 채 다른 작업**한 것이다.

## 실측 방법

fal·LLM 비용 없이 테스트 프로젝트의 최신 `writer_runs` 행을 통제했다.

1. 실제 API가 `running`, 13/14 → 화면 93%를 표시하게 함
2. 장부만 `completed`, 14/14로 전환
3. 새로고침 없이 화면이 완료 상태로 바뀌는지 측정
4. 테스트 행 3개는 종료 후 모두 삭제

## 추가로 닫은 구멍

첫 수리는 `visibilitychange`·`focus` 때 즉시 재조회하는 것뿐이었다. 오너 지적대로 화면을 계속
