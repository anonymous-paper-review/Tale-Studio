## 관찰 메모

- G1+G2: I2V 입력 프레임 쌍의 시간 간격 설계 문제 — 프롬프트에 "샷 길이 n초, 그 사이 변화량" 개념이 없음.
- G4+G5: 씬 시간대(현재/과거)와 캐릭터 버전(현재 옥화/젊은 옥화) 매핑이 프롬프트 조립에 반영 안 됨 — 캐릭터 레퍼런스 선택 로직.
- G3: 스타일 앵커를 최초 1회만 주입 → 긴 체인에서 희석. 재주입 지점 설계.

## 논의 필요 항목

1. **G1 속도 개념의 형태**: (a) 샷 길이에서 자동 계산, (b) 샷별 속도 필드(느림/보통/빠름) 노출, (c) 둘 다(자동+수동 오버라이드). 오너가 조절하고 싶은지가 관건.
2. **G4 캐릭터 버전 모델**: "젊은 옥화"를 별도 캐릭터로 볼지, 옥화의 "시대 변형(variant)"으로 볼지 — 데이터 구조 결정이라 A/B 이후라도 빨리 정해야 함. variant 모델이면 씬의 시간대 태그로 자동 선택 가능.
3. **G7 대사 파이프라인**: 대사를 어디서 확정하나 — Writer 스크립트의 대사를 I2V 프롬프트+TTS에 흘리는 경로 설계. 음성 생성과의 순서.
4. **품질 검증 방법**: 프롬프트 변경 전후 같은 입력으로 비교 세트를 만들어 오너 판정 받는 절차 (실험 규칙 `.claude/rules/experiments.md` 적용).

## 진행 (2026-08-27)

### G1·G2 — 닫힘. 긴 샷이 동작을 늘여 슬로우모션이 되던 것

**문서의 추정이 절반 틀렸다.** "프롬프트에 샷 길이 개념이 없다"고 적었는데, 카메라 절은
이미 `durationSeconds` 를 받아 "N초에 걸쳐 고르게"를 말하고 있었다. 길이를 안 보는 건
**피사체 절**이었다:

```
cameraClause(motion, durationSeconds)   ← 길이 있음
subjectClauses(dyn)                     ← 길이 없음
```

실측(테스트 프로젝트 14샷):

| 샷 | 길이 | magnitude | 나가던 문장 |
|---|---|---|---|
| `sh_01_01` | **10초** | small | "a small, restrained movement" |
| `sh_02_04` | **5초** | small | **똑같음** |

10초에 작은 동작 하나면 화면이 거의 멈춘다. 같은 동작을 10초에 펴는 것 — 그게 오너가 본
슬로우모션이다.

**수리 원칙: magnitude 를 임의로 키우지 않는다.** 그건 연출 의도이고 앱이 바꿀 게 아니다.
대신 "이 길이 안에서 무엇이 완결돼야 하는가"를 말한다.

- 긴 샷(≥7초) + 작은 동작 → 여파를 이어가게 한다(무게 이동·호흡·옷자락, never freeze)
- 긴 샷 pace → "자연스러운 속도로. N초를 채우려고 느리게 하지 마라. 본동작은 끝나기 전에
  완결되고 남은 시간은 여파가 채운다"
- 짧은 샷 → 기존 문장 그대로. 문제 없던 경로는 건드리지 않는다
- 큰 동작 → 긴 샷이어도 여파 문구 안 붙임(이미 화면을 채운다)

G2(First/End 프레임 시간 간격)는 같은 뿌리라 함께 닫힌다 — 본동작 완결 시점이 앞당겨지면
END 프레임이 도착 상태가 된다.

실제 계약문 비교(같은 spec, 길이만 다름):

```
5초  … "a small, restrained movement". Pace the motion across the full 5-second duration …
10초 … "a small, restrained movement" — then let its aftermath carry the remaining time
      (weight settling, breath, cloth and hair still moving); never freeze after it lands.
      Timing: perform each scripted movement at natural, lifelike speed — do NOT slow it
      down to fill 10 seconds …
```

회귀 잠금: `tests/motion-contract-duration.test.ts`(6) — 짧은 샷 불변·magnitude 무조작·
결정론까지 잠근다.

> **판정 경계**: 헌법대로 결과물의 좋고 나쁨은 오너만 판정한다. 이 수리는 비교 재료를
> 만든 것이지 "좋아졌다"는 주장이 아니다. 같은 샷을 재생성해 전/후를 보면 판정할 수 있다.

### G3 — 확인 필요. 코드와 증언이 어긋난다

오너 증언: "스타일 앵커가 처음 입력되고 추후 입력되지 않는데 앵커 중간에 삽입해야".

코드를 보면 실사 생성 경로에 앵커가 **매번** 배선돼 있다 (`generate-storyboard-batch`,
`generate-storyboard`, `generate-video` 전부 `resolveStyleAnchor`):
스타일 절 + 참조 이미지(최대 2장) + 앵커별 검증 절까지 실린다(`#anchor-wiring`, 2026-08-14 오너 확정).

즉 "처음만 들어간다"는 지금 코드와 맞지 않는다. 가능성 둘:
1. 오너가 겪은 8-26 시점 이후 이미 고쳐졌다
2. 앵커는 들어가는데 **효과가 약하다**(프롬프트 내 위치·비중 문제)

2번이면 프롬프트 조립 순서를 봐야 하는데, 이건 결과물을 봐야 판정 가능하고 그건 오너 영역이다.
**다음 행동**: 같은 샷을 지금 코드로 재생성해 오너가 "일본풍이 실렸나"를 판정 → 안 실렸으면
프롬프트 내 앵커 위치·비중 조정.

참고: 러프 스토리보드에 앵커가 없는 것은 **설계다**(결함 아님). 러프는 흑백 연필 스케치로
고정돼 있고(`PANEL_STYLE_BASE`), 여기 실사/일본풍 앵커를 넣으면 러프의 목적이 깨진다.
