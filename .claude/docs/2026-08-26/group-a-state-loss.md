## A1 최종 — "하나는 재생성 불가" 원인·수리 (2026-08-27 13:20~13:30 KST)

### 재현

오너 리포트의 "패널 최소화 + 썸네일 미클릭"은 **증상이 나타난 정황**이었고, 실제 방아쇠는
**그 샷을 막고 있던 queued 잡**이었다. 통제 재현(fal 과금 없음):

1. 한 샷(`sh_02_03`)에 queued 상태의 잡을 심는다 — 웹훅 유실로 좀비가 된 잡과 같은 상태
2. 사람이 명시적으로 재생성을 누른다 (`force: true`)
3. 서버 응답: **HTTP 200 · `ok: true` · 제출 0건 · `skipped: [{reason: "in_flight"}]`**
4. 화면: 스피너만 계속 돌고 아무 안내 없음 → 사용자 눈엔 "눌러도 반응 없음 = 재생성 불가"

`evidence/a1-01-stuck-spinner.png` — Shot 3만 영구 스피너로 굳은 상태.

### 원인 — 네 겹의 사슬

| # | 지점 | 문제 |
|---|---|---|
| 1 | 라우트 가드 순서 | `in_flight` 검사가 `force`보다 먼저라, 사람이 눌러도 skip |
| 2 | 좀비 잡 | 웹훅 유실로 queued 가 안 풀리면 그 샷이 영구 차단 |
| 3 | 회수 실패 | fal 404 의 `message` 가 빈 문자열 → 종결 가드("evidence must be nonblank")에 걸려 좀비가 안 죽음 |
| 4 | 클라 무음 | `no_info` skip 만 스피너를 정리하고, `in_flight` skip 은 알리지도 풀지도 않음 |

3번이 특히 고약하다 — 좀비를 청소하려고 만든 경로가 **정작 그 좀비 앞에서 죽는다.**
`STALE_QUEUED_MS`(10분) 자동 제외만 남아, 그 전까지는 사람이 몇 번을 눌러도 조용히 막혔다.

### 수리

- **서버**: `force` + 특정 샷이면, 막고 있는 잡을 fal 진실로 회수한 뒤 판정한다.
  좀비면 여기서 종결돼 같은 요청 안에서 재생성이 통과한다. 회수는 무거우므로 1회 4건 상한.
- **회수**: 종결 사유를 `describeFinalizeError` 로 합성 — `message` 가 비어도 `name`·`status` 가
  남아 가드를 통과한다. (부수 효과: 다른 실패도 사유에 HTTP status 가 붙어 부검이 쉬워짐)
- **클라**: 클릭 유래(`force`) 요청이 전부 막히면 낙관적 스피너를 풀고 이유를 말한다 —
  "패널 n개는 앞선 생성이 아직 끝나지 않았어요. 잠시 후 다시 눌러주세요."
  자동 경로는 그대로 조용하다(진짜 생성 중인 샷의 표시를 지우면 안 되므로).

### 검증

같은 요청이 수리 전후로 갈렸다.

```
수리 전: 제출 0 | skip [{shotId: sh_02_03, reason: in_flight}]
수리 후: 제출 1 | skip []        ← 좀비 잡은 failed 로 종결(ApiError: (status 404))
```

회귀 잠금: `tests/rough-regenerate-inflight-block.test.ts` (8) — 가드 순서·회수·증거 합성·
클라 안내·자동 경로 무음을 각각 잠근다. 전체 typecheck · 1492 tests 통과.

### 남은 갈래 — "생성 눌러놓은 게 초기화"

A1 원문의 앞쪽 절반은 이번에 재현되지 않았다. 어제 A2 에서 고친 복귀 재수화·폴링 자가복구가
같은 뿌리를 이미 덮었을 가능성이 크다(둘 다 "스테이지를 떠난 사이 상태를 잃는다"). 재발하면
`ui_reflected` 배선과 장부 부검으로 바로 분류할 수 있으므로 별도 열린 항목으로 남기지 않는다.

### 한도 실측 (2026-08-26 저녁, 과금 0)

가짜 진행 중 행(이미지 6 + 영상 4, `reserved:` 표식)을 장부에 심고 테스트 계정 세션으로 실서버 호출:

- 이미지 요청 → 429 "image limit (6/6)" / 같은 상태에서 영상 요청 → 429 "video limit (4/3)" — 서로의 풀에 오염되지 않음(분리 실증). 관측 이벤트 2건 정확히 기록. 흔적 전부 삭제.
- **측정 범위 명시: 이것은 우리 서버 문지기(429)의 검증이다. fal에는 요청이 1건도 가지 않았다.** fal은 동시 한도를 넘어도 실패를 내지 않고 자기 큐에 태운다(대기가 길어질 뿐). 즉 "fal에서 몇 건에 터지나"라는 측정 대상은 실패 건수가 아니라 "동시 실행 슬롯 수"다.

### fal 동시 실행 슬롯 실측 (2026-08-26 저녁, 오너 승인 실험, 실제 과금 약 $0.85)

도구: `scripts/fal-slot-probe.mjs` (우리 서버 게이트를 거치지 않고 fal 큐에 직접 제출 → 전원 상태 폴링).

| 시도 | 모델 | 건수 | 결과 | 판정 |
|---|---|---|---|---|
| 1차 | flux-2/klein/9b ($0.006) | 22 | 건당 1.2초로 3초 만에 전부 종료, 폴링 2틱 | **측정 실패** — 첫 틱에 이미 11건 완료라 동시 최대치 과소집계(관측 9는 무의미) |
| 2차 | openai/gpt-image-2 ($0.03) | 24 | 제출 거부 0건, **24건 전원이 1.3초 만에 동시 실행 진입, 대기 0**, 건당 76.8초, 전원 완료 | **슬롯 ≥ 24 확정** |
| 3차 (천장 탐색) | openai/gpt-image-2 ($0.03) | 40 | 제출 거부 0건, **40건 전원이 1.5초 만에 동시 실행 진입, 대기 0**, 건당 76.4초, 전원 완료 | 슬롯 ≥ 40 (당시엔 천장 미도달로 판단) |
| 4차 (천장 확정) | openai/gpt-image-2 ($0.03) | 60 | 제출 거부 0건, **41건 실행 + 19건 대기**(대기 최대 139.5초), 전원 완료(총 223초) | **천장 = 40 확정** — 관측 41은 폴링 경계 오차 |

확정된 사실:
- **fal은 초과분을 거부하지 않는다.** 60건을 한꺼번에 던져도 제출 실패·429가 0건이고, 넘친 19건은 대기줄에 서서 앞 작업이 끝나는 대로 순차 실행돼 전부 완료됐다. "몇 건에서 터지나"는 성립하지 않는 질문이고, 정확한 모델은 **"넘긴 만큼 뒷사람이 기다린다"**이다.
- **계정 동시 실행 한도 = 40.** 60건 실험에서 처음으로 대기가 관측됐고(41 실행 / 19 대기), 오너가 fal 대시보드에서 본 표기($500 충전 = 30건, $1000 충전 = 40건)와 일치한다. 즉 이 한도는 고정 슬롯이 아니라 **충전액 연동 티어**다.
- 코드 주석의 "fal 슬롯 20" 가정은 **틀렸다(과소)**. 그 위에 세운 MAX_GLOBAL_INFLIGHT_JOBS=18은 실측 천장의 절반도 안 되는 보수치라 산 슬롯을 크게 놀리고 있었다.
- **대기 비용의 실측치**: 넘친 19건은 최대 139.5초를 기다렸다. 전역 상한을 두는 이유가 이것이다 — 상한이 없으면 A 유저의 배치 뒤에 선 B 유저의 첫 요청이 2분 넘게 대기한다.

확정되지 않은 것:
- 모델별·플랜별 차이 여부. 측정은 gpt-image-2 한 모델 기준이다.
- 이 실측은 **동시 실행 가능 여부**만 본 것이다. 동시 40건이 실제 프로덕션에서 안전한지는 별개 — fal 과금 속도, 우리 서버의 webhook 처리량, Supabase 쓰기 부하가 함께 걸린다.
- 충전 잔액이 줄어 티어가 30으로 내려가는 시점. 그때 34는 fal 큐로 4건이 새므로 재검토가 필요하다.

> **결정 brief (2026-08-26)**
> 오너: 전역 상한 18 → **34** (실측 천장 40 − 마진 6). 유저당 상한은 영상 3·이미지 6 유지.
> 마진을 옛 2보다 크게 잡은 이유는 티어가 충전액에 연동돼 잔액에 따라 40 → 30으로 내려갈 수 있기 때문이다.
> 40에 딱 붙이면 티어 하락 즉시 대기가 길어지고, 34면 그 경우에도 초과분이 4건에 그친다.
> 재측정은 `scripts/fal-slot-probe.mjs`로 하되 실제 과금이 발생하므로 오너 승인이 필요하다.
> 이번 실험 총 비용: 4회 합계 약 $3.9.

# 백로그 (그룹 A에서 갈라져 나온 것 — 닫지 않음)


**대기열 2단계 — 우리가 줄을 갖는다**
- 지금(1단계): 상한에 걸린 요청은 fal 큐에 들어가지도 못하고 429로 되돌아온다. 유저가 직접 다시 눌러야 한다.
- 2단계: 요청을 pending 으로 받아두고 슬롯이 나면 서버가 자동 승격 → "대기 3번째" 표시. 취소도 가능해진다.
- 3단계: 실측 실행시간(이미지 76초 기준)으로 예상 시간까지. 편차가 커서 2단계 안착 후에 얹는다.
- 이유: 대기 순번·예상 시간·공정성(유저 라운드로빈)·취소는 전부 **우리가 줄을 갖고 있을 때만** 가능하다.
  fal 큐에 다 맡기면 슬롯은 채우지만 순번을 못 보여주고, 취소가 불가능하며, 큐 진입 시점에 과금이 확정된다.
- 묶어서 처리할 것: C2(영상 생성 끊김) · H3(전체 생성 + 진행바)

기타 백로그:
- 거부→대기열 전환: 자리가 나는 시점은 우리 DB로 추적 가능하므로 "자리 나면 자동 시작"까지 기술적으로 열려 있음. C2 해소·H3(전체 생성+진행바)의 기반. 오너 판단으로 보류
