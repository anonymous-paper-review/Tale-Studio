캐릭터 데이터 구조 · 2026-08-27~28

같은 사람의 다른 시절을 한 카드에 담기 — 왜 안 됐고, 무엇을 고쳤나

"젊은 옥화"가 옥화와 무관한 인물로 앉아 있었습니다. 이걸 파고들다 사물이 사람 자리에 들어가던 별개 사고까지 같은 뿌리에서 나온 걸 확인했고, 캐릭터의 겉모습을 저장하는 자리를 따로 만들었습니다.

결론 먼저 — 구조는 옮겼고 화면 전환까지 확인했습니다. 다만 새 구조로 실제 이미지를 다시 뽑아본 적은 없습니다. 생성 버튼은 실제 과금이라 누르지 않았습니다.

1

알고 싶었던 것

이번 작업은 질문 세 개에서 출발했습니다. 전부 오너가 던진 것입니다.

  • "젊은 옥화가 왜 옥화와 안 닮나." 같은 인물의 과거인데 다른 사람처럼 나옵니다.
  • "화면에서는 카드가 하나 더 생기나, 아니면 묶이나."
  • "시점을 현재·과거·미래 셋으로만 나눠도 되나. 외부 변수가 있을지 모르겠다."

세 번째 질문이 특히 중요했습니다. 데이터 구조를 잘못 잡으면 나중에 갈아엎어야 하는데, 지금은 실제 회상 장면 데이터가 하나도 없어서 미래에 뭐가 올지 모르는 상태로 결정해야 했습니다.

2

맞춰야 할 조건 — 일곱 개 전부

판정하려면 조건을 먼저 빠짐없이 적어야 합니다. 오너가 대화에서 확정한 것들입니다.

조건내용
① 연속성젊은 옥화는 기존 옥화를 바탕으로 만들어져야 한다"젊은 옥화라는건 옥화가 있고 그 옥화를 바탕으로 만들어져야 연속성이 보존된다"
② 카드 묶기별도 카드를 추가하지 말고 옥화 카드 안에서 묶는다
③ 소품 분리사물은 사람과 별개 테이블로 옮긴다
④ 모습 분리시절·의상 변형도 별개 테이블로 만든다
⑤ 데이터베이스 기본기관계·인덱스·중복 방지 같은 표준 요소를 갖춘다"db설계할때 내가 아예 몰라서 (…) 보편적인 정답으로 고려해줄 수 있을까"
⑥ 러프한 시점현재·과거·미래 셋이면 충분하되 예외 상황을 견딜 것
⑦ 조명과 분리낮·밤을 뜻하는 time_of_day에 서사 시점을 섞지 않는다

①번이 실제로 어떤 상태였나

같은 프로젝트 안에 두 인물이 서로 아무 관계 없이 나란히 있었습니다. 각자 자기 모델시트 — 정면·측면·표정을 한 장에 모은 캐릭터 도면 — 를 갖고 있습니다.

옥화 — 현재 40대 중반. 베이지·크림 계열 한복, 팔레트도 같은 계열.
젊은 옥화 — 별도 인물로 등록됨 20대 초반. 흰 저고리·검정 치마, 팔레트가 갈색·붉은색 계열.

왜 닮을 수가 없었는지 — 구조가 막고 있었습니다

시트를 만드는 코드가 참조 이미지로 넣을 수 있는 건 자기 자신이 이미 갖고 있는 시트뿐이었습니다. 다른 캐릭터를 참조로 건네는 경로가 아예 없었습니다.

젊은 옥화는 옥화를 한 번도 본 적이 없는 상태로 생성됐습니다. 나이 설정만 다르게 준 완전히 독립된 인물이었던 겁니다. 얼굴이 안 닮는 게 당연합니다.

닮았는지 아닌지의 최종 판정은 오너 몫입니다. 이 문서가 말할 수 있는 건 참조 경로가 없었다는 구조적 사실과 위 두 그림에서 눈에 보이는 차이(의상 색, 팔레트 구성)까지입니다.

3

파고들다 발견한 고장 여섯 개

하나를 고치려다 같은 뿌리에서 나온 것들이 줄줄이 나왔습니다. 순서대로 적습니다.

① 사물이라는 표시가 중간에 사라졌다

별개 사고의 진짜 원인

이전에 엿판(엿 파는 판)이 얼굴 없는 사람으로 그려져 아기를 안은 그림이 나온 적이 있습니다. 응급처치로 걸러내는 코드를 넣어뒀는데, 이번에 진짜 원인을 찾았습니다.

producer가 "엿판 = 사물"이라고 넘김
   ↓
캐스트 변환 단계에서 그 표시를 버림   ← 여기서 끊김
   ↓
샷 설계 단계는 누가 사물인지 모름
   ↓
"사물은 소품 칸에 넣어라"라고 부탁만 함
   ↓
모델이 안 지킴 → 엿판이 인물 자리에 → 아기로 그려짐

코드 주석에 그대로 적혀 있었습니다 — "person/object 구분 없이 모두 StoryCharacter 로 싣는다". 부탁은 확률이고 변환은 결정론입니다. 확률에 안전을 맡기고 있던 겁니다.

② 화면 탭은 보여주기만 했다

덮어쓰기 위험

카드 안에 시절 탭을 먼저 붙였을 때, 탭은 어떤 그림을 보여줄지만 바꿨습니다. 생성·저장 쪽은 여전히 "캐릭터 + 뷰" 두 개로만 자리를 구분하고 있었습니다.

즉 젊은 시절 탭에서 다시 만들기를 누르면 현재 옥화의 시트·후보·저장 파일을 덮어쓸 수 있는 상태였습니다. 읽기 전용 점검에서 잡았고, 실제로 눌러보지는 않았습니다.

③ 쓰기만 옮기고 읽기는 옛 칸에 남았다

비대칭

겉모습 저장 위치를 새 테이블로 옮겼는데, 읽는 쪽 일부가 옛 칸을 계속 봤습니다. 새로 만든 시트가 저장돼도 화면과 내보내기에는 안 보이는 상태입니다.

특히 위험했던 건 최종 스토리보드와 영상 생성이었습니다. 인물 참조 이미지가 통째로 빠진 채 실제 과금이 발생하는 요청이 나갈 수 있었습니다.

④ 새 인물이 겉모습 없이 생길 수 있었다

불변조건 붕괴

기존 데이터는 옮겼지만, 새로 인물을 만드는 경로 다섯 곳이 여전히 옛 방식으로 저장하고 있었습니다. 그대로 두면 겉모습이 하나도 없는 인물이 생기고, "기본 모습은 정확히 하나"라는 전제가 바로 깨집니다.

⑤ 소품이 다시 사람 테이블로 들어올 수 있었다

재발 경로

소품 6개를 옮겨놓고도, 인물을 만드는 API가 여전히 사물도 같은 테이블에 넣을 수 있었습니다. ①번 사고가 재발할 통로가 열려 있던 셈입니다.

⑥ 시점을 저장할 자리만 만들고, 만들어 달라고 하지 않았다

마지막에 발견

서사 시점을 저장하는 칸과 그걸로 모습을 고르는 규칙까지 다 만든 뒤에 발견했습니다. 정작 이야기를 만드는 단계에 "시점도 같이 내놔라"라고 요구하지 않고 있었습니다.

타입 검사만 통과하면 넘어가는 구조라, 실제로 돌렸으면 값이 비어 저장 직전에 멈췄을 겁니다.

4

무엇을 바꿨나

여섯 개를 순서대로 닫았습니다. 조건별 대조는 이 절 끝에 있습니다.

데이터 구조 — 신원과 겉모습을 갈랐다

characters              사람의 이름·역할·서사 정보 (신원)
  └ character_appearances   그 사람의 시절·의상·시트·얼굴 (겉모습)

옥화는 이제 모습 두 개를 가집니다. 현재(기본)와 젊은 시절입니다. 나중에 의상이나 상태가 추가돼도 같은 층에 얹히지, 무관한 인물이 새로 생기지 않습니다.

표준 요소 — ⑤번 조건에 대한 답

넣은 것안 넣었으면 생기는 일
관계와 삭제 규칙옥화를 지워도 "젊은 옥화 모습"이 주인 없이 떠돎
사람이 읽는 열쇠로 연결코드가 매번 내부 식별자를 되찾아야 함코드가 실제로 쓰는 쪽을 세어봤습니다 — 문자열 열쇠 11곳, 내부 식별자 0곳
인덱스 4개데이터가 쌓일수록 조회가 느려짐. 연결 칸에 자동 생성되지 않습니다
"기본 모습은 하나뿐" 규칙코드로만 막으면 한 군데만 빠뜨려도 뚫림
빈 값 차단오류 없이 이상한 결과만 나옴 — 가장 찾기 어려운 종류
수정 시각 자동 기록손으로 넣으면 반드시 어딘가 빠뜨림
읽기 권한 정책남의 프로젝트 데이터가 노출됨

권한 정책은 처음 작성분에 빠져 있었습니다. 저장소 규칙과 대조하다 잡아서 추가했습니다.

현재·과거·미래 — ⑥번 조건에 대한 답

셋이면 충분합니다. 단 시점 이름을 모습 이름으로 쓰지 않는 조건에서입니다.

상황어떻게 처리되나

자동 화면 점검은 완료되지 않았습니다

미완

프로젝트에 있는 자동 화면 점검 명령은 화면을 확인하기 전 단계에서 스크린샷 도구 자체가 실패했습니다. 대신 브라우저를 직접 열어 렌더와 탭 전환을 확인했습니다. 둘은 같은 것이 아닙니다 — 자동 점검은 콘솔 오류와 여러 화면을 한 번에 훑지만, 직접 확인은 제가 본 화면 하나뿐입니다.

작업 중 사고 하나

복구됨

병렬로 돌린 작업 하나가 격리된 작업 폴더가 아니라 공유 폴더에 변경을 썼습니다. 되돌리기 명령을 일절 쓰지 못하게 막고, 변경 내용만 따로 보존한 뒤 원래 폴더에 수동으로 다시 붙였습니다. 공유 쪽 다른 작업은 그대로입니다.

결론

  1. 젊은 옥화가 옥화와 안 닮은 것은 설정 문제가 아니라 다른 인물을 참조로 넘기는 경로가 없던 구조 문제였습니다.
  2. 엿판이 사람으로 그려지던 별개 사고도 같은 뿌리였습니다 — "이건 사물"이라는 표시가 중간에서 사라지고 있었습니다.
  3. 사람의 신원과 겉모습을 갈라 저장하고, 소품은 사람 테이블 바깥으로 뺐습니다. 운영 데이터베이스에서 겉모습 161행·소품 6행으로 이동을 마쳤습니다.
  4. 현재·과거·미래 셋이면 충분합니다. 단 시점 이름을 모습 이름으로 쓰지 않고, 애매하면 오류를 내는 조건에서입니다.
  5. 과거가 여러 시절로 늘어나도 구조는 그대로 둡니다. 그 장면에만 정확한 모습을 지정하면 됩니다.
  6. 화면에서는 옥화 카드 하나 안에서 현재와 젊은 시절이 전환되는 것을 확인했습니다.
  7. 새 구조로 이미지를 다시 뽑아본 적은 없습니다. 연속성이 실제로 생기는지는 시트 한 장을 뽑아 오너가 판정해야 알 수 있습니다.

근거로 쓴 것 — 운영 데이터베이스 직접 조회(8개 항목), 자동 시험 1,561개 통과 기록, 타입 검사 통과, 브라우저에서 연 화면과 탭 전환, 위 두 모델시트 원본, 코드 읽기 점검 4건.

이 문서가 하지 않는 것 — ① 새 구조로 이미지를 생성해보지 않았습니다. 연속성 판정은 아직 없습니다. ② 이야기 생성을 실제로 돌리지 않았습니다. 시점 값이 잘 나오는지는 규칙과 시험으로만 확인했습니다. ③ 회상 장면이 실제 데이터에 0건이라 과거 모습 자동 선택이 실전에서 도는 것을 본 적이 없습니다. ④ 자동 화면 점검이 도구 오류로 완료되지 않았습니다. ⑤ 그림의 좋고 나쁨은 판정하지 않습니다 — 오너 몫입니다.
