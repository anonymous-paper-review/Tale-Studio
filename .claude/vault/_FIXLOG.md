# 프로덕션 수리 원장 — 상시

**프로덕션에서 실제로 관측된 사고**만 모은다. 사고 하나 = 항목 하나이고, 항목은 `검증` 칸이
확인될 때까지 열려 있다. 코드가 고쳐졌다는 것만으로는 닫히지 않는다.

- 이 파일은 날짜 파일이 아니라 **살아 있는 원장**이다. 닫힌 항목은 잘라내 `_archive/_FIXLOG-closed.md`로 옮긴다
  — 여기 남은 것은 전부 아직 열려 있는 것이다.
- **커밋 메시지를 복제하지 않는다.** 코드로 귀결된 것은 diff 와 커밋 본문이 진실이다. 여기 적는 것은
  git 이 담지 못하는 것뿐 — 사고→원인→수리 커밋의 **연결**, 데이터 수리·오너 액션의 **진행 상태**,
  배포 후 확인할 **검증**, 미착수 처방의 **상태 전이**.
- **코드 수리 ≠ 사고 종결.** 대부분의 수리는 향후 생성만 보호한다. 이미 만들어진 데이터가 어떤
  상태인지를 따로 적고, 그것까지 정리돼야 닫는다.
- **경계**: 한 사고에서 갈라져 나온 미착수 처방은 사고를 쪼개지 않기 위해 그 항목 안에 남긴다.
  사고와 무관하게 결정된 미착수 작업은 `_DEFERRED.md`, 결론이 없는 논제는 vault 날짜 파일의 `## 3. 미결`.

## 폼

```
### F-NNN · <한 줄 제목>   `상태: 수리됨|부분수리|백로그|오너대기`
- **증상**: 프로덕션에서 무엇이 관측됐나 (프로젝트·샷·잡 id 등 실측 좌표와 함께)
- **원인**: 확정된 기전 — `파일:줄`. 노출을 만든 커밋이 있으면 그것도
- **수리**: 수리 커밋 + 그 수리가 **무엇까지 보호하는가** (대개 "향후 생성만")
- **데이터**: 이미 만들어진 데이터가 어떤 상태인가 — 소급 가능/불가, 오너 대기 중인 행동
- **검증**: 무엇이 확인되면 이 항목을 닫는가 (배포 후 실측 항목)
- 기록: YYYY-MM-DD
```

### F-003 · 런 중 채팅 병행 초안 — 비정본 인물 id 혼입   `상태: 부분수리` ★ 오너 승인 대기

  붙었다. 파이프라인 산출이 아니라 writer 채팅 에이전트가 CRUD(`writer-store.addShot`)로 만든 **별개

  같은 `sh_XX_NN` 모양을 공유) ② design_ref/spec 전무 → 하류에서 **설계 없음으로 확정**

  오너가 관찰한 "인물 asset 이 아예 안 들어감"은 ②+③ 두 결손의 합이다.
- **원인**: 세 갈래는 "이 16샷은 다른 생성 경로가 만들었다"는 한 원인의 가지다. ①은 표시상 비일관,
  ②는 설계상 정상(수동 샷엔 원래 provenance 가 없다). **진짜 결함은 ③** — `writer-chat-updates.ts:57-58,
  88-89` 의 `asStringArray` 는 모양만 보고 정본 대조를 하지 않는다. 방어가
  `api/writer/chat/route.ts:29` 의 프롬프트("Never invent new IDs") 뿐이었다. `.claude/rules/architecture.md`
  §3·§4 위반(모델 출력의 무검증 실행). **회귀가 아니다** — 2lane·대사병렬·shotcheck-gate 어느 것도
  이 파일들을 건드리지 않았고, 개편 이전에도 동일하게 재현됐을 사고다.
- **수리**: **입구만 닫혔다.** `731f859`(`#run-chat-gate`)가 파이프라인 실행 중 writer 채팅을 LLM 없이
  결정론 즉답으로 막는다(`src/components/layout/global-chat.tsx:519-531, 543-551`).
  남은 백로그 3건 — 셋 다 미착수:
  - **R1 인물 id 화이트리스트 (제품 레이어)** — 최우선. `validateWriterUpdates` 에 정본 id 집합을
    주입해 미승인 id 를 드롭하고, 기존 `skipped` 채널로 사용자에게 표면화(침묵 드롭은 같은 함정을
    다시 판다). 로스터는 **DB 가 진실** — 클라가 조립해 보내는 `writerContext` 를 믿지 않는다.
    (미검증 추정: 사고 당시 클라 컨텍스트의 인물 로스터가 비어 있어 모델이 id 를 발명했을 가능성.
    요청 본문이 어디에도 저장되지 않아 사후 확인 불가.)
  - **R2 store 레벨 가드** — 현재 게이트는 **UI 한 곳**이고, `current_status='awaiting_confirmation'`
    (씬 게이트 대기) 창은 **의도적으로 열려 있다**. 경로 전체를 닫으려면 `applyChatUpdates` 진입부에서
    활성 런을 확인해야 한다(`writer_runs.status` 로 파생 — 새 상태를 만들 필요 없음).
  - **R3 persist DELETE 범위** — persist 는 프로젝트의 **모든** shots 를 지우고 다시 넣는다. 이번엔
    persist(07:14:33)가 채팅(07:14:58)보다 **먼저**라 16샷이 살아남았다. 순서가 반대였다면 통째로,
    조용히 사라졌을 것이다. 근본책은 `shots.source`(`'pipeline'|'manual'`)를 두고 자기 소유 행만
    지우게 하는 것. R2 는 "런 중"만 막고 R3 는 "런이 나중에 또 돌 때"까지 막는다 — 둘 다 필요하다.
  - (R4 id 축 통일은 **착수하지 않는다** — 충돌 없는 표시상 비일관이고, 기존 행의 `shot_id` 개명은
    `rough_storyboard`·`generation_jobs`·director 노드가 참조하므로 **금지**.)
- **데이터**: `dc531572` 인물 id 정본화(**A안**: `girl`→`char`, `tracker`→`kingdom_hunters`; shots 16행 +
  scenes 4행) — **오너 승인 대기**. 16샷을 지우고 8씬으로 재실행하는 B안은 오너가 이미 director
  단계까지 끌고 갔으므로 비권장(그 뒤 작업이 전부 날아간다). 실행 전 `dialogue_lines[].characterId`
  에도 같은 비정본 id 가 있는지 **확인 필요**(초안 SQL 은 그 컬럼을 건드리지 않는다).
  `design_ref` 임의 부착은 **절대 금지** — 옆 샷 설계를 훔치는 F-002 의 원 사고를 그대로 재현한다.
- **검증**: R1 배송 후 ① 채팅이 미승인 인물 id 를 뱉었을 때 드롭되고 사용자에게 사유가 보이는지
  ② `shots.characters` 에 `characters` 테이블 밖 id 가 **새로** 생기지 않는지(주기 점검).
  데이터는 A안 실행 후 `NOT (characters <@ 정본배열)` 카운트가 0 이면 닫힘.
  R2 는 **씬 게이트 대기 중** 채팅 수정 시도가 거부되는지, R3 는 재persist 후 수동 샷이 살아남는지로
  각각 확인한다.
