# 배경 뷰 시트 vs 3D — "배경이 많다"의 단위와 승격 판정 설계 — 세션 기록

> 세션 2026-08-10. 다음 세션에서 "배경 레퍼런스/뷰 시트/3D 뷰어 도입"을 이어갈 때 먼저 읽는다.
> 원칙: 실측만 기록. 같은 날 카메라 계약 트랙([[2026-08-10-prompt-contract-audit]])과 판정 프레임을 공유한다.

## 0. 한 줄 요약

"배경(3D 공간의 2D 스냅샷) 때문에 3D 뷰가 필요한가"를 종료 프로젝트 실데이터로 검증했다.
실측 결론: **배경 수요의 단위는 로케이션도 샷도 아닌 "뷰 클러스터"(로케이션당 5~8개, 씬 넘어 반복)**이고,
previz 배경은 현재 무방어(같은 법정이 씬마다 딴 건물 — 시각 증거 확보)라 **재방문 일관성이 이미 깨져 있다**.
아이디어의 심장은 3D 뷰어가 아니라 "샷이 로케이션이 아닌 특정 뷰를 참조한다"는 스키마이며,
순서는 I2I 뷰 시트 먼저 → 구조 실패 시 3D 승격. 승격 게이트(G1/G2/G3) 설계까지 왔고 bar 숫자 확정이 미결.

## 0.5 기원 — 오너 통찰 원문

> "로케이션 헌팅을 하고 특정 세계(장소)를 많이 구성한다기보다 그 세계에서 어떤 각도의 '배경'이 많이 필요한가가 중요함"
> "배경 돌리는 건 컨시스턴시 없어도 되지 않나?" / "배경이 많다?라는 개념을 정의해야 됨"

응답 요지: 실측이 첫 문장을 정확히 지지(안 쓰이는 로케이션 실존, 뷰 수요는 데쿠파주가 사후 확정).
둘째 질문은 컨시스턴시를 3성분으로 쪼개면 해소(§2 결정 b). "많다"의 단위는 뷰 클러스터(§2 결정 a).

## 1. 실측 발견 — 안 통한 시도 포함

- **배경 수요 실측 (Sample1 116샷/14씬/로케 5 + w260810 23샷/4씬/로케 2)**:
  - 로케이션 수는 2~5로 작고, 무거운 로케이션에 샷이 몰린다(법정 54샷/6씬, 폐허 도시 23샷/4씬).
  - 샷별 배경 서술(framing.layers.background)은 사실상 샷 수만큼 유니크(법정 51/54) — 그러나 키워드 클러스터링하면 **판사석 7 · 벽 22 · 방청석 7 · 천장 4 · 디테일 12 = 한 공간의 5~8개 뷰를 씬마다 재서술**한 것.
  - tight 샷(28/54)의 배경 서술 다수가 "blurred/out-of-focus" — 판독 가능한 플레이트 실수요는 wide+mid 24샷 → 5~8뷰로 수렴.
  - 같은 뷰가 씬을 넘어 반복(판사석 정면 축: sc6·7·9·10).
- **로케이션 헌팅 낭비 실존**: producer가 정의했으나 씬 매핑 0인 로케이션이 양쪽 프로젝트에 각 1개(Sample1 "회상", w260810 "오아시스 왕국").
- **previz 배경 무방어 (시각 증거)**: 같은 명목 뷰(판사석 정면 WS/eye_level)를 sc6/7/9/10에서 나란히 봤더니 **목재 전통 법정 → 시민회관풍 → 기둥 고전 법정 → 미니멀** — 씬마다 다른 건물. producer wide_shot(백색 대리석 미니멀)과도 전부 다름. 원인은 코드로 확정: previz는 패널별 독립 T2I + 배경은 `Background:` 텍스트 1줄, 로케이션 wide_shot은 previz ref 목록에 없음(batch ref = [러프 그리드, 캐릭터, 스타일 앵커]). **인물은 이중 방어(마네킹 규칙+view_main ref), 배경은 무방어** — 비대칭.
  - 재현 좌표: 프레임은 shots.rough_storyboard.frames.start (shot_id: sh_06_39/sh_07_49/sh_09_67/sh_10_76, project 9d6efa6d), ref는 locations.wide_shot.
- **로케이션 이미지 현황**: 전 로케이션 wide_shot 1장 존재, establishing_shot 컬럼은 전부 null — "로케이션당 정면 와이드 1장"이 배경 진실의 전부.
- **오너 전제 하나 교정**: "모든 장면(스냅샷)을 여러 개 만들어 놓을 수 없어서" → 실측상 수요는 무한이 아니라 **유한(5~8뷰)하고 사전 계산 가능** — v4 static_spec(camera_angle×shot_type×framing)이 이미 '플레이트 발주서'다. 아무도 발주서로 안 읽고 있었을 뿐.
- **드라마투르그와의 합류 실측** ([[2026-08-10-dramaturgy-world-derivation]]): 유도 무대가 기관·계기 공간(관측소/브리핑실/공동구)으로 쏠림 = 랜드마크 밀한 실내 = same-room 판정이 가장 어려운 클래스. 유도가 "적은 무대 × 깊은 재방문"으로 수렴시키므로 **드라마투르그가 성공할수록 재방문 일관성(G1)의 지분이 커진다.**

## 2. 결정 — 코드로 귀결 안 된 것만

### D-2026-08-10-c: "배경이 많다"의 단위 = 뷰 클러스터
- 상황: 배경 인프라(뷰 시트/3D) 설계에 수요 단위 정의가 필요했음
- 결정: 단위는 **로케이션당 판독 가능한 뷰 클러스터 수**(실측 5~8, 재방문 가중). 로케이션 수(공급자 단위, 안 쓰이는 것 포함)도 샷별 배경 서술 수(같은 뷰의 재서술 노이즈)도 아니다.
- 기각한 대안: 로케이션 수 기준(너무 굵음) / 샷 수 기준(너무 잘음)
- 감수하는 것: 클러스터 경계는 자동 확정 불가 — 오너 수동 클러스터링 1회가 규격 확정 절차(미결 1)

### D-2026-08-10-d: 컨시스턴시 3성분 분해 — 돌리기는 자유, 재방문은 저장 문제
- 상황: "배경 돌리는 건 컨시스턴시 없어도 되지 않나?"에 정밀 답이 필요했음
- 결정: ⓐ **재방문 일관성**(같은 뷰 복귀 시 같은 공간 — 필수, 단 생성 기술이 아니라 **뷰의 자산화+재사용**으로 해결) ⓑ **인접 뷰 기하 정합**(약한 요구 — 영화도 치팅, 오버랩/무빙에서만) ⓒ **스타일·조명 연속**(필수지만 style anchor+v3로 기처리). 새 각도 첫 생성은 ⓑ 수준 자유, 두 번째 방문부터 첫 결과를 ref로.
- 기각한 대안: 컨시스턴시를 단일 축으로 취급 — 이유: ⓐ와 ⓑ의 요구 강도가 정반대라 뭉치면 과잉/과소 설계
- 감수하는 것: ⓑ를 대충 하면 팬/트래킹이 뷰 경계를 넘는 샷에서 티가 남 (실측상 그런 무빙 1~5%·계약 압축 후 — [[2026-08-10-prompt-contract-audit]] G3)

### D-2026-08-10-e: 심장 = shot.view_ref 스키마, 3D는 뷰 생성기 중 하나 — I2I 먼저
- 상황: "3D view에서 카메라 각도 잡아 ref 만들고 previz 샷 재생성" 아이디어의 심사
- 결정: 삭제 테스트 결과 심장은 **"샷이 로케이션(1장)이 아니라 로케이션의 특정 뷰를 참조한다"는 참조 단위 변경**. 3D 뷰어는 뷰 생성기의 한 구현(다른 구현: wide_shot에서 I2I 멀티뷰 파생). 순서: I2I 뷰 시트 먼저 → G1/G2 구조 실패 시 3D 티어 승격(최소 티어부터: depth/splat 재투영 → 블록아웃 → 풀 3D). "3D에서 입력받아 샷 하나 재생성"은 §5 명시적 재생성 패턴과 정합하되 **오버라이드 경로**(기본은 static_spec 각도→뷰 자동 매칭 — 116샷 스케일에서 수동 카메라는 노동 폭발).
- 기각한 대안: 3D 뷰어 선도입 — 이유: 뷰-자산 저장 없으면 재방문 일관성이 또 깨짐(3D여도 스냅샷을 자산화 안 하면 동일 문제)
- 감수하는 것: I2I 파생 뷰의 기하 정합은 미검증 — 그게 실험(미결 3)

### 판정 프레임 (공유): 승격 신호 = 실패의 형태
- [[2026-08-10-prompt-contract-audit]] D-2026-08-10-b가 정본 — 재시도 비수렴(구조 실패)만 승격 근거, 판정축 자격 = "3D가 구조적으로 고치는 것만"(G1 방 정체성 블라인드 분류 / G2 각도 이행 판독 대조 / G3 무빙 수요). G3는 DB 감사로 선닫힘(1~5%) 후 캡 완화 변수로 이관됨.

## 3. 미결 — 열린 논의

- 질문: **뷰 클러스터 경계 확정** — 법정 54샷의 배경 서술 51개를 오너가 직접 클러스터링해 몇 개로 잘리는지 확인 (내 키워드 클러스터 5~8은 근사). 닫히는 조건: 오너 수동 클러스터링 1회 → 뷰 시트 규격 확정.
- 질문: **승격 bar 사전 등록** — "구조 실패 뷰에 걸린 샷 비율"(재방문 가중) 상한 20% 제안 + 리트라이 예산 2회. 오너가 "재방문율 20%"로 오독했던 지표명은 "실패 뷰에 걸린 샷 비율"로 개명 합의. 닫히는 조건: 오너가 두 숫자 확정 (실험 전 필수 — 사전 등록 원칙).
- 질문: **뷰 시트 실험 (I2I 레인)** — 법정 wide_shot 1장 → 클러스터 뷰 5장 I2I 파생 → sc6/7/9 판사석 샷 재생성(뷰 ref 부착) → 재방문 일관성 blind 비교. 기각 조건 후보: 파생 뷰가 방 정체성 유지 실패(→3D 신호) or 실사 ref가 러프 모노크롬 스타일 오염. 닫히는 조건: 가설 폼 작성+실행. 판정 방법은 [[2026-08-06-previz-verifier]] 판정 3원칙 재사용(blind 방 묶기 + distractor).
- 질문: **3D 티어 매핑** — G1 실패→depth/splat 프록시부터, G2 계통 실패→해당 각도 계열만 depth 재투영, 풀 3D는 최후. 닫히는 조건: 뷰 시트 실험의 실패 형태 관측.
- 질문: **최종 생성(V6)의 배경 ref 흐름** — 타입 주석상 location 에셋(wide_shot 1장)이 전 각도 샷에 같은 ref로 들어가는 구조로 보이나 **미검증**(이번 세션은 previz만 열었음). 닫히는 조건: generate-sheet 경로 실측 — previz와 같은 무방어/오방어인지.
- 질문: CU 배경 가시성 규칙 — [[2026-08-06-previz-verifier]] 미결("answer key에 반영")과 이번 "tight 샷 배경 blurred 실측"이 같은 지점. 닫히는 조건: 뷰 시트가 tight 샷을 플레이트 수요에서 제외하는 규칙 명문화.
- 잔가지: 뷰 자산의 스키마 초안(locations 자식 테이블 view = {view_id, angle_tag, image, provenance} — §5 파생물 규칙 적용) / 무빙샷 previz(3프레임 스트립으로 충분한지)는 캡 완화 후 G3 재측정과 연동.
