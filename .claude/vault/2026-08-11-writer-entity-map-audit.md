# writer 파이프라인 엔티티 전수 감사 — 세션 기록

> 세션 2026-08-10~11. 다음 세션에서 이어가기 위한 기록.
> 원칙: 실측만 기록(추측 아님). 코드로 귀결된 것은 여기 없음 — diff/커밋 메시지가 기록.

## 0. 한 줄 요약

writer 파이프라인이 만드는 엔티티 60개를 전수 조사해, "만들고 안 쓰는 것"과 "설계 의도가
배선 부재로 끊긴 것"을 분리해 지도로 만들었다(아티팩트 — 스테이지별 프롬프트 원문·실제
산출물·끊긴 배선 14건 포함). 오버홀의 다음 행동은 필드 삭제가 아니라 **경로 쌍 3개 중
어느 쪽을 진실원으로 삼을지 정하는 것**이고, 그 결정이 아직 안 났다.

## 1. 실측 발견 — 안 통한 시도 포함

- **발견(구조)**: 파이프라인의 문제는 "만들고 안 쓰는 습관"이 아니라 **같은 일을 하는 경로가
  두 벌인데 한 벌만 살아 있는 상태**다 — 실사 단일/일괄, 모션 산문/계약, facet/산문,
  러프의 state 조인 vs 검사기의 컬럼 조회. 사장 필드는 이 구조의 증상이다.
- **발견(실사 경로)**: 실사 리페인트에 두 경로가 있고, **텍스트를 한 글자도 안 보내는 일괄
  경로가 Director 첫 진입 시 자동 실행**된다(빈칸 자율 채움). 근거: `use-writer-director-sync.ts:423`
  + `generate-storyboard-batch/route.ts:47`(텍스트 컬럼 미select). 실측 사용량 단일 59건 : 일괄 58건.
- **발견(설계 눈가림)**: v3(씬 촬영계획)는 조명 아크를 켈빈으로 정하면서 `time_of_day`·`weather`를
  못 받고, 로케이션은 id 문자열만 받아 `lighting_sources`를 못 본다. "대화 씬은 180°축 필수"라는
  자기 규칙을 대화 유무도 모른 채 인물 수로만 추정한다. 근거: `v3_scene_plan.ts:119-132`.
- **발견(버려지는 provenance)**: v4가 `// 데쿠파주 출처를 결정론적으로 보존 — beat→shot 추적성`
  주석과 함께 심는 `operation·source_beats·shot_function·rhythm_role` 4필드를, 바로 다음
  스테이지인 조립기가 **참조 0건**으로 버린다(`v4_shots.ts:556-561` vs `c_application_2.ts` 전역 grep).
- **발견(인물 정보)**: 핸드오프 매퍼가 `personality: []`를 하드코딩(`cast-contract.ts:17`)해서,
  데쿠파주가 보는 인물은 사실상 id와 role뿐이다. `entity_type`(person/object)도 이 경계에서 소실된다.
- **발견(보안·미조치)**: `WRITER_STEP_SECRET`이 프로덕션 환경변수 14개 중에 **없다**(vercel CLI 확인).
  `/api/writer/step`은 `getUser`·소유권 검사가 0건이고 게이트가 `if (secret && 불일치)` 구조라,
  시크릿 부재 시 조건이 성립하지 않아 통과한다 → 외부에서 남의 프로젝트 파이프라인 구동 가능(과금 직결).
- **안 통한 것**: "만들고 안 쓰는 필드"만 세는 접근 → 왜: 그것만으로는 처방이 안 나온다.
  같은 값을 두 소비자가 **다른 소스로 읽는** 경우(러프=state / 검사기=컬럼)가 더 위험한데
  필드 단위 집계로는 안 보인다. 경로 쌍 단위로 봐야 드러났다.
- **판정 정정 사례**: v1 막별 아크가 v3에 미전달이라고 두 번 보고했으나, 그 사이 병행 세션이
  정식 배선했다(`789a71f`, "E8 정식 배선 — act-arc-ablation 채택"). **낡은 트리를 근거로 한
  판정이 며칠도 못 간다** — 병행 세션이 도는 동안의 감사는 결론 직전에 재확인이 필요하다.

## 2. 결정 — 코드로 귀결 안 된 것만

### D-2026-08-11-a: 감사 결과를 코드 정리가 아니라 지도로 먼저 남긴다
- 상황: 사장 필드 수십 개와 끊긴 배선 14건을 동시에 찾았고, 즉시 정리하고 싶은 유혹이 컸다.
- 결정: 코드를 손대기 전에 엔티티 지도(아티팩트)를 만들어 "무엇이 어디까지 가는가"를 고정한다.
- 기각한 대안: 사장 필드 일괄 삭제 — 이유: 삭제는 프롬프트를 바꿔 생성 품질 회귀를 부르는데,
  어느 쪽을 진실원으로 삼을지 정하기 전에는 무엇을 지워도 되는지 알 수 없다.
- 감수하는 것: 지도 제작에 든 시간. 그리고 지도는 병행 세션의 변경으로 낡는다(위 정정 사례).

### D-2026-08-11-b: LLM 호출 전문은 수집하되 정리 장치는 붙이지 않는다
- 상황: writer 텍스트 스테이지의 LLM 입출력이 서버 어디에도 안 남아 진단 근거가 없었다.
- 결정: `llm_calls` 테이블에 전문을 수집(배포 완료)하고, 삭제·보관 정책은 개발 단계에서 도입하지 않는다.
- 기각한 대안: 이관 확인 후 즉시 삭제 — 이유: 로컬 아카이브가 유일본이 되면 디스크 사고가 곧 소실.
- 감수하는 것: `llm_calls`가 런당 1~2MB로 무한 증가. → `_DEFERRED.md` D-002 로 추적.
