밤 러너 사용 안내

메모만 남기면, 자는 사이 실행되고 아침에 판정한다

당신이 손대는 파일은 딱 두 개다 — 저녁과 아침에 메모·판정을 쓰는 곳 하나(_INBOX.md), 아침에 결과를 읽는 날짜별 보고서 하나(reports/날짜.html). 나머지는 전부 밤 자동화의 살림살이다.

2026년 8월 17일 개편 반영 · 계약 정본: .claude/vault/backlog/_NIGHT.md

먼저 이것만 — 밤 러너가 뭐 하는 물건인가

  1. 당신은 저녁에 메모를 쓴다.
    형식 없이, 문장이 안 끝나도 된다. .claude/vault/_INBOX.md에 아무렇게나 적으면 된다.
  2. 밤이 알아서 해석하고, 쪼개고, 실행한다.
    Orca 자동화가 매일 밤 계약 문서(_NIGHT.md)를 읽고 시작한다. 사전 승인을 기다리지 않는다 — 해석이 갈리면 안전한 쪽 하나를 골라 실행하고, 틀린 실행도 결과와 학습 자료로 남긴다. 조사·실험·코드 수리·기능 개발 전부가 실행 대상이다.
  3. 당신은 아침에 날짜별 보고서 HTML을 읽고, 판정도 메모로 쓴다.
    밤이 reports/2026-08-17.html처럼 날짜 기준 사람 보고서를 만든다. 읽고 나서 merge reject feedback 판정과 이유를 다시 _INBOX.md에 형식 없이 적으면, 다음 밤이 해석해 해당 결과 카드에 기록한다. 카드 파일을 직접 열 일은 없다. 판정 기록은 버리는 메모가 아니라 반복되면 계약 규칙으로 승격되는 자산이다.

디렉토리 구조

전부 .claude/vault/ 아래에 산다
.claude/vault/
├── _INBOX.md              ← 당신이 쓰는 곳. 저녁 메모 + 아침 판정, 전부 여기
├── backlog/               ← 밤의 살림살이 (루트에는 계약과 도구만)
│   ├── _NIGHT.md          ← 유일한 살아있는 밤 계약. 밤의 헌법이자 실행 절차서
│   ├── reports/           ← 당신이 아침에 읽는 곳. 날짜별 보고서 (2026-08-17.html …)
│   ├── tickets/           ← 티켓과 결과 카드 원장 (100여 개, 상태별로 관리됨)
│   ├── sweep/             ← 세션 수확 결과 (날짜별 실행 산출물)
│   ├── night-runtime.py   ← 메모를 바이트 그대로 사진 찍고(스냅샷) 소비 상태를 기록
│   ├── harvest.py         ← 낮에 정리 안 된 대화 세션에서 미결 사항을 수확
│   ├── provider-gate.py   ← 실행 소유권 관리. 두 실행이 같은 밤에 겹치지 않게 잠금
│   └── preflight.sh       ← 시작 전 검증. 티켓이 루트에 다시 쌓이면 실행 거부
└── _archive/              ← 은퇴한 문서 (_MORNING, _SWEEP, _NOW, _FIXLOG 등)

당신이 보는 곳은 _INBOX.md(쓰기)와 reports/(읽기) 딱 둘이다. tickets/와 sweep/은 밤의 내부 원장이라 열어볼 필요가 없다. _archive/에 있는 것은 전부 죽은 문서다 — 예전 아침 리뷰 파일(_MORNING.md)도 2026-08-17에 여기로 은퇴했고, 판정은 이제 _INBOX.md로 통합됐다. 살아있는 계약은 _NIGHT.md 하나뿐이며, 시작 전 검증이 옛 문서 부활이나 루트에 흩어진 티켓을 발견하면 실행 자체를 거부한다.

하룻밤이 흘러가는 순서

저녁

당신: 메모를 쓴다

_INBOX.md에 생각나는 대로 적는다. "이거 왜 이러지?", "저 화면 색 좀 이상함" 수준이면 충분하다. 다른 개발자가 쓴 메모도 같은 파일 끝에 append되어 원격으로 올라올 수 있다. 밤은 원문을 덮어쓰거나 지우지 않고 — claim 전에 최신 원격 append를 합친 뒤 바이트 그대로 사진을 찍어(스냅샷) 소비한다.

밤 시작

자동화: 검증하고, 잠금을 걸고, 입력을 고정한다

Orca 자동화가 시작 전 검증(preflight.sh)으로 필수 파일이 다 있는지 확인하고, 실행 소유권 잠금을 만든다. 같은 밤에 실행은 딱 하나만 돈다 — 주 실행(Claude)이 명시적으로 실패했을 때만 대체 실행(Codex)이 한 번 이어받는다. 그다음 계약 문서의 지문(해시)과 메모 스냅샷을 고정해서, 실행 도중 규칙이나 입력이 바뀌는 일을 차단한다.

밤중

자동화: 수확 → 분해 → 우선순위 → 병렬 실행 → 기록

수확: 동기화된 메모를 먼저 읽고, 오너 컴퓨터의 낮 세션만 harvest.py로 훑어 미결 사항을 건진다. inbox 입력과 harvest 후보는 같은 우선순위가 아니며, inbox가 먼저다. harvest 후보는 확인됨·후보·오너 판단 필요·중복·해결됨으로 분류한다. 분해: 후보를 "무엇이 참이면 닫히는가?"가 한 문장으로 써지는 가장 작은 실행 단위로 나눈다. 기록: 결과가 reported가 되면 원문을 삭제하지 않고 archive 복사와 소비 표식을 남긴다. archive는 승인 완료가 아니다. 아침 HTML에서 오너가 판정해야 최종 닫힌다.

아침

당신: 보고서를 읽고, 판정을 메모로 남긴다

reports/에서 오늘 날짜 HTML을 연다. 읽으면서 받아들일 것(merge), 되돌릴 것(reject), 조건 달 것(feedback)을 이유와 함께 _INBOX.md에 평소 메모처럼 적는다 — "어제 색온도 실험은 merge, 업로드 순서 고친 건 reject: 이유는…" 수준이면 된다. 다음 밤이 해석해 카드에 기록한다. 그림·영상의 좋고 나쁨은 당신만 판정한다 — 밤은 비교 자료와 측정표만 만들 뿐, "잘 나왔다" 같은 결론을 쓰지 않는다(이 프로젝트의 헌법이다).

티켓 상태의 뜻

상태는 위치 표시일 뿐, 승인 관문이 아니다
상태뜻밤의 처리
ready바로 실행 가능즉시 실행
waiting선행 조건이 있음조건을 확인해 가능한 부분은 진행
needs-owner사람의 선택이 필요선택지는 아침 카드로 올리되, 사실 조사는 계속
draft닫힘 조건이 미완성조건을 채워 실행 단위로 바꾸고 즉시 실행
blocked안전 경계에 걸림사유를 적고 다른 단위로 진행
awaiting-merge-review코드 변경 완료, 검토 대기격리 사본의 결과와 검증 명령을 아침 검토에 올림

안전 경계 — 밤이 스스로 멈추는 조건

  1. 절대 정지는 두 가지뿐.
    되돌릴 수 없는 행동, 그리고 예산 한도 초과. 모호함이나 테스트 실패는 정지 사유가 아니라 기록하고 넘어가는 사유다.
  2. 연속 3개 단위가 결론 없이 끝나면 새 단위 생성을 닫는다.
    도구나 입력 품질에 문제가 있다는 신호로 보고, 그 밤은 진단 모드로 전환한다.
  3. 오전 8시가 되면 새 일을 잡지 않는다.
    실행 중인 단위의 기록만 마치고 마무리한다.
  4. 생성 버튼은 과금이다.
    이미지·영상 생성(fal, higgsfield)은 실제 돈이 나간다. 돈 안 드는 확인을 항상 먼저 두는 이유다.

Orca가 없는 개발자는 어떻게 돌리나

Orca는 알람시계 + 문지기일 뿐, 실행 본체가 아니다

Orca가 하는 일은 둘뿐이다: 밤마다 제시간에 깨우고, 실행 잠금(primary claim)을 만든 뒤 Claude를 띄운다. 실행 본체는 전부 저장소 안에 있다 — 계약(_NIGHT.md)도, 잠금 상태 기계(provider-gate.py)도, 수확기(harvest.py)도 Orca 설치 없이 그대로 돈다. 계약도 2026-08-17 개정으로 하드코딩 경로를 전부 걷어내서, 어느 머신의 어느 clone에서도 같은 문서가 그대로 돌아간다.

Orca 없는 개발자는 macOS 기본 예약 실행기인 launchd로 같은 밤을 돌린다. 진입점은 backlog/night-launchd.sh 하나다: run 모드는 잠금 → 네이티브 Claude Code 헤드리스 실행 → 종료 기록까지 하고, dry-run 모드는 임시 폴더만 써서 파이프라인 전체가 돌아가는지만 검증한다. 설치 절차 전체(전제 확인 → dry-run → launchd 등록 → 운영 명령)는 .claude/vault/night-runner-setup.md가 정본이며, 개발자 머신의 Claude Code가 그 문서를 읽고 그대로 설치하면 된다.

한 가지 실질적 차이: 화면 스모크 테스트(pnpm smoke)는 Orca 런타임 전제가 없으면 실패가 아니라 skip으로 빠진다. 즉 밤은 정상 완주하지만 "브라우저에서 실제로 렌더됐나" 증거가 빠진 채로 완주한다. 아침 보고서에서 스크린샷 증거가 비어 있으면 이 경우다.

보고서는 저장소 안의 HTML 파일이 정본이라 어느 환경에서든 똑같이 생긴다. 두 개발자 모두 Claude를 쓰므로, 세션에서 이 파일을 열면 Claude가 artifact 형태로 렌더해 보여줄 수 있고 — 파일이 정본, artifact는 보기 방식일 뿐이라 충돌이 없다.

내부 명령 시퀀스

상세 — 실행 시작 명령 시퀀스 (자동화 내부용, 사람이 칠 일 없음)

Orca precheck가 preflight.sh를 통과시키고 automation-provider-gate.sh로 실행 잠금(primary sweep claim)을 만든 뒤, 계약 본문의 시작 블록이 다음을 수행한다:

1. state sweep으로 잠금 상태 조회 → 소유자(claude/codex)와 run_id·owner_token 확보
2. shasum -a 256 _NIGHT.md로 계약 지문 고정
3. night-runtime.py snapshot-inbox로 메모 스냅샷 고정 (snapshot_id·snapshot_fingerprint 발급)
4. harvest.py --dry-run → 표 확인 후 본 실행 → 마지막에 --validate-complete
5. 보고서 저장이 전부 확인된 뒤에만 complete sweep success로 성공 도장

실패나 시간 초과 시엔 failed/timeout으로 닫고, 그 경우에만 Codex 대체 실행이 같은 run_id로 한 번 허용된다.
