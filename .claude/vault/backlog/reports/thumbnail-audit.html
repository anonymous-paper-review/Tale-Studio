저장·요청 비용 점검 · 2026-08-19

세 장을 올리면서 작은 그림은 한 장만 만들고 있었습니다

작게 줄인 미리보기 그림이 저장 용량·쓰기 요청·읽기 요청 세 축에 각각 어떻게 작용하는지 재고, 지금 무엇이 빠져 있는지 파일 단위로 확인했습니다.

결론 먼저 — 백필이 덜 된 게 아니라 코드가 원래 그렇게 짜여 있습니다. 러프·스토리보드는 시작·연출·끝 세 프레임을 올리는데, 작은 그림은 시작 프레임만 만듭니다. 그래서 지금 채워 넣어도 새로 만드는 것마다 같은 구멍이 다시 생깁니다.

1

작은 그림이 하는 일

목록이나 판 위에 그림 수백 장이 깔릴 때 원본을 그대로 내보내면 화면 한 번 여는 데 수백 메가가 나갑니다. 그래서 올릴 때 가로 512픽셀 WebP 축소본을 원본 옆에 같이 만들어 두고, 목록에서는 그걸 대신 띄웁니다.

실측한 크기 비율입니다.

평균 크기원본 대비
원본 (스토리보드 프레임)244 kB100%
작은 그림15 kB5.6%

약 18분의 1입니다. 이게 제대로 깔려 있으면 화면 한 번 여는 비용이 그만큼 줄어듭니다.

2

세 축에 각각 어떻게 작용하나

작은 그림은 저장을 늘리고 읽기를 줄이는 거래입니다. 어느 쪽이 이득인지는 조회 횟수가 정합니다.

축작은 그림이 하는 일지금 우리 수치
저장 용량원본 옆에 파일이 하나 더 생기므로 늘어납니다. 대신 원본의 5.6%뿐입니다4,289개 · 64 MB
쓰기 요청만들 때 한 번만 늘어납니다. 원본 1장당 1건파일당 1건 · 1회성
읽기 요청요청 횟수는 그대로지만 나가는 바이트가 18분의 1이 됩니다62 MB (4,149장)

중요한 구분 하나. 작은 그림은 읽기 요청 횟수를 줄이지 않습니다. 그림 한 장을 보려면 어느 쪽이든 요청 1건입니다. 줄어드는 건 나가는 데이터량입니다.

단, 없을 때는 횟수까지 늘어납니다 — 다음 절이 그 이야기입니다.

참고로 화면에 안 들어온 그림은 아예 요청되지 않습니다. 화면 코드가 화면에 들어올 때까지 안 받는 방식을 쓰기 때문입니다. 프로젝트에 768장이 있어도 스크롤로 눈에 들어온 것만 나갑니다.

3

없으면 요청이 두 번 나갑니다

화면 코드는 일단 작은 그림을 먼저 요청합니다. 없으면 404를 받고, 그때 원본을 다시 요청합니다. 화면이 안 깨지게 하려고 넣은 안전장치인데, 비용 관점에서는 요청이 두 배가 됩니다.

4

결함 하나 — 세 장을 올리고 한 장만 만듭니다

이게 근본 원인입니다. 백필이 덜 된 게 아닙니다.

러프와 스토리보드는 한 샷당 시작·연출·끝 세 프레임을 만들어 셋 다 올립니다. 그런데 작은 그림을 만드는 호출은 시작 프레임에만 붙어 있습니다.

const [startUrl, directionUrl, endUrl] = await Promise.all([
  upload(`${base}/${seg}_rough_start.png`, frames.start),
  upload(`${base}/${seg}_rough_direction.png`, frames.direction),
  upload(`${base}/${seg}_rough_end.png`, frames.end),
])
await uploadThumbnail(`${base}/${seg}_rough_start.png`, frames.start)
                                    ↑ 시작 프레임만. 연출·끝은 빠져 있습니다

src/lib/fal/finalize.ts — 같은 형태가 880행, 1000행, 1071행 세 군데

파일을 세어 보니 코드 모양 그대로 나옵니다.

시작 프레임만 정확히 100%입니다. 연출·끝이 0%가 아니라 73%·64%인 건 소급 생성 도구를 한 번 돌린 적이 있기 때문입니다. 그 뒤에 만들어진 것들이 다시 빠졌습니다.

그래서 지금 채워 넣기만 하면 안 됩니다. 코드를 안 고치면 새 샷을 만들 때마다 프레임 세 장 중 두 장이 계속 빠집니다. 소급 생성을 주기적으로 돌려야 하는 상태가 되는데, 그건 고친 게 아니라 청소를 반복하는 겁니다.

결함 둘 — 화면에 안 뜨는 파일에도 만들었습니다

생성용 임시 파일 141개에 작은 그림이 만들어져 있습니다. 이건 소급 생성 도구가 보관함의 모든 이미지를 가리지 않고 훑기 때문입니다. 화면에 뜨지 않으므로 아무도 안 읽습니다 — 저장 용량과 쓰기 요청을 그냥 버린 것입니다.

액수 자체는 작습니다(약 2메가). 다만 "커버리지를 100%로 맞추자"고 그냥 돌리면 나머지 130개까지 만들게 됩니다. 소급 생성 도구에 대상 필터가 필요합니다.

19%의 파일이 데이터의 91%를 차지합니다

작은 그림이 없는 991장은 전체의 19%인데, 읽기 요청의 32%와 나가는 데이터의 91%를 만듭니다. 나머지 4,149장이 다 합쳐 62메가인데 이 991장이 635메가입니다.

확실한 것과 모르는 것

확인한 것

  • 작은 그림은 원본의 5.6% 크기다 (평균 15 kB)
  • 코드가 세 프레임 중 시작 프레임에만 작은 그림을 만든다 — 세 군데 모두
  • 시작 프레임만 정확히 100%, 연출·끝은 73%·64%
  • 화면에 뜨는 그림 5,140장 중 991장에 작은 그림이 없다
  • 없으면 404를 받고 원본을 다시 요청해 요청이 2건이 된다
  • 그 991장이 전체 나가는 데이터의 91%를 만든다
  • 화면에 안 뜨는 임시 파일 141개에도 만들어져 있다
  • 다 만들면 저장 +35 MB, 조회당 데이터 −86%

모르는 것

  • 404 응답이 요금 대상인지 — Cloudflare 문서에 없습니다. 명시적으로 면제된 건 권한 없음(401)뿐입니다
  • 실제 조회 횟수 — 화면을 몇 번 열었는지 기록이 없어, 위 계산은 "한 번씩 다 봤을 때" 기준입니다
  • 업로드 원본 80개에 작은 그림이 필요한지 — 화면 어디에 뜨는지 확인하지 않았습니다
  • 연출·끝 프레임이 목록 화면에 실제로 뜨는지 — 뜨지 않는다면 작은 그림이 아니라 다른 대책이 맞습니다
8

할 일

  1. 코드를 먼저 고칩니다. finalize.ts 세 군데에서 세 프레임 모두에 작은 그림을 만들게 합니다. 이걸 안 하면 아래가 전부 반복 청소가 됩니다.
  2. 소급 생성 도구에 대상 필터를 넣습니다. 화면에 뜨는 그림만 만들고, 배치 참조 시트·참조 띠는 건너뜁니다.
  3. 991개를 소급 생성합니다. 도구는 이미 있습니다 — scripts/backfill-thumbnails.mjs. 서비스가 막혀 있어 지금은 못 돌립니다.
  4. 임시 파일에 잘못 만든 141개를 지웁니다. 아무도 안 읽는 파일입니다.
  5. 연출·끝 프레임이 목록에 실제로 뜨는지 확인합니다. 안 뜬다면 작은 그림을 만들 게 아니라 목록에서 아예 요청하지 않는 게 맞습니다.

1·2번은 지금 할 수 있습니다. 3·4번은 파일 보관함 차단이 풀려야 합니다.

  • 파일 보관함 전수 집계 — 원본과 작은 그림을 짝지어 세었습니다 (2026-08-19). 데이터베이스 직접 접속으로 읽음
  • 코드 확인 — src/lib/fal/finalize.ts(880·1000·1071행), src/lib/storage-thumb.ts, src/components/thumb-image.tsx, src/lib/image-url.ts, scripts/backfill-thumbnails.mjs

이 문서가 하지 않는 것

  • 아무 코드도 고치지 않았고 파일도 만들거나 지우지 않았습니다. 8절은 전부 제안입니다
  • 화면을 실제로 열어 확인하지 않았습니다. 어느 프레임이 목록에 뜨는지는 코드가 아니라 눈으로 봐야 확실합니다
  • 실제 조회 횟수를 재지 않았습니다. 요청 기록이 없어 "한 번씩 다 봤을 때" 기준으로만 계산했습니다
  • 작은 그림의 화질이 충분한지 판단하지 않았습니다. 512픽셀이 지금 화면 크기에 맞는지는 사람이 봐야 합니다
