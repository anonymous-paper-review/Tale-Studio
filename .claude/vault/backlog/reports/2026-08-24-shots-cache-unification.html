샷 데이터를 여섯 곳이 각자 들던 것을, 캐시 한 칸으로 합쳤습니다

작가·감독·편집자 화면과 내보내기가 같은 프로젝트의 샷 목록을 각자 서버에서 받아 각자 들고 있었습니다. 화면을 오갈 때마다 같은 데이터를 다시 받았고, 한 화면의 편집을 다른 화면이 모르는 "사본 갈림"이 여기서 났습니다. 이번 작업으로 여섯 읽기가 한 칸을 공유합니다.

결론 먼저 — 여섯 읽기 전부 전환, 코드 시험 1,484건 전부 통과. 덤으로 생성 타입 파일(database.ts)이 실제 데이터베이스보다 8열 낡아 있던 것을 발견했습니다. 실제 브라우저 검증은 이번에 안 돌렸습니다(5절).

1

무엇을 하려 했나 — 그리고 지도가 판을 바꿨다

출발할 때는 "샷을 만지는 곳 35곳"이라는 숫자만 있었습니다. 전부 갈아엎는 줄 알았는데, 한 곳 한 곳을 읽기/쓰기·브라우저/서버로 갈라보니 판이 달랐습니다:

분류몇 곳이번 작업에서
브라우저 읽기 — 화면이 목록을 받아오는 곳6전부 캐시로 (작가·감독·편집자 화면 + 내보내기 3곳)
브라우저 쓰기 — 화면에서 고치는 곳9그대로 두고, 성공 지점에 무효화(invalidate) 한 줄씩
서버 읽기·쓰기 — 생성 완료 처리·파이프라인20손대지 않음 — 캐시는 브라우저 메모리 층이라 무관

3

도중에 틀렸던 것 셋 — 전부 잡혀서 고쳐졌다

실수 ① — 일괄 수정 도구가 중간에 죽어 4파일이 빠졌는데, 검사는 통과였다

자체 발견

여섯 호출부를 한 번에 바꾸는 수정 도구가 중간 파일에서 멈췄는데, 이미 바뀐 파일들만으로도 타입 검사가 통과라 빠진 4파일을 모르고 지나갈 뻔했습니다. 코드 검사 도구가 "가져왔는데 안 쓰는 부품"을 경고해 준 것을 따라가 발견했고, 잔존 직접 요청을 다시 세어(grep from('shots')) 0이 될 때까지 마저 바꿨습니다. 교훈: 일괄 수정 뒤에는 남은 개수를 반드시 다시 센다.

실수 ② — 오류를 "[object Object]" 로 바꿔치기하던 어댑터

시험이 잡음

서버 오류는 표준 오류 객체가 아니라 { message } 모양의 일반 객체로 옵니다. 어댑터의 첫 판이 이를 문자열로 뭉개 "[object Object]" 라는 쓸모없는 메시지를 만들었습니다. 실패 경로 시험이 곧바로 잡았고, 두 모양을 다 받게 고쳤습니다.

발견 — 생성 타입 파일(database.ts)이 실제 데이터베이스보다 8열 낡아 있었다

숨어 있던 것

캐시에 정확한 타입을 붙이자, 화면이 실제로 읽는 열(러프 스토리보드·목각 영상 등 8개)이 생성 타입에 없다는 오류가 쏟아졌습니다. 옛 코드에서는 여러 요청을 한 다발로 받는 과정에서 타입이 "아무거나"로 뭉개져 안 보였을 뿐, 전부터 낡아 있던 타입입니다. 실제 데이터베이스 구조를 대조 실측해서 빠진 8열을 보강해 두었고, database.ts 재생성은 별도 작업으로 남겼습니다.

4

무엇이 좋아지나 — 사용하는 사람 기준

  • 화면을 오갈 때 같은 데이터를 다시 안 받는다. 작가 → 감독으로 넘어가면, 30초 안이면 감독 화면이 작가가 받아둔 그 데이터를 그대로 쓴다. 167샷짜리 프로젝트 기준 화면 진입 한 번이 552KB였다 — 이제 신선 기간 안 왕복은 0KB다.
  • 편집이 다른 화면에 전해질 길이 생겼다. 샷을 고치면(쓰기 9곳) 칸에 무효화가 남고, 다른 화면이 다음에 읽을 때 새 데이터를 받는다 — 예전에는 각 화면이 자기 사본을 쥔 채 서로의 변경을 알 방법 자체가 없었다.
  • 생성 완료가 확실히 반영된다. 파이프라인이 샷을 다 채운 순간, 재로드 전에 무효화를 먼저 남긴다 — "완료됐는데 30초 전 캐시를 보여주는" 함정을 막았다.
  • 타입이 진실에 가까워졌다. 예전엔 "아무거나"로 받던 여섯 곳이 이제 실측 스키마 그대로의 타입을 받는다.
5

확실한 것과 모르는 것

이 작업이 증명한 것

  • 여섯 읽기 전부 캐시 경유 — 직접 요청 잔존 0 (재계수)
  • 동시 호출 합침·신선 즉답·칸 격리·무효화 재조회 (신규 시험 7건)
  • 옛 오류 분기·경합 시험·내보내기 계약 전부 보존 (기존 시험 1,477건)
  • 배포 빌드 2회 연속 통과

증명하지 않은 것

  • 실제 브라우저 검증은 이번에 안 돌렸다 — 코드 시험뿐이다. 이전 회차처럼 시험 계정 + Playwright으로 돌리려면 별도 실행이 필요하다
  • 감독 화면의 생성 완료(영상 등)는 화면 내부 갱신에 의존한다 — 그 경로에는 아직 무효화가 없다 (다음 조각)
  • 30초 신선 기간이 체감상 맞는지 — 써 봐야 안다
  • database.ts 재생성은 하지 않았다 — 8열 보강은 임시 보정이다
6

믿으려면 뭐가 더 필요한가

  • 실기기 확인 (10분, 0원) — 작가 화면에서 샷 설명을 고치고 감독 화면으로 넘어가 30초 뒤 반영되는지. 시험 계정 + Playwright 로 재현 가능(이전 성적표와 같은 방식).
  • 감독 생성 완료 경로에 무효화 — 영상·실사 완료를 화면이 알아챈 지점에 한 줄. 작은 조각이다.
  • database.ts 재생성 — 실제 데이터베이스에서 다시 뽑기. 이번에 보강한 8열이 자연 소멸된다.
7

결론

사본 여섯 벌이 칸 하나가 됐다. 시험 1,484건이 그 위에서 전부 통과한다.

1. 브라우저의 샷 읽기 여섯 곳이 전부 공유 캐시(프로젝트당 한 칸, 30초 신선)을 지난다. 화면 간 재요청과 사본 갈림이 구조적으로 사라졌다.

2. 쓰기 아홉 곳과 파이프라인 완료 지점에 무효화를 심어, 변경이 다른 화면에 전해질 길을 만들었다.

3. 생성 타입 파일(database.ts)이 실제 데이터베이스보다 8열 낡아 있던 것을 발견하고 실측으로 보강했다 — 재생성은 별도 작업.

4. 실제 브라우저 검증은 이번 회차에 포함되지 않았다 — 코드 층 증명까지가 이 문서의 범위다.

근거로 쓴 것 — 샷 접근 35곳 전수 분류(읽기/쓰기·브라우저/서버) · 신규 시험 7건 + 기존 1,477건 · 타입 검사 · 배포 빌드 2회 · 실제 데이터베이스 구조 대조(8열 실측). 커밋: 2d9e85a · 모듈: src/lib/shots-cache.ts · 시험: tests/shots-cache.test.ts

이 문서가 하지 않는 것 — 실제 브라우저에서의 확인(5절), 감독 생성 완료 경로의 무효화, database.ts 재생성, 속도 체감의 측정. "덜 묻는다"의 코드 층 증명까지만 담는다.
