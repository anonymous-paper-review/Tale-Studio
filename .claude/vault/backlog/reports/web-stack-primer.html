백엔드·서버·호스팅은 서로 다른 질문에 답하는 말입니다

이번 서비스 정지를 계기로, tale-studio가 실제로 어떤 부품들로 조립돼 있는지 배선도를 그렸습니다. 일반론이 아니라 우리 코드에 있는 것만 가지고 설명합니다.

먼저 오해 하나를 풀고 시작합니다 — Supabase는 데이터베이스 회사가 아닙니다. 데이터 보관, 로그인, 파일 보관 세 가지를 묶어서 파는 회사이고, tale-studio는 그 셋을 다 쓰고 있습니다. 이번에 로그인까지 같이 죽은 이유가 정확히 이것입니다.

1

먼저 배선도 한 장

화면을 한 번 여는 동안 요청이 어디를 거쳐 가는지입니다. 나머지 절은 전부 이 그림의 부분 설명입니다.

2

서버 · 뒤쪽 · 호스팅 — 셋은 층위가 다릅니다

이 셋을 같은 것으로 보면 계속 헷갈립니다. 세 단어는 서로 다른 질문에 답합니다.

말답하는 질문tale-studio 에서는
뒤쪽백엔드무슨 일을 하느냐 — 역할주소 코드 72개. 데이터 읽고 쓰기, 권한 검사, 외부 생성 서버에 주문 넣기
서버어디서 도느냐 — 실행되는 컴퓨터Vercel이 요청마다 띄우는 함수. 우리 소유 컴퓨터는 하나도 없습니다
호스팅그 컴퓨터를 누가 대주느냐 — 임대 서비스Vercel. 코드를 받아 빌드하고 주소를 붙여 24시간 돌립니다

셋을 한 문장에 넣으면 관계가 보입니다.

"우리 뒤쪽 코드는 Vercel이 호스팅하는 서버에서 돈다."

역할이 뒤쪽, 도는 자리가 서버, 그 자리를 대주는 게 호스팅입니다. 그래서 "뒤쪽 = 서버"는 반쯤 맞고 반쯤 틀립니다. 뒤쪽 코드가 서버에서 도는 건 맞지만, 서버에서 도는 게 전부 뒤쪽은 아닙니다 — 화면 코드도 Vercel 서버가 만들어서 내려보냅니다.

그리고 "호스팅 = 서버"도 틀립니다. 호스팅은 서비스 이름이고 서버는 그 서비스가 제공하는 것입니다. 집을 빌려주는 임대업과 집 자체가 다른 것과 같습니다.

3

Next.js는 화면만 만드는 게 아닙니다

React 기반이라 화면 전용으로 보이지만, Next.js는 화면과 뒤쪽을 한 저장소에 같이 담는 도구입니다. 우리 코드가 증거입니다.

우리 코드개수어디서 도나
화면 컴포넌트 중 'use client' 표시가 붙은 것브라우저에서 직접 도는 코드라고 명시한 것96 / 119브라우저
주소 코드src/app/api 아래 route.ts72서버 — 브라우저에 안 내려감
문지기 코드src/middleware.ts1서버 — 모든 요청 앞

주소 코드 72개가 우리 뒤쪽 전부입니다. 크게 이런 묶음으로 나뉩니다 — writer(대본), director(연출·스토리보드), produce(제작), assets(자산), project(프로젝트 관리), fal(외부 생성 서버 연동).

여기서 중요한 구분 하나. 같은 Supabase라도 브라우저에서 부를 때와 서버에서 부를 때 쓰는 열쇠가 다릅니다.

  • 브라우저용 열쇠 — 누구나 볼 수 있는 공개 열쇠입니다. 이 열쇠로는 데이터베이스의 권한 검사를 통과해야만 데이터가 나옵니다
  • 서버용 열쇠 — 권한 검사를 통째로 건너뛰는 만능 열쇠입니다. 브라우저에 절대 내려보내면 안 됩니다. 우리 코드에도 "client-side 코드에서 import 금지"라고 적혀 있습니다 src/lib/supabase/admin.ts

이 구분이 있어야 뒤쪽이 존재할 이유가 생깁니다. 브라우저를 못 믿기 때문에 믿을 수 있는 자리에서 도는 코드가 따로 필요한 겁니다. 그게 뒤쪽입니다.

4

Supabase는 어디까지 하나

데이터베이스만 쓰는 걸로 알고 계셨는데, 실제로는 세 기둥을 다 쓰고 있습니다.

Supabase 가 파는 것tale-studio안 쓰면 어떻게 되나
데이터베이스PostgreSQL — 프로젝트·캐릭터·샷·생성기록씀—
로그인 처리이메일·비밀번호 로그인, 세션 관리씀로그인을 직접 만들거나 다른 회사 것을 붙여야 함
파일 보관함media 한 곳 · 9,871 개 · 3.6 기가씀다른 파일 보관 서비스로 옮기면 됨 — 가장 떼어내기 쉬운 기둥
실시간 알림데이터가 바뀌면 화면에 즉시 반영안 씀—
가장자리 함수Supabase 쪽에서 코드 실행안 씀 — 뒤쪽은 전부 Vercel—

이번 사고가 이렇게 아팠던 진짜 이유

세 기둥이 한 회사, 한 프로젝트, 한 요금제에 묶여 있습니다. 그래서 파일 용량 하나가 한도를 넘자 로그인과 데이터까지 같이 끊겼습니다.

만약 파일만 다른 곳에 있었다면, 파일이 안 보이는 대신 로그인과 데이터는 살아 있었을 겁니다. 서비스가 반쯤 동작하는 것과 통째로 죽는 것의 차이입니다.

데이터베이스가 권한 검사도 합니다

보통 권한 검사는 뒤쪽 코드가 합니다. 그런데 Supabase는 데이터베이스 자체에 줄 단위 권한 규칙을 걸 수 있고, 우리도 그걸 쓰고 있습니다. 예를 들어 영상 클립 테이블에는 "이 프로젝트가 속한 작업공간의 주인이 지금 로그인한 사람과 같아야 한다"는 규칙이 걸려 있습니다.

supabase/migrations/20260811120000_lock_rls_and_revoke_anon_writes.sql

이게 중요한 이유는 나중에 나옵니다 — 이 규칙은 "지금 로그인한 사람"을 로그인 처리 기둥에서 가져옵니다. 그래서 데이터베이스와 로그인을 서로 다른 회사로 쪼개면 이 규칙이 작동하지 않습니다.

바깥 회사와의 왕복

그림·영상은 우리가 만들지 않습니다. 외부 생성 서버에 주문을 넣습니다. 이 왕복이 나간 데이터량을 만드는 경로라 따로 그립니다.

5

Vercel 은 정확히 뭘 하나

우리 코드를 받아서 빌드하고, 주소를 붙이고, 요청이 올 때마다 실행합니다. 프로덕션 주소는 talestudio.art입니다.

  • 화면 파일(브라우저가 받는 HTML·JS·CSS)은 전 세계에 흩어진 중계망에서 배달합니다. 그래서 빠릅니다
  • 주소 코드 72개는 요청이 들어올 때마다 함수로 깨어납니다. 상시 켜진 컴퓨터가 아닙니다 — 안 쓰면 요금도 안 나가고, 갑자기 몰리면 여러 개가 동시에 뜹니다
  • 문지기 코드는 모든 요청 앞에서 먼저 돌아서 로그인 여부를 확인하고 안 된 사람을 로그인 화면으로 보냅니다

그래서 Vercel은 뒤쪽을 "돌려주는" 곳이지 뒤쪽 자체가 아닙니다. 뒤쪽 로직은 우리가 쓴 72개 파일이고, Vercel은 그걸 실행할 자리를 빌려줄 뿐입니다. 코드를 다른 호스팅으로 옮겨도 뒤쪽은 그대로입니다.

거꾸로 Supabase는 로직을 빌려주는 게 아니라 완성된 기능을 파는 쪽입니다. 로그인 기능을 우리가 짜지 않았습니다 — 사서 쓰고 있습니다. 이 차이가 다음 절의 핵심입니다.

6

Cloudflare 는 왜 넉넉해 보이나

숫자만 보면 실제로 훨씬 넉넉합니다. 다만 파는 방식이 다릅니다.

무료 한도SupabaseCloudflare
데이터베이스 용량500 MB5 GB D1
파일 보관 용량1 GB10 GB R2
나간 데이터량우리를 죽인 항목5 GB + 5 GB요금 없음 R2
로그인 처리포함없음 — 따로 구해야
데이터베이스 종류PostgreSQLSQLite

세트냐 부품이냐의 차이입니다.

Supabase는 데이터베이스·로그인·파일 보관함을 이미 조립해서 팝니다. 로그인 화면 하나 만드는 데 우리가 쓴 코드는 signInWithPassword 한 줄이었습니다.

Cloudflare는 부품을 따로 팝니다. 넉넉한 대신 로그인은 없고, 데이터베이스도 종류가 다릅니다. 우리 마이그레이션 기록과 줄 단위 권한 규칙은 PostgreSQL 문법으로 쓰여 있어서 SQLite로 그대로 옮겨지지 않습니다.

그래서 통째로 갈아타는 건 큰 공사입니다. 하지만 파일 보관함만 옮기는 건 다른 이야기입니다. 다음 절에서 다룹니다.

7

쪼갤 수 있나 — 세 가지 질문

Supabase 프로젝트 두 개를 한 제품에 연결할 수 있나?

기술적으로는 됩니다. Supabase 연결은 "주소 + 열쇠"로 만들어지니 두 벌 만들면 그만입니다. 무료 요금제는 계정당 활성 프로젝트 2개까지 허용합니다 — 여러분이 소유자나 관리자인 모든 조직을 합쳐서 셉니다. 쉬고 있는 프로젝트는 개수에 안 들어갑니다.

그런데 실제로는 잘 안 됩니다. 두 가지가 걸립니다.

  • 데이터베이스끼리 이어붙일 수 없습니다. 서로 다른 컴퓨터라 "프로젝트 표와 캐릭터 표를 이어서 한 번에 조회"가 안 됩니다. 우리 코드는 이런 조회를 곳곳에서 씁니다
  • 로그인이 한쪽에만 있습니다. 4절에서 말한 줄 단위 권한 규칙은 "지금 로그인한 사람"을 로그인 기둥에서 가져옵니다. 데이터베이스가 다른 프로젝트에 있으면 그 사람이 누군지 모릅니다 — 권한 검사가 통째로 무력화됩니다

계정을 여러 개 만들어 돌려쓸 수 있나?

권하지 않습니다. 무료 한도를 우회할 목적의 계정 분산은 이용약관에 걸릴 수 있습니다. 그보다 현실적인 문제가 큽니다 — 열쇠가 여러 벌이 되고, 어느 계정에 어느 데이터가 있는지 사람이 기억해야 하고, 한 계정이 막히면 어디가 죽는지 추적이 안 됩니다. 이번에 겪은 "왜 로그인이 안 되지"가 계정 수만큼 늘어납니다.

Supabase + 다른 회사 파일 보관함은 되나?

이게 실제로 맞는 답입니다. 앞의 두 방법이 막히는 이유는 전부 "데이터베이스와 로그인이 서로를 필요로 한다"는 것이었습니다. 파일은 이 사슬에 안 묶여 있습니다.

파일은 이어붙일 필요가 없고 권한 규칙도 필요 없습니다. 데이터베이스에는 주소 문자열 하나만 저장되면 됩니다. 그 주소가 어느 회사를 가리키든 나머지 코드는 알 필요가 없습니다.

우리 코드에서 실제로 고쳐야 하는 곳도 좁습니다. 파일 주소를 만드는 함수가 한 줄짜리로 여러 곳에 흩어져 있는데, 이걸 한 군데로 모으면 그 안쪽만 바꿔서 회사를 갈아탈 수 있습니다. 지금은 getPublicUrl 호출이 fal/finalize.ts 등 20여 곳에 직접 박혀 있어서, 먼저 그걸 한 함수로 모으는 작업이 선행돼야 합니다.

확실한 것과 확인이 필요한 것

우리 코드에서 확인한 것

  • 뒤쪽 코드는 Vercel에서 돈다 — 주소 코드 72개
  • 화면 컴포넌트 119개 중 96개가 브라우저에서 돈다
  • Supabase의 세 기둥을 다 쓴다 — 데이터·로그인·파일
  • 실시간 알림과 가장자리 함수는 안 쓴다
  • 줄 단위 권한 규칙이 켜져 있고 로그인 정보에 의존한다
  • 서버용 만능 열쇠와 브라우저용 공개 열쇠가 분리돼 있다
  • 프로덕션 주소는 talestudio.art

확인이 더 필요한 것

  • 파일 보관함을 옮기는 실제 공수 — 주소 만드는 곳 20여 군데를 모으는 작업량을 재보지 않았습니다
  • 외부 생성 서버가 결과물을 얼마나 오래 보관하는지 — 이걸 알아야 "우리가 저장을 안 해도 되나"에 답할 수 있습니다
  • 옮겼을 때 실제 요금 — 무료 한도 비교만 했고 유료 구간 계산은 안 했습니다
  • 기존 파일 9,871개를 옮기는 방법과 시간
9

한 문단 요약

tale-studio는 Next.js로 화면과 뒤쪽을 같이 쓰고, 그 전체를 Vercel이 호스팅하며, 데이터·로그인·파일 세 가지를 Supabase에서 사서 씁니다. 뒤쪽은 역할이고, 서버는 그게 도는 자리고, 호스팅은 그 자리를 빌려주는 서비스라 셋은 층위가 다릅니다.

이번에 서비스가 통째로 죽은 건 세 기둥이 한 요금제에 묶여 있었기 때문입니다. Cloudflare가 넉넉해 보이는 건 사실이지만 통째로 옮기는 건 큰 공사입니다. 대신 파일 보관함만 떼어내는 건 실제로 가능하고, 그것만으로 이번 종류의 사고는 막을 수 있습니다 — 파일이 안 보이더라도 로그인과 데이터는 살아남기 때문입니다.

이 문서의 근거

  • tale-studio 코드 직접 확인 — 주소 코드 개수, 화면 컴포넌트 표시, 문지기 코드, 열쇠 분리, 권한 규칙 마이그레이션 (2026-08-19)
  • Vercel 명령줄 도구로 확인한 프로젝트 구성과 프로덕션 주소
  • Supabase 파일 보관함 전수 집계 — 파일 9,871개
  • Supabase·Cloudflare 무료 한도는 2026년 8월 기준 공개 자료 검색

이 문서가 하지 않는 것

  • 아무 코드도 고치지 않았습니다. 7절의 쪼개기는 가능성 설명이지 실행 계획이 아닙니다
  • 이전 비용과 공수를 계산하지 않았습니다. 무료 한도 숫자 비교까지만 했습니다
  • 다른 회사 파일 보관함을 실제로 붙여 보지 않았습니다. 요금·속도·안정성은 써 봐야 압니다
  • 요금 한도 숫자는 검색으로 얻은 값이라 실제 계약 조건과 다를 수 있습니다. 결정 전에 각 회사 요금 페이지에서 다시 확인해야 합니다
