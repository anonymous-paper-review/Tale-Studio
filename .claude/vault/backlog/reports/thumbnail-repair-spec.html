작업 명세 · 인수인계용 · 2026-08-19

썸네일 파이프라인 수리 — 만드는 쪽과 쓰는 쪽을 동시에 고칩니다

작은 그림이 세 프레임 중 한 장만 만들어지고, 만들어진 것조차 주요 화면이 쓰지 않고 있습니다. 어느 쪽 하나만 고치면 효과가 0이라 같이 고쳐야 합니다.

전제 — 파일 보관함이 요금 초과로 막혀 있어 파일을 만들거나 지우는 작업은 지금 못 합니다. 이 명세의 A·B·C는 전부 코드 변경이라 지금 가능하고, D(소급 생성·삭제)는 보관함이 열린 뒤입니다.

1

배경 — 왜 지금 손대나

실측 결과 세 가지가 동시에 어긋나 있습니다.

  • 만드는 쪽 — 한 샷당 프레임 세 장을 올리는데 작은 그림은 시작 프레임만 만듭니다. 날짜별 생성 비율이 30% 안팎으로 코드 모양과 일치합니다.
  • 쓰는 쪽 — 카드·그리드를 그리는 두 컴포넌트가 작은 그림을 아예 거치지 않고 원본을 직접 물고 있습니다. 그중 하나는 세 장을 동시에 마운트합니다.
  • 소급 생성 도구 — 화면에 안 뜨는 생성용 임시 파일에도 작은 그림을 만들었습니다(141개).

화면에 뜨는 그림 5,140장을 한 번씩 보면 지금은 697메가가 나갑니다. 전부 제대로 걸리면 97메가입니다. 저장은 35메가 늘어납니다.

순서가 중요합니다. 쓰는 쪽을 안 고친 채 소급 생성만 돌리면 저장·쓰기 비용만 늘고 효과는 0입니다. 2026년 7월 17일부터 8월 12일까지 26일 동안 정확히 그 상태였습니다 — 파일은 만들면서 화면 스위치는 꺼져 있었습니다. 같은 실수를 반복하지 않으려면 A → B → C → D 순서를 지켜야 합니다.

B — 쓰는 쪽: 화면이 작은 그림을 쓰게 하기

소비처가 10곳입니다. 호출부마다 감싸지 말고 공용 컴포넌트 안에서 처리하는 것이 이 작업의 핵심 설계입니다.

설계 원칙 — 한 곳만 알게 한다

호출부 10곳에서 각자 thumbUrl()을 감싸면, 하나라도 빠뜨렸을 때 조용히 원본이 나갑니다. 지금 상태가 정확히 그렇게 만들어졌습니다. 게다가 404 폴백은 호출부에서 처리할 수 없습니다 — 상태가 필요합니다.

그래서 src/components/thumb-image.tsx의 ThumbImage가 이미 갖고 있는 "작은 그림 우선 + 404 시 원본 폴백" 로직을 유일한 통로로 삼고, 나머지 컴포넌트가 그것을 쓰게 합니다.

필요한 준비: ThumbImage에 호출부들이 쓰는 속성을 받을 수 있게 넓힙니다 — loading, onLoad, aria-hidden, style, key는 부모가 붙입니다. 기본값은 지금과 같게 유지합니다(loading="lazy", decoding="async").

D — 보관함이 열린 뒤

파일 쓰기·삭제가 필요해 지금은 실행할 수 없습니다. 요금 문제가 풀린 뒤 A·B·C를 배포한 상태에서 돌립니다.

  1. 소급 생성 991개 — node scripts/backfill-thumbnails.mjs --dry-run으로 대상을 먼저 확인하고 실행합니다. 저장이 약 35메가 늘어납니다. 이 파일이 저장소에 없다면 위 C-1 의 경고를 먼저 읽으세요.
  2. 잘못 만든 141개 삭제 — 생성용 임시 파일에 붙은 작은 그림입니다.
  3. 실제 전송량 측정 — 아래 6절 참조. 이걸 해야 이 명세의 숫자가 검증됩니다.
6

검증

제약 하나를 먼저 알아야 합니다

이 저장소에는 화면을 렌더해서 검사하는 시험 장치가 없습니다. 시험 실행 환경이 브라우저 없는 방식이고, 관련 라이브러리도 설치돼 있지 않습니다. 기존 156개 시험은 전부 순수 함수만 다룹니다.

그래서 "작은 그림이 실제로 화면에 걸리는가"는 자동 시험으로 못 잡습니다. 이 명세는 그 한계를 인정하고 두 갈래로 나눕니다.

자동 시험으로 잡는 것

이 저장소의 관행을 따릅니다 — 컴포넌트에서 순수 함수를 뽑아내 그것을 시험합니다(storyboardColumns, applyStoryboardZoomShortcut이 이미 그렇게 돼 있습니다).

뽑아낼 것확인할 것
3프레임 주소 목록 생성 함수rough-frame-cycle 에서 분리세 프레임이 전부 작은 그림 주소가 되는가 · ?v= 쿼리가 보존되는가 · 프레임이 없는 구버전 패널은 단일 주소로 떨어지는가

A(만드는 쪽)는 기존 시험 방식으로 잡힙니다. tests/에 이미 보관함 호출을 흉내내는 시험들이 있으므로, 세 프레임 각각에 대해 작은 그림 생성이 호출되는지 확인하면 됩니다.

사람이 확인해야 하는 것

  • 순환·일시정지·프레임 고정이 그대로인가 — 자동으로 못 잡습니다
  • 512픽셀 화질이 카드 크기에 충분한가 — 특히 fit="contain"으로 크게 담기는 러프 카드
  • 실제 전송량 — 브라우저 개발자 도구 네트워크 탭에서 그리드 화면을 열고 총 전송량을 잽니다. 이 명세의 "697메가 → 97메가"는 파일 크기로 계산한 값이지 측정값이 아닙니다. 실제로 재봐야 확정됩니다

이 저장소에는 화면을 실제로 띄워 확인하는 절차가 따로 마련돼 있습니다(/smoke). 다만 지금은 로그인이 막혀 있어 실행되지 않습니다 — 요금 문제가 풀린 뒤에 씁니다.
