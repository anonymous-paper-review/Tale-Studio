# t0-stuck-jobs-webhook-loss — 완료 소식이 돌아올 주소가 바뀌면, 그 작업들은 영영 "진행 중"인가

```yaml
id: t0-stuck-jobs-webhook-loss
source: sweep:claude:5a3338db · sweep:claude:cc9e03b1
kind: audit
budget: { usd: 0, runs: 1, wall_min: 40 }
blockers: []
status: done   # 2026-08-16 밤 — 가설 성립(12시간 이상 굳은 작업 3건/952건, 업체는 3건 다 완료), 단 시각이 나흘 간격으로 흩어지고 옆 작업은 정상 완료 → 원인을 주소 변경으로 지목하지 않음
priority: high
```

- **맥락 (사람 언어)**: 그림과 영상은 바깥 업체가 만든다. 다 만들면 업체가 우리 쪽 주소로 "끝났다"고 알려주는 구조인데, 그 주소가 **오너 컴퓨터에서 띄우는 임시 통로**를 가리키고 있다. 오너가 이미 못 박은 제약이 있다 — *"내가 그건 재실행 못 해; 하면 주소지 바뀌잖아."* 주소가 바뀌면 그 전에 주문한 작업들의 완료 소식은 갈 곳을 잃는다. 어젯밤 다른 세션도 같은 종류의 사고를 겪었고(통로가 죽어 업체가 우리 그림을 못 받아 80건 실패), 또 다른 세션은 검증 전 발견으로 *"완료 알림이 유실되면 그 작업은 영원히 진행 중으로 남는다"*를 적어뒀다. 둘 다 확인 없이 끝났다. 데이터베이스를 읽기만 하면 답이 나오고 돈이 안 든다.
- **가설**: 완료 소식을 못 받아 "진행 중"이나 "대기"인 채로 굳은 생성 작업이 데이터베이스에 남아 있다.
- **전제**: 완료 소식이 돌아올 주소를 만드는 코드가 실재하고, 그 주소의 재료가 앱 공개 주소 설정값이며 현재 값이 임시 통로 도메인이라는 것은 sweep 단계가 확인했다. 어젯밤 한 세션이 작업 기록 86건(실패 83 · 대기 3)을 지웠으므로 **그 이전 증거 일부는 이미 사라졌다** — 이 조사는 삭제 이후에 남은 것과 새로 생긴 것만 본다.
- **예측**: 참이면 굳은 작업의 주문 시각이 특정 구간에 몰릴 것이고, 그 구간이 곧 주소가 바뀐 시점이다 — 원인이 추측이 아니라 시각으로 지목된다. 거짓이면(0건) 완료 소식 경로는 지금 건강하다는 뜻이고, 세 곳에 흩어져 있던 이 걱정을 한 번에 닫을 수 있다.
- **측정**: 생성 작업 기록에서 상태가 완료도 실패도 아닌 것을 전부 뽑아, 주문 시각 기준으로 **12시간 이상 지난 것**의 건수를 센다. 함께 기록: 상태별 분포, 주문 시각의 시간대별 히스토그램, 작업 종류별 분포. 그 다음 그중 표본 몇 건이 바깥 업체 쪽에서는 실제로 끝났는지 대조한다(업체 조회는 읽기 전용, 새 주문 금지). 데이터베이스 **읽기 전용** — 쓰기·삭제 금지. 채점은 전부 세기이며 모델 판정 없음.
- **기각 조건** (사전 등록): 12시간 이상 굳은 작업이 **0건**이면 가설 기각. 1건 이상이면 성립으로 기록하되, 주문 시각이 특정 구간에 몰리지 않고 고르게 흩어져 있으면 **원인을 주소 변경으로 지목하지 않는다**(다른 원인 가능성을 열어둔 채 건수만 보고한다). 업체 쪽 대조가 접근 권한 문제로 불가하면 그 축은 확인 불가로 남긴다 — 추정으로 채우지 않는다.

## 좌표 (동결)

- 완료 소식 주소를 만드는 곳: `src/lib/fal/webhook-url.ts` (2순위 재료가 앱 공개 주소 설정값)
- 현재 설정값: `.env.local` 의 `NEXT_PUBLIC_APP_URL` — 임시 통로 도메인
- 작업 기록 테이블: `generation_jobs` (라이브 Supabase가 진실원)
- 이미 지워진 증거: 어젯밤 86건 삭제(실패 83 · 대기 3), 완료 14건만 잔존 — 삭제 시점 이후만 유효
- 같은 통로가 원인이었던 선례: 템플릿 그림 3종을 업체가 못 받아 80건 실패 → 스토리지로 이전해 해결(템플릿만 해결됐고 완료 소식 경로는 그대로)
