# 결제 도입 준비 체크리스트 (MoR 기준)

> 목적: 토이프로젝트 운영 방식(main 직푸시, live DB 직접 수정, 즉시 배포)에서
> "돈을 받는 서비스" 운영 방식으로 넘어갈 때 챙겨야 할 것들의 전체 지도.
> MoR(Merchant of Record: Paddle, Lemon Squeezy, Polar, Creem 등 — 세금·영수증·분쟁을
> 대신 맡아주는 재판매 사업자) 방식을 전제로 한다.
>
> 원칙: 1인 개발이므로 대기업 프로세스를 흉내내지 않는다.
> 아래 항목은 "법칙(안 지키면 사고)"과 "관습(편의)"을 구분해뒀다.
> ★ = 결제 켜기 전에 반드시. ☆ = 결제 켠 뒤 순차적으로.

## 0. 먼저 정할 것 (코드보다 먼저)

  MoR은 세금계산서·국내 법인 계약을 못 한다. 스튜디오 티어는 MoR로 존재 불가.

- ★ **MoR 선택 기준**: 수수료, 한국 사업자 정산 지원(달러 송금/페이오니아 등), 한국 카드 승인률,

  Polar(개발자 친화, usage-based 지원), Creem(신생, AI SaaS 특화) 중 비교.
  - MoR 입점 심사가 있다: 약관·환불정책·가격 페이지가 실제로 사이트에 게시돼 있어야 통과된다(→ 5장).
  - MoR 수수료(대략 매출의 4~7%+건당)는 v4 마진 밴드(10.3~25.0%)에 아직 반영 안 됨 — 반영 시 재검산 필요.
- ★ **v4 미결 숫자 3개** (결제 구현이 직접 막히는 것): Account 초과 단가($79~158 중 택1),
  자동 충전 월 상한 기본값, 무료 지급 Take 유효기간(1~3개월 중 택1).

## 1. 개발환경 / 배포 파이프라인

지금: main 직커밋·직푸시 → Vercel 즉시 배포, live Supabase가 유일한 DB.
결제가 붙으면 "배포 실수 = 남의 돈 문제"가 되므로 최소한의 분리가 필요하다.

- ★ **환경 3단 분리 — 확정안: `local` / `dev` / `main`** (이게 이 장의 전부. 나머지는 부수 효과)
  - `dev`·`main`은 git 브랜치다. Vercel이 브랜치를 환경으로 매핑한다:
    `main` push → Production 배포, `dev` push → Preview 배포(브랜치 고정 도메인 할당 가능).
  - DB는 2개면 된다: **개발 Supabase 프로젝트 1개를 local과 dev가 공유**, live는 main 전용.
    개발 DB를 더 쪼개는 건 1인 개발엔 관습이지 법칙 아님. 단 live를 dev가 같이 쓰는 건 금지 — 그건 분리가 아예 없는 것.
  - MoR 키 매핑: 샌드박스 키 = local·dev(Vercel Development/Preview 스코프), 라이브 키 = main(Production 스코프)에만.
    **샌드박스 키와 라이브 키가 같은 스코프에 공존하는 순간 사고가 난다** (테스트한다고 눌렀는데 실결제되는 류).
  - 웹훅 매핑: MoR 샌드박스 웹훅 → dev 브랜치 도메인, 라이브 웹훅 → production 도메인.
    local에서 웹훅까지 받으려면 터널이 필요하니, 웹훅 검증은 dev에서 하는 걸 기본으로.
  - 개발 DB 공유의 대가: local과 dev의 테스트 데이터가 섞인다. 기존 `seed:test-accounts` 규율로 충분.
- ★ **DB 백업**: Supabase 유료 플랜의 PITR(특정 시점으로 되돌리기) 활성화. 결제·크레딧 데이터는
  "지워지면 복구 불가"가 아니라 "지워지면 돈 분쟁"이다. 복원 리허설 1회 해볼 것.
- ★ **마이그레이션 규율**: 이미 `supabase/migrations/`로 운영 중(좋음). 결제 이후엔 대시보드에서
  live DB 직접 스키마 수정 금지 — 마이그레이션 파일로만. 개발 DB에 먼저 적용 → live 순서.
- ☆ **main 보호는 가볍게**: 1인 개발에 PR 리뷰 강제는 관습이지 법칙이 아니다. 대신
  "push 전 `pnpm typecheck && pnpm test` 통과"를 CI(GitHub Actions)로 걸어 배포 전 자동 차단만 확보.
  결제 코드 경로(`/api/billing/**`, 웹훅)는 테스트 없이 머지 금지를 스스로 규칙화.
- ☆ **배포 롤백 절차 확인**: Vercel instant rollback 써본 적 없으면 한 번 연습. 결제 장애 시 "이전 버전으로 5분 내 복귀"가 가능해야 함.
- ☆ **에러 추적 도입**: Sentry 등. 지금은 콘솔 로그로 버티지만, 유저가 돈 낸 뒤의 500 에러는 재현 요청을 할 수 없다.

## 2. 결제 시스템 본체 (MoR 연동 설계)

여기가 unknown unknown이 제일 많은 곳. 핵심 명제 하나로 압축된다:
**"결제 성공"의 진실원은 브라우저가 아니라 웹훅(MoR 서버가 우리 서버로 쏘는 알림)이다.**

- ★ **엔타이틀먼트(권한) 분리**: "누가 뭘 쓸 수 있나"는 우리 DB의 `billing` 테이블들이 소유.
  클라이언트가 보내는 어떤 값도 믿지 않는다. 체크아웃 성공 리다이렉트 페이지도 믿지 않는다(위조 가능).
- ★ **웹훅 처리 4원칙**:
  1. **서명 검증**: MoR이 주는 시크릿으로 서명 확인. 안 하면 아무나 "결제됨" 이벤트를 위조 가능.
  2. **멱등성**: 같은 이벤트가 2번 와도(재시도 정상임) 크레딧이 2번 적립되면 안 됨. 이벤트 ID를 저장하고 중복 무시.
  3. **순서 뒤집힘 허용**: `updated`가 `created`보다 먼저 올 수 있다. 이벤트 타임스탬프로 판단.
  4. **원본 저장**: 웹훅 페이로드 원문을 `billing_events` 테이블에 그대로 쌓는다. 나중에 분쟁·버그 추적의 유일한 근거.
- ★ **크레딧 원장(ledger)**: 잔액을 숫자 하나로 UPDATE하지 말고, 적립/차감을 행(row)으로 쌓고 잔액은 합산.
  - 이유: 환불로 음수가 되거나, 동시 생성 요청 2개가 잔액을 동시에 깎는 경쟁 상태에서 UPDATE 방식은 반드시 깨진다.
  - 차감은 생성 잡 시작 시점에 예약(hold) → 성공 시 확정, 실패 시 반환. 기존 `generation_jobs`와 잇는다.
- ★ **결제 직후 UX**: 웹훅은 결제 후 수 초~수 분 늦게 올 수 있다. 유저가 결제하고 돌아왔는데 크레딧이 0이면
  환불 문의가 온다. 성공 페이지에서 짧은 폴링("결제 확인 중…") 처리 필요.
- ★ **환불·차지백 웹훅**: `refunded`/`disputed` 이벤트에서 크레딧 회수(이미 써버렸으면 음수 잔액 허용 + 신규 생성 차단).
  MoR이 분쟁 응대는 해주지만 우리 쪽 권한 회수는 우리 코드 몫이다.
- ☆ **구독이면 추가로**: 갱신 실패(dunning — MoR이 재시도해줌), 유예기간, 취소 시 기간말까지 유지,
  플랜 변경 시 일할계산(proration)은 MoR 설정 확인. "구독 취소가 어렵다"는 앱 내 1클릭 취소 링크로 예방(규제 흐름이기도 함).
- ☆ **일일 대사(reconciliation)**: 하루 1번 MoR API의 거래 목록과 우리 `billing_events`를 비교하는 스크립트.
  웹훅 유실(우리 서버 다운 중 수신 실패)은 반드시 일어난다. 밤 루프(Orca automation)에 얹기 좋은 잡.

### 최소 테이블 스케치

```
billing_customers   (workspace_id, mor_customer_id)
billing_events      (mor_event_id UNIQUE, type, payload jsonb, received_at)  -- 원본 로그, 멱등성 키
credit_ledger       (workspace_id, delta, reason, ref_id, created_at)        -- 적립/차감/환불회수 행
subscriptions       (workspace_id, mor_subscription_id, plan, status, current_period_end)  -- 구독 쓸 경우
```

`workspaces.plan`은 유지하되, 이제 이 값을 사람이 대시보드에서 바꾸는 게 아니라 웹훅 핸들러만 바꾼다.

## 3. 보안

이미 돼 있는 것: RLS 잠금 + anon 쓰기 회수(`20260811` 마이그레이션), 요금제 게이트 서버사이드 검증.
결제 도입 시 추가:

- ★ **웹훅 엔드포인트**: 서명 검증(위 2장) + 실패 시 4xx/5xx를 올바르게 구분(5xx여야 MoR이 재시도함).
- ★ **service role 키 점검**: `supabaseAdmin`(RLS 우회 키)이 서버 라우트에서만 쓰이는지, 클라이언트 번들에
  새는 경로가 없는지 1회 감사. 결제 후엔 이 키 유출 = 전 고객 크레딧 조작 가능.
- ★ **비용 폭주(abuse) 방지**: 결제 유저가 스크립트로 생성 API를 난사하면 크레딧보다 먼저 우리 fal 청구서가 터질 수 있다.
  - 크레딧 차감을 생성 요청의 관문으로(2장 hold 방식) — 이게 rate limit을 겸한다.
  - fal/Gemini 쪽 지출 알림(billing alert) 설정. "우리 쪽 원가 상한"은 코드 밖에서도 한 겹 필요.
  - 무료 티어는 일회용 이메일 가입 반복으로 털린다 — 무료 크레딧은 짜게, 혹은 카드 등록 후에만.
- ★ **관리자 경로**: `isAdminWorkspaceOwner` 류 admin 판정이 이메일 하드코딩이면, 크레딧 수동 조정 기능이
  생기는 순간 이 판정이 돈 만지는 권한이 된다. 판정 로직과 감사 로그(누가 언제 얼마 조정) 확인.
- ☆ **감사 로그**: 크레딧 수동 조정·플랜 변경 같은 운영 행위는 전부 행으로 남긴다(위 ledger의 `reason`으로 충분).
- ☆ **시크릿 로테이션 절차**: MoR API 키·웹훅 시크릿·service role 키를 유출 시 어떻게 교체하는지 한 번 적어두기.
- 참고: **카드 정보는 우리가 만지지 않는다**(MoR 체크아웃이 처리) → PCI-DSS(카드정보 보안 인증)는 사실상 범위 밖. 이게 MoR의 최대 장점.

## 4. 정책 / 법무 문서

MoR 입점 심사에서 요구하는 것 + 실제로 분쟁을 막아주는 것. 전부 사이트 푸터에서 접근 가능해야 한다.

- ★ **이용약관(Terms of Service)**: 서비스 범위, 계정 정지 사유, 생성물의 권리 귀속(AI 생성물 소유권 — 이 서비스 특성상 중요),
  보증 부인. 템플릿에서 시작하되 "생성 결과물 라이선스" 항목은 직접 정해야 함.
- ★ **환불 정책(Refund Policy)**: MoR 심사 필수. 디지털 재화 특성상 "크레딧 사용 전 N일 내 환불, 사용분은 불가" 류로
  명확히. EU 소비자의 14일 철회권은 "즉시 제공 디지털 콘텐츠 동의" 문구로 처리(MoR 체크아웃이 대부분 커버 — 설정 확인).
- ★ **개인정보처리방침(Privacy Policy)**: 뭘 수집하고(이메일, 프로젝트 데이터, 생성 프롬프트), 어디로 가는지
  (Supabase, Anthropic, Google, fal, MoR — 서브프로세서 목록), 삭제 요청 처리 방법.
- ★ **가격 페이지 실물화**: 현재 pricing 페이지는 "베타 끝나면" 예고 상태. MoR 심사는 실제 가격이 게시된 페이지를 요구.
- ☆ **계정 삭제 플로우**: 활성 구독/잔여 크레딧이 있는 계정의 삭제 요청 처리 순서를 정해두기(구독 취소 → 데이터 삭제).
- ☆ **지원 채널 명시**: 문의 이메일 하나는 반드시 게시(MoR도 요구). 결제 문의는 MoR로, 서비스 문의는 우리로 가는 안내.

## 5. 세무 / 사업 (한국 사업자 관점)

MoR 구조에서는 **판매자가 MoR**이고, 우리는 MoR에게 정산금을 받는 관계다. 그래서:

- 소비자 대상 부가세(VAT/sales tax) 신고·납부는 MoR 몫 — 우리가 각국 세무서에 등록할 필요 없음. 이게 MoR을 쓰는 이유.
- ★ **사업자 등록**: 정산금을 받으려면 사업자(개인사업자면 충분) + 외화 수취 계좌(또는 페이오니아 등). 이미 있으면 통과.
- ★ **우리 몫의 세무**: MoR에게 받는 정산금은 우리 매출 — 종합소득세/부가세 신고 대상. 영세율(외화획득 용역) 적용 여부는
  세무사에게 1회 확인 (여기서 단정하지 않음 — 확인 필요 항목).
- ☆ **통신판매업 신고**: 판매자가 MoR이므로 불필요하다는 해석이 일반적이나, 국내 소비자 비중이 커지거나
  국내 PG를 붙이는 시점엔 필요해진다. 그 시점에 재확인.
- ☆ **한국 B2B 고객의 세금계산서 요청**: MoR은 한국 세금계산서를 못 끊는다. B2B 수요가 생기면 별도 계약 경로 필요 — 지금은 무시.

## 6. 운영 / 모니터링

- ★ **웹훅 실패 알림**: 웹훅 핸들러 에러는 조용히 죽으면 안 된다. 실패 시 알림(이메일/슬랙/텔레그램 아무거나) 필수.
  "유저는 결제했는데 크레딧이 안 들어옴"이 최악의 장애 유형이고, 이건 유저가 신고하기 전에 우리가 알아야 한다.
- ★ **생성 원가 대시보드**: 일별 fal/Gemini 지출 vs 크레딧 매출을 볼 수 있는 최소한의 쿼리. 마진이 음수로 뒤집히는 걸
  월말 청구서에서 처음 알면 늦다.
- ☆ **결제 플로우 스모크**: staging에서 MoR 샌드박스 카드로 "체크아웃 → 웹훅 → 크레딧 적립 → 생성 1회 → 차감 확인"
  전 구간을 도는 테스트를 `pnpm test:manual` 계열로. (실 카드 결제는 자동화 금지 — 기존 스모크 헌법과 동일.)
- ☆ **장애 대응 카드 1장**: "결제는 되는데 크레딧이 안 들어올 때 → billing_events 확인 → 수동 적립 절차" 같은
  플레이북을 티켓 형식으로 vault에 하나. 새벽에 문의 오면 자는 머리로도 따라할 수 있게.

## 7. 착수 순서 (확정: 환경 → 권한 → 결제)

결제는 권한 시스템의 스위치일 뿐이다. 스위치를 먼저 만들면 붙일 곳이 없다.

1. **환경 분리** (반나절~1일) — `dev` 브랜치 + 개발 Supabase 프로젝트 + Vercel env 스코프 분리
   + live PITR 켜기 + CI(typecheck·test) 배포 전 차단. 이후 모든 작업이 live 밖에서 돌게 하는 안전판.
2. **유저별 권한(엔타이틀먼트) — 결제 없이 먼저** — v4 과금 축 4개(프로젝트당 생성 최대·연결·Take·Export)
   + Account를 스키마와 게이트로 구현. Take 원장(hold/확정/반환)을 `generation_jobs` 경로에 배선,
   생성 전 Take 소모량 표시(v4 #2), 소진 순서(무료→플랜분→충전분). 검증은 관리자 수동 플랜 부여로 —
   이 수동 경로가 나중에 국내 B2B 수동 계약 경로(0장)로 재사용된다. `plan-limits.ts`·`generation-quota` 뼈대 위에 얹는다.
3. **결제(MoR) 붙이기** — 체크아웃 + 웹훅(서명검증·멱등성·원본저장). 2단계가 끝나 있으면 웹훅이 할 일은
   "플랜 세팅 + Take 적립" 두 줄로 줄어든다. 병렬로: 기획 안건(`payments-planner-agenda.html`) 논의,
   정책 문서 4종 + 실가격 페이지 → MoR 입점 심사 제출.
4. **dev 전 구간 스모크** (샌드박스 카드: 체크아웃 → 웹훅 → 적립 → 생성 1회 → 차감) → 심사 통과 → 라이브 키 전환
5. 라이브 후: 일일 대사 스크립트, 웹훅 실패 알림, 원가 대시보드 (☆들)
