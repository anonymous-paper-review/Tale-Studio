## 2. preview 를 그대로 앵커로 쓰면 안 되는 이유 (팀리드 질문 2)

**결론: 절대 금지.** 근거 4겹.

1. **스킬 규정 위반 (명문)** — SKILL.md 마지막 줄:
   > "프로덕션 배선 시: 보드 = `style_anchors.image_url`(I2I), 원작/쇼케이스 = `preview_url`.
   > **원작 이미지를 프로덕션 앵커 슬롯에 직결 금지** (콘텐츠/정체성 누수)."
   preview 는 정의상 원작/쇼케이스 슬롯의 물건이다.

2. **앵커는 대부분 경로에서 1번 레퍼런스 = 최강 지배 위치** (`src/lib/style-anchor.ts:64`).
   `STYLE_ANCHOR_CLAUSE`(`style-anchor.ts:4`)의 방어는 `"Do NOT reproduce its subject or objects."` **한 문장뿐**이다.
   피사체가 정물이면 이 문장이 막을 게 별로 없지만, 피사체가 **여우 셰프 + 파리 옥상 + 에펠탑 + 구리 냄비 + 스트링 라이트**면
   막아야 할 표면이 폭증한다. 1번 자리의 강한 이미지 신호 대비 방어 문구가 1문장이라는 비대칭이 문제다.

3. **의인화 종(種) 누수 — 이 preview 특유의 위험.** 피사체가 사람이 아니라 **의인화 여우**다.
   캐릭터 생성 경로(`character_view` 턴어라운드)에서 1번 레퍼런스가 수인이면
   산출 캐릭터에 머즐·짐승 귀·퍼가 섞일 확률이 구조적으로 높다. 정물 앵커에는 없던 종류의 실패 모드다.

4. **IP 인접성.** 파리 옥상 + 요리 + 소동물 셰프 + 그 여우 디자인은 특정 스튜디오 작품군을 강하게 환기한다.
   프로덕션 전 프로젝트의 **모든** 생성물에 1번 레퍼런스로 박히는 슬롯에 넣을 물건이 아니다.
   (스킬도 같은 이유로 고유명사 자체를 금지 — 생성기가 nsfw 거부까지 한다.)

**그러나 preview 는 "목표 레지스터의 정의"로서는 유효하다.** 오너가 그것을 보고 골랐기 때문이다.
따라서 본 작업은 preview 를 **I2I 생성 레퍼런스로만** 쓰고(스킬 단계 3 의 정상 용법), 산출된 중립 보드를 앵커로 승격한다.
누수 여부는 단계 4 QA + 단계 5 전이 프로브로 검증한다.

### 3.2 인물 방언 절 (정물 보드가 못 나르는 부분 — 이번 교체의 핵심)

> 어필 있는 장편 애니메이션 비율, 성인 약 6두신, 약간 커진 두개골, 부드럽게 가늘어지는 사지, 작고 정제된 손.
> 크고 맑은 눈 — 젖은 메니스커스와 하나의 지배적인 둥근 스펙큘러 하이라이트, 단순화된 방사형 홍채, 부드러운 눈꺼풀 볼륨, 딱딱한 아이라인 없음.
> 작고 낮은 부조의 단순화된 코·입, 둥근 볼에 따뜻한 서브서피스 홍조.
> 의복은 조각된 볼륨으로 읽히며 두껍고 부드러운 주름 소수.

### 3.3 Core / Supporting / Content-bound

- **Core (반드시 보드가 나름)**: 비포토리얼 아트디렉티드 PBR · 소프트 GI + 림 · 둥근 어필 형태언어 · 서브서피스 피부 · 클럼프 머리카락 · 저주파 재질 · 아웃라인 없음 · 인물 비율

### 3.4 설계 판단 — 앰버 그레이드를 일부러 버렸다 (스킬 기본값에서 벗어난 지점)

스킬 단계 1 은 "팔레트는 단어 대신 hex 로 프롬프트에 직접 넣는다"고 규정한다. **이번엔 넣지 않았다.** 근거 3개:

1. **모작 방향 가드 (SKILL.md)** 의 판별 질문 — "이 요소가 다른 인물·공간·시간대에서도 반복되는가?"
   석양 앰버는 **아니오**다. 그건 이 preview 장면의 시간대지 "3D 애니메이션"이라는 매체의 불변량이 아니다. → Content-bound.
2. **A′ 마네킹 보드 실측 (SKILL.md)**: "보드의 각진 기하·좁은 팔레트가 인물뿐 아니라 **장면·사물 전체에 전파**. 보드 선택 = 룩 결정 행위."
   → 앰버를 보드에 구우면 이 앵커를 고른 **모든 프로젝트의 모든 프레임이 석양**이 된다. 밤 씬도, 실내도.
3. **현행 카탈로그의 실제 병증이 그것** (§1.2) — 지금 `real_3d` 가 `real` 과 갈리는 지점이 매체가 아니라 색온도인 이유가
   바로 보드에 구워진 따뜻한 그레이드다. 앰버를 유지하면 교체해도 같은 혼동이 반복된다.

→ 두 후보 모두 **중립 주광(cool white daylight)** 으로 고정하고, 프롬프트에 `NOT sunset / NOT golden hour / NOT orange / NOT amber` 를 명시 부정했다.
   이렇게 하면 `real` 과의 델타가 **그레이드가 아니라 스타일라이제이션**에 놓인다 — 그게 원래 이 앵커가 팔아야 할 차이다.

### 3.5 E′ 기본 회귀 방지 절 — 적용과 1건 대체

## 4. 보드 설계 — 정물 단독으로는 못 고친다

### 4.1 문제의 형식화

forensics §4.1 이 확정한 것: 정물 앵커가 운반 가능한 정보 = {재질, 조명, 컬러그레이드, DoF}.
사람이 "3D 애니메이션"을 판별하는 근거 = 주로 {두신비, 얼굴 조형, 피부·머리카락 셰이딩, 아웃라인 유무}.
**교집합이 거의 비어 있다.** 그래서 배선이 정상인데도 "전혀 안 지켜진다"가 성립한다.

즉 B1 은 "보드를 더 잘 그린다"가 아니라 **"보드에 캐릭터 조형 정보를 넣는다"** 여야 한다.
그런데 캐릭터를 넣는 순간 `STYLE_ANCHOR_CLAUSE` 의 "Do NOT reproduce its subject" 를 지켜야 할 대상이 생긴다 — 이게 B1 의 명시 리스크다.

### 4.2 정체성 누수를 낮추는 4겹 설계

보드 안 인물을 **"캐릭터"가 아니라 "해부·셰이딩 스터디"** 로 만든다:

1. **익명성 락(프롬프트 명문)** — "an anonymity-locked anatomy-and-shading study, **NOT a character**: ordinary plain features, plain short dark hair, a plain solid-color short-sleeved shirt and plain long trousers, calm neutral expression, no acting, no accessories, no jewelry, no makeup, no logo, no pattern, nothing held in the hands."
   → 복사 가능한 **정체성 표면(헤어스타일·의상·소품·표정 연기)을 전부 제거**한다. 남는 건 조형 언어뿐이고, 그게 우리가 원하는 것이다.
2. **종(種) 락** — "Human — not an animal, not anthropomorphic, no fur, no muzzle, no tail, no animal ears."
   → §2-3 의 의인화 여우 누수를 생성 단계에서 차단.
3. **중립 포즈·중립 조명** — 연기 없는 이완된 정면 3/4 입상. 포즈가 밋밋할수록 하류가 베낄 유인이 없다.
4. **정물 7요소 동시 유지** — 카탈로그 형제와의 비교 가능성 + 재질 정보를 잃지 않기 위해. 보드는 정물을 **버리지 않고 확장**한다.

**남는 리스크 (프로브로만 판정 가능)**: 익명 인물이라도 하류 캐릭터 생성에서 얼굴이 복사될 수 있다.
SKILL.md 의 A′ 선례는 "마네킹의 장면 누수는 n=1 미발현('Do NOT reproduce its subject' 절이 방어)" 이라 기록하면서도 **게이트는 유지**하라고 못박았다. 그 게이트가 §6 이다.

### 4.3 두 후보 — A/B 축은 "정보량 ↔ 누수 위험"

| | C1 — 통합 정물+입상 | C2 — 스터디 보드 |
|---|---|---|
| 구성 | 카탈로그 정물 7요소 그대로 + 그 뒤에 익명 인물 전신 입상 1인 | 한 평면 위 3 스터디: 좌=익명 인물 두상 클로즈업, 중=동일 인물 전신 소형, 우=재질 클러스터 |
| 얼굴 정보 | 중 (전신 거리라 얼굴이 작음) | **고** (두상 클로즈업 = 눈·피부·머리카락 최대 해상도) |
| 누수 위험 | 낮 (장면 속 한 사람) | **높** (클로즈업 얼굴이 가장 복사되기 쉬운 표면) |
| 형제 호환성 | **높** (정물 세팅 유지 → `real`·`jp_anime` 와 나란히 비교 가능) | 낮 (세팅이 다름) |
| 부수 위험 | 인물이 "장면"으로 읽혀 배경 구성이 하류로 샐 수 있음 | 모델이 패널·라벨·텍스트를 그릴 수 있음 (부정문으로 방어) |

두 안 모두 §3.2 인물 방언 절을 프롬프트에 포함했다. 프롬프트 원문: `dev/Image_Style/real_3d_v2/prompt_c1.txt`, `prompt_c2.txt`.

### 5.4 각 후보의 결함 (육안)

**C1 — 구조 결함 1건 (중간 심각도)**
인물의 발이 탁자 상판 평면 위에 겹쳐 그려졌다. 벽-바닥 경계선보다 신발이 아래(=앞)에 있어
"탁자 뒤 바닥에 선 사람"이 아니라 "탁자 위에 선 사람"으로도 읽힌다. 원근 오류다.
앵커의 임무가 스타일 운반이고 하류는 레이아웃을 복사하지 않으므로(`Do NOT reproduce its subject`) **전이 성능에 미치는 영향은 작다고 판단**하지만,
레퍼런스 보드로서 눈에 띄는 흠이다. 스킬은 ≤2회 재시도를 허용하므로 오너가 C1 을 고르면 재생성 1회 권장.

**C2 — 스케일 부조화 (경미, 설계상 허용)**
전신 인물이 사과·컵과 같은 탁자 위에 소형으로 서 있어 초현실적이다. 다만 "스터디 보드" 관례로 읽히고,
오히려 **"이건 장면이 아니라 스터디다"** 라는 신호를 줘서 §4.2 의 익명화 의도를 강화하는 쪽으로 작동한다.

**C1 의 숨은 약점 — 레지스터 분열**
C1 은 소품(나무결·사과·스텐 반사)이 인물보다 **사진 쪽에 가깝다**. 한 보드 안에서 인물=애니메이션 / 사물=준포토리얼로 갈린다.
이건 위험하다 — 현재 프로덕션의 실패 양상이 정확히 "사물·배경이 실사로 나온다"이기 때문에,
C1 은 그 실패를 앵커 안에 그대로 재현할 수 있다. **C2 는 소품도 확실히 단순화된 스타일라이즈드 렌더**라 이 분열이 없다.

### 5.5 새로 생긴 리스크 — 채도 과교정 (정직하게 기록)

§3.4 에서 앰버를 의도적으로 버렸는데, 그 결과 **채도가 52% → 23%(C1) / 16%(C2)** 로 크게 떨어졌다.
A′ 선례("보드의 좁은 팔레트가 장면·사물 전체에 전파")를 그대로 적용하면, **이 보드는 하류를 탈색시킬 수 있다.**
preview 의 매력 중 상당 부분이 채도 있는 색에서 나온다는 점에서 이건 앰버 문제의 **거울상 실패**다.
- C2(16%)가 C1(23%)보다 위험이 크다.
- 이것이 §6.1 G3 를 **양방향 게이트**로 설계한 이유다. 프로브에서 카페·야간 씬이 탈색돼 나오면 과교정 확정.
- 교정 방법은 앰버 복귀가 **아니라**, 보드 소품에 채도 있는 색을 넣되 조명은 중립으로 유지하는 것
  (예: 천을 선명한 청색, 과일을 선명한 적색으로 지정 — 시간대가 아니라 오브젝트 색이므로 Content-bound 가 아니다).

### 6A.3 채도 과교정(§5.5) 검증 — 우려보다 가볍다 (단, 지표가 이 질문에 부적합)

| 프로브 | 채도 | 명도 | 해석 |
|---|---|---|---|
| C1 character | 13% | 87% | **측정 불가** — 플랫 백색 배경이 화면 대부분이라 지표가 배경에 지배됨 |
| C2 character | 8% | 80% | 동일 사유로 측정 불가 |
| C2 cafe | 28% | 59% | 정상 범위 |
| C2 scooter | 20% | 44% | 야간 씬으로 타당 |
| C2 action | 35% | 31% | **양호** — 야간인데도 채도가 살아 있음 |

실제 장면 3종이 20~35% 로 각 시간대에 타당한 채도를 냈다. **탈색은 일어나지 않았다.** §5.5 의 우려는 과대평가였다.
단 두 가지 정직한 단서:
1. character 프로브의 8~13% 는 **탈색 증거가 아니다** — 플랫 배경 때문에 지표가 무의미하다. 이 수치로 어느 쪽 주장도 하면 안 된다.
2. 표준 프로브 콘텐츠 자체가 칙칙하다("worn utility jacket", "cargo trousers", 야간 2종). **채도 축을 재려면 프로브 세트에 밝은 색 씬이 하나 필요하다** — 스킬의 표준 4종에 대한 개선 제안.

또 하나: C1 프로브(13%)가 C2 프로브(8%)보다 채도가 높고, 보드 채도도 C1(23%) > C2(16%) 였다. 표본 1쌍이라 단정은 못 하지만 **보드 채도가 하류로 전파된다는 A′ 선례와 방향이 일치**한다.

**보정 측정 — 배경을 제외하면 결론이 바뀐다.** 위 수치가 배경에 오염됐다는 의심을 검증하려고
밝은 무채색 픽셀(V>230 & S<25)을 배경으로 보고 제외한 뒤 다시 쟀다:

| 이미지 | 전체 채도 | 배경 제외 채도 | 전경 비율 |
|---|---|---|---|
| C1 character 프로브 | 12.8% | **24.7%** | 30% |
| C2 character 프로브 | 8.0% | 9.3% | 77% |
| C1 보드 | 22.7% | 25.9% | 84% |
| **C1b 보드** | 25.0% | **25.7%** | 97% |
| C2 보드 | 15.9% | 18.5% | 84% |

두 가지가 드러난다:
1. **C1 프로브의 "탈색"은 허상이었다** — 12.8% 는 백색 배경이 만든 값이고 인물만 보면 24.7% 로 보드와 같은 수준이다. §6A.3 표의 character 행은 이 보정으로 대체해 읽어야 한다.
2. **후보 간 비교는 성립하지 않는다** — 세 프로브의 배경이 제각각이다: C1=순백(30%만 전경), C2=밝은 웜그레이(77%), C1b=중간 그레이(**100%** — 필터가 하나도 못 걸러냄). 배경 필터가 셋에 서로 다르게 작동하므로 **11.1% / 9.3% / 24.7% 는 애초에 같은 것을 재고 있지 않다.**
   → **이 지표로는 후보 간 채도 우열을 판정할 수 없다.** 앞서 "보드 채도가 하류로 전파된다(A′ 방향 일치)"고 쓴 문단은 이 보정으로 **철회한다** — C1b 는 보드 채도가 가장 높은데 프로브 채도는 가장 낮게 찍혔다(11.1%). 방향이 뒤집힌다.
   → 육안으로는 세 인물 모두 비슷한 톤이고, 그 칙칙함의 출처는 보드가 아니라 **프로브 프롬프트 자체**다("worn utility jacket", "cargo trousers"). 보드 채도의 하류 전파 여부는 **이번 실험으로는 미결**이며, 재려면 밝은 색 콘텐츠 프로브가 필요하다(§6C.1).

그리고 정직하게 덧붙이면, **C1b 의 채도 개선은 이 지표로는 거의 안 잡힌다**(25.9% → 25.7%, 사실상 동일).
면적 가중 평균이라 벽·탁자가 화면을 지배하고 채도를 실어 나르는 오브젝트(청천·적사과·녹식물)는 면적이 작기 때문이다.
**육안으로는 색이 확실히 돌아왔는데 지표는 침묵한다** — 이 질문에 대해서는 `style_stats.py` 의 채도 평균이 부적합한 계기다.
판정은 육안이 맡고, 지표는 §5.2 의 플랫 블록(레지스터 이동)처럼 지표가 실제로 민감한 축에만 쓰는 게 맞다.

## 6C. 이 검증의 한계 (반증 가능성 유지)

## 8. DB 초안 SQL (미실행)

**본 세션은 DB 를 만지지 않았다.** 아래는 오너 육안 승인 후 실행할 초안이다.

전제: 승인된 보드를 Supabase Storage `media/style-anchors/` 에 **새 파일명으로** 올린다.
기존 `real_3d.png` 를 덮어쓰지 **않는다** — 롤백 가능성과 기존 산출물의 출처 추적을 위해.

```sql
-- 0) 사전 확인 (현재 값 보존용 — 실행 전 캡처해 둘 것)
select key, label, medium, image_url, preview_url, is_active
from style_anchors where key = 'real_3d';

-- 1) 교체 (승인된 후보의 새 URL 로)
update style_anchors
set image_url = 'https://qnjnrihfpqkdhjuzvepy.supabase.co/storage/v1/object/public/media/style-anchors/real_3d_v2.png'
where key = 'real_3d';

-- 2) 롤백 (사고 시)
update style_anchors
set image_url = 'https://qnjnrihfpqkdhjuzvepy.supabase.co/storage/v1/object/public/media/style-anchors/real_3d.png'
where key = 'real_3d';
```

주의 4건:

0. **RLS 때문에 앱 경로로는 못 고친다.** `supabase/migrations/20260811120000_lock_rls_and_revoke_anon_writes.sql:63-67` 이
   `style_anchors` 에 RLS 를 켜고 **`for select using (is_active)` 정책 하나만** 만들었다. INSERT/UPDATE 정책은 없고
   같은 마이그레이션이 anon 의 쓰기 권한을 회수했다. → 이 UPDATE 는 **테이블 소유자(admin) 경로로만** 통과한다.
   `supabase db query --linked` 가 그 경로다 (소유자는 RLS 를 우회 — `force row level security` 미설정 확인됨).

1. **`preview_url` 은 건드리지 않는다.** 오너가 고른 그 그림이 픽커에 계속 떠야 한다.
   B1 은 "preview 를 anchor 쪽으로 끌어오는" 처방이지 그 반대가 아니다. (preview 통일은 B2 소관, 별건.)
2. **`resolveStyleAnchorByKey` 에 5분 TTL 메모리 캐시**가 있다 (`src/lib/style-anchor.ts:24`, `STYLE_ANCHOR_CACHE_TTL_MS`).
   UPDATE 직후 최대 5분간 **구 URL 로 계속 생성**된다. 서버리스라 인스턴스별로 만료 시점도 다르다.
   → 교체 직후 즉시 검증 생성을 돌리면 **구 앵커 결과를 보고 "효과 없음"이라 오판**할 수 있다. 5분 대기 후 측정할 것.
3. **기존 산출물은 불변**이고 신규 생성만 룩이 바뀐다 (forensics B1 리스크 평가와 동일). 진행 중 프로젝트에서 룩이 갈릴 수 있음을 오너가 인지해야 한다.
   `dc531572-…` 는 이미 36샷을 구 앵커로 뽑았으므로, 재생성 시 기존 프레임과 섞이면 톤이 불일치한다.

적용 방법은 `supabase db query --linked` (프로젝트 메모리: `db push` 는 막혀 있음).
